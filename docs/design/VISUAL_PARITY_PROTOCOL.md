# 页面与原型的一致性怎么验（做法，不是提醒）

立于 2026-09-20。起因是 Lemon 的一句话：

> 「我想先问问你，为什么设计图和实际做出来就有这么大差距呢……你只解决了眼前问题没有用，
> 根源是你实际做出来的和设计有差距，你却不知道，这是机制和底层问题，你需要彻底解决。」

关键词是**「却不知道」**。不是手艺不行，是**验证方式本身查不出差距**，所以每次都要等
Lemon 看见了才发现。本文件写的是替代验证方式，不是「下次注意」。

---

## 一、为什么「看截图」这条路不成立

当天连续踩到四个坑，每一个都足以让视觉判断失真：

| # | 坑 | 后果 |
|---|---|---|
| 1 | 视口 emulation 会被悄悄清掉（回合结束、窗格宽度变化、有时导航后） | 一直在 **280px** 窄屏下看，命中 `max-width:640px` 的堆叠规则，看到三段竖排；Lemon 看到的是 1440px 下三段并排。**看的根本不是同一个东西** |
| 2 | 用 CSS `zoom` 放大看细节 | `zoom` **参与布局计算**，放大 2 倍等于把可用宽度砍半，三等分段被挤成两行。这个「缺陷」是放大手法自己造出来的 |
| 3 | `computer zoom` 的 region 裁剪在 Browser pane 不支持 | 悄悄退化成全屏截图，且被缩到 800×500 —— 只有真实分辨率的 **55%** |
| 4 | 就算前三条都躲开了 | 「段高差 5px」「纵向对齐差 23px」这种量，肉眼在缩水的截图上判不了 |

第 1 条最致命：它不报错，只是安静地给你一个不同的世界。

## 二、替代做法

### 1. 只信数字，数字从两边同一视口实测

`scripts/visual-parity.mjs`：用系统已装的 Chrome（headless）+ Node 内置 WebSocket 走 CDP，
零依赖，不装 puppeteer。它把**已确认原型**和**实现页面**放进同一视口，取同一组量，逐项比。

```bash
PARITY_ADMIN_BASE=http://localhost:8803 PARITY_ADMIN_PASSWORD=... \
  node scripts/visual-parity.mjs
```

退出码：`0`=一致，`1`=有差异，`2`=跑不起来。
**`2` 单独列出来**，因为「环境坏了」伪装成「通过」是这类工具最常见的失效方式。

比什么由契约决定（`docs/design/parity/*.json`），一份契约 = 一块界面：

```json
{
  "prototype": { "file": "docs/design/prototypes/step6-opsbar-v4.html", "root": ".D" },
  "impl":      { "url": "${PARITY_ADMIN_BASE}/admin/", "root": ".wb-ops",
                 "login": { "passwordEnv": "PARITY_ADMIN_PASSWORD" } },
  "probes": [
    { "name": "三段", "proto": ".seg", "impl": ".wb-seg", "all": true,
      "metrics": ["height", "contentTop", "contentBottom", "padding"] }
  ]
}
```

`contentTop` / `contentBottom`（首尾子元素到容器上下边的距离）是性价比最高的两个量：
**顶对齐、居中、底对齐的差别全在这两个数上**，而这正是肉眼最容易放过、观感上最扎眼的一类差距。

### 2. 结构不同构的地方不要硬比

原型和实现的 DOM 很少长得一模一样（原型里 `.col` 包着标题和内容，实现里标题和内容是
`.wb-seg` 的两个平级子元素）。**别比 `gap` 这种依赖具体嵌套的量**，会误报；比
`height` / `contentTop` / `contentBottom` 这种「结果量」—— 内部怎么排的不重要，
排出来占多高、上下留多少才重要。

宽度同理：两边容器宽度本来就不同（原型页面 1162px，后台内容区 1126px），
段宽不该比，比了全是噪音。

### 3. 契约要写进仓库，不是跑完就算

新做一块界面 → 原型定稿 → **当轮**写一份契约。契约在仓库里，
以后任何人（任何窗口）改那块 CSS，`scripts/wrapup-check.sh` 第 9 项会替他发现改坏了。

### 4. 工具自己先做变异测试

这条来自项目既有规矩（判断工具的假阳性比报错危险，人会学会略过它）。
契约写完后，**把已知的正确实现改坏，确认脚本报得出来**：

| 变异 | 期望 | 2026-09-20 实测 |
|---|---|---|
| 撤掉 `justify-content:center` | 报 contentTop/Bottom 差异 | ✓ 报出 4 处，差 23px / 17.5px |
| 行距 7px 改回 2px | 报段高差异 | ✓ 报出 7 处，差 5px |

自测本身也抓出了脚本的真缺陷：`#wb-routes` 是接口返回后才渲染的，
`load` 事件后立刻测会时灵时不灵 —— 补了 `waitForSelectors`。
**没做变异测试就不会发现它，只会看到一个偶尔「通过」的脚本。**

## 三、仍然需要用眼睛的部分

比对脚本只管**几何量与关键样式**。这些它管不了，仍要看：

- 颜色搭配、留白节奏、字体观感是否「好看」
- 信息层级对不对、文案是否啰嗦（Lemon 明确要过：**界面上不要写解释旁白**）
- 交互是否割裂（如「下拉 + 按钮」本是一次操作的两半，做成两个独立控件就割裂）

用眼睛的时候，**先满足三个前提**，否则看了等于没看：

1. 视口先设好，**测量/截图前断言 `innerWidth`**（这条今天拦住过两次错误判断）；
2. 要放大看细节，用 `transform: scale()`，**绝不用 CSS `zoom`**；
3. 知道交付的截图被缩过，细节结论不要建立在截图上 —— 让数字兜底。
