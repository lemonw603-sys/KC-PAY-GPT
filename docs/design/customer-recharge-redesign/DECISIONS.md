用户已确认按以下建议推进，并新增 Session 教程与订阅确认入口（均已做进原型，纯前端、不碰后端）：

- **邮箱不打码、卡密打码**：确认页完整展示邮箱（核对优先），卡密前 4 + 后 2 打码。（B1 / B8 → 定）
- **先只上 Light，保留 Dark**：Dark 代码保留、默认关闭，想开随时开。（B2 → 定）
- **不新增确认前 preview 接口**：前端本地解析邮箱已够；有效性由创建接口判定。（B3 → 定）
- **FAILED 客户结果码**：认可价值，但需后端配合，排到本次之后。（B4 → 延后）
- **轮询节奏落地改回生产值**：属落地清单，见 HANDOFF §3。（B6 → 定）
- **保留「提交新的充值」入口**：受 CDK 一次性保护，不会重复扣款。（B7 → 定）
- **新增 ① Session 获取教程弹层**：输入页与更换 Session 处均有「如何获取 Session？」入口；弹层含 4 步引导 + 两个官方外链（`chatgpt.com`、`chatgpt.com/api/auth/session`）+ 脱敏 JSON 示例 + 安全提示。参考同类站 lmfai666.com 的做法，但收敛为不占首屏的弹层。
- **新增 ② 订阅确认（轻量版）**：成功状态加「去 ChatGPT 官网确认订阅状态」外链，跳官方设置页，本页不经手订阅信息。**否定**自建订阅查询后端（见 C11）——经核查该参考站的「订阅查询」本身也只是跳转 `chatgpt.com` 的外链。

## 正式移植结论（2026-09-01）

- 用户已确认采用 Claude 的整体视觉与交互方向，不再把旧双栏候选 `491be96` 当作本次设计结果。
- 正式客户页采用：单列三步、独立邮箱核对、确认前零订单请求、确认后才建单、页面内持续展示状态、成功就地展示且不弹窗。
- 左侧固定展示区删除；移动端允许适度压缩高度，但不以压缩为由牺牲邮箱核对和状态可见性。
- Claude 可自由发挥视觉、布局、动效和非事实性文案；只修明确错误或无法证明的事实承诺，不用额外限制压缩设计空间。
- 必须修正的事实口径：确认前只在本地读取 Session 内声明的邮箱；确认后完整 Session 仍用于充值。不得绝对承诺“系统只读取邮箱”“不会读取 Session”或未经验证的“全程加密”。邮箱确认文案只要求客户确认目标邮箱，不承诺前端已证明 token 当前真实身份。
- 正式移植已经进入 `v1/public` 本地候选并通过本地验证；尚未部署生产，生产仍是旧客户页。实现和验证证据见 `docs/2026-09-01_customer-recharge-redesign-production-candidate.md`。

## C. 被否定（评估后放弃，附理由）

| # | 放弃的方案 | 理由 |
|---|---|---|
| C1 | 保留双栏 + 左侧固定介绍栏 | 与「单焦点、降低理解成本」冲突；用户明确授权删除 |
| C2 | 保留成功模态弹窗 | 用户明确要求就地展示、不打断；信息与状态区重复 |
| C3 | 确认页调用后端接口「解析/预览邮箱」 | 违反「确认前零请求」；且现无此接口。改为纯前端解析 `session.user.email` |
| C4 | 前端在确认页复刻后端完整 Session 校验（有效期 / JWT claims / 是否已 Plus） | 会分叉并重复后端逻辑，且不允许改后端；有效性仍由创建接口权威判定，前端只负责「读到邮箱」 |
| C5 | 用「进度百分比数字条」表示处理进度 | 后端无真实进度量，假百分比会误导客户；改用脉冲 + 时间线 + 自动刷新表达「在动」 |
| C6 | 为「更透明」向客户展示内部状态 / 失败技术原因 | 违反硬边界；对客户无意义且徒增不安（尤其 `SUBMIT_UNKNOWN` 这类资金不确定态） |
| C7 | Tab 并列「提交 / 查询」占据首屏 | 绝大多数是提交客户；查询降为顶栏次要入口，减少首屏决策负担 |
| C8 | 客户侧退款 / 交易查询入口 | 硬约束：退款、交易、余额仅内部后台处理，客户侧不提供 |
| C9 | 引入外部字体 / UI 框架 / CDN 资源 | 支付类页面重信任与加载稳定性；坚持零外部依赖，且现有 helmet/CSP 环境更安全 |
| C10 | 把 Session 明文暂存到 `localStorage` 以便「返回修改」保留 | 泄露风险；改为仅在内存 `pending` 暂存，离开即弃，查询码才入 `sessionStorage` |
| C11 | 自建「订阅查询」后端（用 session 调 ChatGPT 官方订阅接口查订阅状态） | 要动后端、扩大敏感数据面、有稳定性/封号风险，收益不匹配；参考站自身的「订阅查询」也只是跳转官网外链。改为成功页官方外链的轻量版 |

## D. 与现有实现的语义一致性核对

以下确认「重设计没有改变任何业务语义」：

- 【事实】三接口入参 / 出参 / 错误码沿用 `create-app.js`、`order-status-service.js`、`order-intake-service.js`，未增删字段。
- 【事实】状态映射沿用后端 `CUSTOMER_STATUS`，前端不新增 / 不重定义任何状态。
- 【事实】`parseSessionInput`（剥离浏览器扩展尾随文本、取首个完整 JSON）逻辑与现有 `customer.js` 一致，行为不变。
- 【代码验证】创建订单仅发生在确认后的 `confirmCreate` 处理器，与现有「submit 处理器才 `POST /orders`」的约束一致（对齐 `CURRENT_STATE.md` §5「单纯粘贴不会建单」）。
- 【尚未验证】未与真实后端联调（原型用内存 mock），见 HANDOFF「未验证项」。
