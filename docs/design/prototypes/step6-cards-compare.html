§1 · 数据来源（哪些是真的）

  • 生产只读实查（2026-09-20）：两台的 account_code、provider_code、总数与在库数 —— legacy-primary / hnskj 总 14、在库 2；backup-a / manual_excel 总 16、在库 7。 备用台库里 provider_code 是 manual_excel，实际卡台是 highvcc，页面按 Lemon 定的叫「备用卡台（highvcc）」。
  • ※ 示例：余额、用量 N/3、尾号、订单号、开卡成本、可销倒计时、token 状态 —— 只示布局与措辞，不是现场值。

§2 · 四个数各自从哪来（不新写判断，硬约束）

  • 可分配：复用 eligibleInventoryCardSql(..., {productCode:'plus'})，即第③④块那份权威资格规则。水位目标＝card_stock_low_threshold。
  • 钱包余额：HNSKJ 读快照表 card_provider_snapshots；highvcc 是实时打外部 API，按 Lemon 定 —— 给「查余额」按钮，不自动查，打开页面不打外网。
  • 底线：目前全项目没有这个设置键，本轮新增（Lemon 定「补一个」）。
  • 今日已开 / 日限：card_stock_jobs 按 provider_account_id 分组（字段本来就有，实查两台都有记录）；日限＝card_replenishment_daily_limit。
  • token：tokenStatus() 只答「配没配过」，答不了有效性。按 Lemon 已定口径 —— 只在有告警时报「已失效」，没告警不写「有效」。
  • 卡状态人话：复用 classifyStockCardOperationalState；待销复用 classifyRetirementRow 的 due / notYetDue。页面一行判断都不自己写。

§3 · 皮肤：为什么是候光

  • D-283 / D-284② 字面写的是「外壳 sidebar 暂留旧皮，四页做完再统一换」，但现场已经换了 —— workbench.css 里有一段不带 .workbench 作用域的全局覆盖，改的是 body / .admin-shell / .sidebar / .nav-item， 来自 7c1a5c0（commit message 自陈「外壳候光已改」）。
  • 所以外壳已是候光皮，工作台也是。卡片页属 D-281 说的「四个一级页实质重做」，用候光才一致；继续用旧皮会是候光外壳套旧皮内容。这一条请 Lemon 过目 —— 它与 D-284② 的字面不符，但符合现场。

  • ⑦ 删补余额区块 / 路线切换搬工作台（已在工作台做完） / 卡片录入降高级
