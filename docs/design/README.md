## 九个阶段（客户可见，与内部阶段一一对应）

已收到订单 → 正在准备支付卡 → 正在排队 → 正在验证账号 → 正在获取支付信息 → 正在提交支付 → 正在等待支付结果 → 正在确认订阅 → **订阅成功**

## 硬规则（违反过，所以写死）

| 规则 | 为什么 |
|---|---|
| **百分比不得提前冲线** | 每阶段有上限，阶段内按 `floor+(ceil-floor)*(1-e^-2.6t)` 逼近但永不到达；只有真正订阅成功才置 100。"进度走完了事情没完"比不动更糟 |
| **不承诺具体秒数** | 只能写「通常几分钟之内完成」。真实一单约 2 分 42 秒且依赖本机执行器在跑。（我违反过一次，写成「一两分钟」被当场抓出） |
| **末步叫「订阅成功」**，不叫充值成功 | Lemon 定 |
| **不向客户展示"自动续费已关闭"** | 卡是运营的，客户不会被二次扣款，写出来只会让他冒出本来没有的疑问 |
| **不用「会话数据」「登录数据」等中文说法** | 听着像在采集客户数据。用 `Session`（英文）与「Token 页面内容」按来源命名 |
| **风控提醒固定文案** | 「订阅已生效，不用再做任何操作。请不要在 ChatGPT 设置里的「升级套餐」中点击升级，这类操作容易触发官方风控。」不得自行补写后果 |
| **出问题时对客户说实话** | 「遇到点问题，我们已经收到通知在处理」。同一时刻运营手机收到确切原因 |

## 设计令牌（取自 refactoring-ui 技能的固定刻度）

- 字号只从 `12 / 14 / 16 / 18 / 20 / 24 / 30 / 36` 选；间距只从 `4 / 8 / 12 / 16 / 24 / 32 / 48` 选
- 颜色写 HSL；灰阶 8–10 档，起点是很深的灰不是纯黑
- **弱化用颜色和字号，不用更细的字重**（不低于 400）
- 晨雾：灰阶 168°，主色 `hsl(163,72%,26%)`，金 `hsl(38,46%,42%)`
- 石板：灰阶 213°，主色 `hsl(162,58%,49%)`，金 `hsl(38,48%,62%)`

## 踩过的坑（别再犯）

- `.ring svg{transform:rotate(-90deg)}` 是**后代**选择器，会把环内对勾的 svg 一并旋转 90°——对勾因此看着是反的。必须写 `.ring>svg`。
- 按段做 CSS 过渡再停住 ≠ 匀速。要连续就得逐帧插值。
- `选择器, @media(...){...}` 是**无效 CSS**，会让其后的样式全部失效。暗色覆盖要单独成条规则。
- 中文系统字体只有离散字重，`font-weight:440` 会被渲染成 400。要提升次要文字的清晰度，**改字号和行高**，不要调字重。
- 卡片顶部一道彩色横条是套路化做法（AI 生成感），已弃用；改为上沿内高光 + 分层投影。
- 教程里的步骤清单与"两个按钮 + 演示动画"内容重复，删掉后弹层才收进一屏。

### 实施中确认的三处与原型不同

1. **不用 Google Fonts**。原型取 Familjen Grotesk 与 IBM Plex Mono，客户在国内那个域名多半加载不出来、还会吊住首屏。改系统字体栈，`--fd`/`--fm` 变量保留，日后自托管只改两行。
2. **没有"到期时间"这一行**。原型屏 5 与屏 7 都显示"到期 2026-10-11"，但 2026-09-12 查证生产库**没有订阅到期时间字段**（`expires_at` 那几列都是内部凭证/许可的过期时间）。按开通时间 +1 个月推算属于给客户一个我们并不掌握的承诺，所以改显示**开通时间**。要恢复这一行，得先有真实数据来源。
3. **多一个"需要换一个账号"状态**。设计的七屏里没有它，但订单被退回等新 Session 是真实分支（F-34/F-35），缺了它被退回的客户会卡死。呈现沿用屏 6 的样子（环停住转琥珀），下方接换号表单。

### 九阶段的数据来源（2026-09-12 对生产库实查后修正）

D-180 当时写的是"阶段来自 `browser_runs` 检查点"。实查后修正为三处：

- `order_events.to_status` → 第 1、2、3 阶段
- `browser_run_events.action` → 第 4、5 阶段（session-bootstrap / page-reset / account-readonly-probe / page-signature / card-material-preflight / checkout-navigation）
- `browser_operations.operation_type` → 第 6、7、8、9 阶段

**不能用 `browser_runs.last_checkpoint_kind`**：它只保留最后一个检查点，2026-09-11 成功单的 `PLUS_ACTIVATED` 被随后的 `CANCELLATION_CONFIRMED` 覆盖掉了，完整轨迹只在 `browser_operations` 里。

### 新增的第七条硬规则

**百分比要钳在阶段上限下方整一个百分点**。曲线在代数上永远到不了上限，但在双精度里会：一个阶段停留超过一小时后 `exp(-2.6t)` 下溢为 0，百分比精确等于上限、坐到下一阶段的地板上；`Math.round(59.5)` 又把半个点抬回去。这条是写测试时抓出来的。

段长（曲线快慢）按真实阶段时长定为 **90 秒**——那次成功单的阶段跨度从 22 秒到 2 分 36 秒，90 秒能让全程都有可见移动。它只用于画曲线，不是承诺，也从不显示。
