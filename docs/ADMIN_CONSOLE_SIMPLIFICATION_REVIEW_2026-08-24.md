# Plus 运营后台臃肿度与模块收敛审查

**日期**：2026-08-24  
**用途**：记录本轮关于运营后台模块合并、删除、保留、增加及承载风险的建议，供其他模型评估。  
**状态**：分析建议，尚未实施 UI、API、数据库或生产部署变更。

## 一、范围与已确认架构

系统由运营后台（中枢）、可切换卡台适配层、API 执行器和独立 Browser 执行器组成。当前本轮只审查运营后台及非 Browser 工作线的后台结构；Browser 仍保持独立工作线和独立导航，不因本审查合并或删除。

当前后台导航（代码观察）：

1. 总览
2. 订单
3. 异常队列
4. 资金证据核对
5. 卡余额充值
6. 卡台路线
7. Browser 执行
8. 卡片库存
9. CDK 管理

## 二、已确认事实（不是推测）

### 1. 卡台路线
卡台可替换，未来存在备用卡台；替换后旧订单仍需保留原路线，新订单使用新路线。因此卡台路线涉及路由、容灾和历史追溯，不是库存的同义功能。

**结论：独立导航必须保留，不与卡片库存合并。**

### 2. Browser
用户已确认 Browser 是单独工作线，并要求独立导航。它未来是更重要的充值执行方式，但当前不应阻塞非 Browser 工作线。

**结论：独立“Browser 执行”导航必须保留。**

### 3. 异常队列
当前前端代码将 `exceptions` 映射为订单列表的 `REVIEW_REQUIRED` 预设筛选：

```js
state.view = view === 'exceptions' ? 'orders' : view;
state.status = view === 'exceptions' ? 'REVIEW_REQUIRED' : status;
```

这说明它目前没有独立的业务数据模型，实质是订单筛选入口。

**结论：可删除独立导航入口；保留订单中的“需要处理/异常”筛选和数据。**

### 4. 资金证据核对
该模块用于处理 Provider、订单、卡片交易之间的证据冲突、结果未知和人工核对，防止重复扣款或错误重试。未知结果不能自动重充或自动退款。

**结论：业务能力必须保留。**

### 5. 卡余额充值
该模块的“充值”是给卡片补余额，不是客户购买 Plus。现有实现包含资金尝试、幂等、`PENDING`、`UNKNOWN`、`MANUAL_REVIEW`、`SETTLED`、`FAILED` 等状态及人工确认分支。

**结论：业务能力必须保留；可与资金证据核对归入同一“资金与对账”导航，但不能删除底层状态、审计和安全开关。**

### 6. 库存页面
当前同时展示库存状态、卡台 active 数、账户余额/额度、阈值、自动补卡、人工开卡、新卡接管、同步、卡片明细及历史交易等内容。核心能力大多有业务用途，但首屏内容偏多。

已发现的明确重复：`卡台 active 卡` 与 `卡台当前 active 卡数` 当前都使用 `providerActive`，应只保留一个展示字段（底层数据是否删除需另行核查，不能直接删字段）。

## 三、建议的导航收敛方案（待用户确认后实施）

```text
总览
订单
资金与对账
卡台路线
卡片库存
CDK 管理
Browser 执行
```

### 合并/改名

- “资金证据核对”与“卡余额充值”归入“资金与对账”父导航，作为两个页签或子页面；保留原功能和权限边界。
- “异常队列”不再单独占用顶层导航，改为“订单 → 需要处理（REVIEW_REQUIRED）”。
- “卡片库存”不删除能力，内部改为分区/页签：库存概览、开卡与新卡接管、卡片明细、补卡任务。

### 明确保留

- 卡台路线：独立保留。
- Browser 执行：独立保留。
- CDK 管理、订单、库存、资金未知/对账处理：保留。

## 四、总览首屏建议

### 首屏保留（直接影响运营决策）

- 接单开关、派发开关；
- Provider/卡台写入开关及当前卡台；
- 处理中订单；
- 等待 Session；
- 等待补卡；
- 资金未知；
- 对账案件；
- 可分配库存；
- 卡台健康；
- Worker 健康。

### 建议移出首屏（不删除底层能力）

- 退款观察；
- 泛化的“内部提醒”；
- 低频或重复统计；
- 最近订单中的非关键扩展列；
- 成功率等统计指标（移到统计/订单筛选区域）。

原因是减少首屏查询与认知负担，而不是因为这些数据“错误”或“无价值”。当前没有足够的长期压测证据，不能断言系统一定承载不了 200–300 单/天；应先减少首屏并测接口、数据库和页面加载性能，再决定是否进一步裁剪。

## 五、卡片库存页面建议

1. 概览只显示可分配、已分配、耗尽、隔离、核对中等运营状态，以及统一后的 active 数。
2. 开卡、接管、同步、补卡任务放到独立页签，避免进入库存页即加载全部任务和历史。
3. 卡片列表默认只显示后四位；用户已确认订单详情需要完整卡号，因此完整卡号仅在受控详情页展示，并记录审计。
4. 交易/分配历史改为点击后延迟加载，避免首屏大批量查询。
5. 任何“合并展示”不等于删除数据库字段或 API；先查调用方和迁移依赖。

## 六、真正必要的新增内容（先核对现有能力，避免重复建设）

只有以下三类可视化能力具有明确必要性：

1. **系统状态条**：接单、派发、Provider 写入、卡台写入、当前卡台。
2. **订单详情统一追溯摘要**：CDK、邮箱、Session 更换次数、卡片、Provider、充值金额、开卡/补余额金额、最终状态、自动续费取消状态。
3. **风险入口**：资金未知、对账案件、等待补卡、等待 Session。

实施前必须先核查现有页面/API 是否已经提供，不能因为“规划中”就重复新建。

暂不建议新增独立操作审计中心、独立财务中心、独立退款中心、更多统计中心、泛化通知模块或新的 Provider 管理层；这些会增加接口和运维面，当前没有证明其必要性的事实证据。

## 七、承载与稳定性判断边界

- **已知**：当前后台已有较多指标和接口；部分指标来自不同同步/任务状态。
- **未知**：没有完整的 200–300 单/天长期压测、数据库慢查询基线、首屏接口瀑布和错误率趋势，因此不能仅凭页面数量断言“接口承接不了”或“数据必然不稳定”。
- **建议验证顺序**：先记录首屏接口列表、响应时间、SQL/索引和失败率；再做页面分区与按需加载；最后用接近目标量的压测和故障演练决定是否继续删减。

## 八、禁止直接执行的变更

在用户确认模块结构前，不得：

- 删除后端接口、数据库表或字段；
- 删除资金安全状态、幂等逻辑、卡片追溯；
- 合并卡台路线与库存；
- 隐藏或移除 Browser 导航；
- 直接大改后台或部署生产。

## 九、下一步（本文件记录的建议，不代表已批准）

1. 用户/其他模型先评估本方案；
2. 确认顶层导航和总览首屏字段；
3. 对每个拟合并/移出的页面做 API、数据库、权限依赖盘点；
4. 小范围 UI 原型/改动；
5. 单元、集成、浏览器交叉验证；
6. 通过对抗式审查后，才考虑生产部署。

## 十、对本文件的对抗式审查（2026-08-24）

### 已复核、可由当前代码支持的内容

- `异常队列` 当前确实通过 `REVIEW_REQUIRED` 复用订单列表，而非独立订单数据源。
- `待验证新卡`、`本地可分配卡`、卡台账户余额等字段确实出现在总览/库存相关 UI。
- `卡台 active 卡` 与 `卡台当前 active 卡数` 当前都渲染 `providerActive`，属于展示重复。
- 卡台路线已有独立后台视图和人工切换决策；本轮建议没有改变“只影响新订单、旧订单保留原路线”的规则。
- 卡余额充值和资金证据核对的底层状态及资金安全逻辑不能因 UI 合并而删除。

### 本轮方案不能声称已经证明的内容

- 尚未完成每个页面的 API/数据库/权限依赖清单，因此不能声称“删除某导航一定无副作用”。
- 尚未完成 200–300 单/天的长期压测，因此不能声称当前接口或数据库一定无法承载。
- 尚未完成生产 Browser 付款验证，因此本文件不对 Browser 的实际付款成功率、页面稳定性或费用结果做结论。
- 本文件未核定每一个总览指标的最终保留/移除清单；“建议移出首屏”仍需结合运营使用频率和接口成本确认。

### 发现的遗漏与修正

1. **待验证新卡不能被误删**：它是手动开卡接管/隔离流程的入口，虽然不一定要放总览首屏，但必须保留在“卡片库存 → 开卡与新卡接管”中。
2. **资金风险不能简单等同于资金未知**：两者可能对应不同状态和处理动作；UI 可以统一入口，但字段、状态和审计语义必须保持区分。
3. **卡台账户余额与卡片余额必须继续分开**：总览已有“不是可分配卡片余额”的语义提示，重构时不能把两者合并成一个库存数字。
4. **CDK 可追溯字段不能因精简而丢失**：CDK、订单、卡片、邮箱、时间、金额、Provider 订单/交易和最终状态仍是用户确认的追溯链核心。
5. **“内部提醒”不能未经核对直接删除**：它当前是一个展示区，是否低价值要逐项检查其内容来源；可先改为明确的风险/待处理列表，而不是直接删掉底层提醒数据。

### 审查结论

本文件的方向性建议基本准确，但它是“结构收敛方案”，不是完整的后台正确性验收，也不是删除清单。下一步必须先做逐模块依赖和运行时数据核对，再由用户确认最终 UI 变化；任何未核实项均不得当作既定事实。
