# 最终需求对抗式审查（2026-08-21）

> 审查对象：当前决策账本、需求对齐稿、V1 规格、路线图、代码实现、历史 Provider PoC 与 2026-08-21 最新用户确认。
>
> 本文是审查报告。2026-08-21 用户已确认审查修正方向，并补充“卡片默认不跨订单复用，但特殊情况保留受控人工口子”。正式结果见 `FINAL_REQUIREMENTS_BASELINE_2026-08-21.md` 和 `DECISIONS.md`。

## 一、结论

当前方向总体正确，但还不能称为无冲突的“最终版”。审查确认了 8 个文档或实现冲突、5 个需要补全的业务边界。最严重的不是页面细节，而是：

1. 旧决策仍把手动开卡、逐单充值确认和退款提醒写成正式结论，与最新确认直接冲突；
2. 正式规格仍按“每单新开卡”设计，没有以“库存优先、阈值自动补卡”为主流程；
3. “充值成功”与“取消自动续费成功”的终态定义不一致；
4. Session 可更换，但现有客户状态和接口没有可恢复状态；
5. “未充值卡”术语存在逻辑错误：新开卡的初始入金本身就是 CARD_RECHARGE，不能用“无充值交易”判断库存卡未使用；
6. HNSKJ 既有卡充值接口真实存在且文档完整，但 v1 尚未实现。

## 二、已证实的文档冲突

### F-01：自动补卡与旧决策冲突（确定）

- 最新确认：人工补卡与自动补卡并存；自动补卡暂定每次 1 张、每张 $16、每天最多 5 张。
- D-006 仍写“手动开卡是默认主流程”。
- D-008 仍写“自动开卡本轮不继续扩展”。
- 路线图也未把自动补卡接通列为近期正式任务。

结论：D-006、D-008 已被后来确认的需求部分取代，必须标记“已被后续决策替代”，不能与新结论同时保持“已确认且有效”。

### F-02：自动履约与逐单 Permit 冲突（确定）

- 最新确认：生成 CDK 代表已付款；客户兑换后自动履约，不要求运营者逐单点击。
- D-009、V1_SPEC §14 和当前后台仍要求逐单 Permit。
- 当前代码仍存在 recharge_authorizations、recharge permit 按钮和“待确认充值”。

结论：当前运行实现不是目标自动化模式。应保留“单订单唯一资金尝试栅栏、全局急停、未知结果锁定”，但人工 Permit 不能继续作为每单正常前置条件。资金栅栏与人工审批是两件事。

### F-03：退款方向互相冲突（确定）

- 最新确认：退款极少，人工处理；不做自动退款识别和提醒，只预埋可追溯点。
- D-016 仍写“退款仅识别提醒”。
- V1_SPEC §10、§14 仍要求自动观察、疑似退款识别和 Bark 提醒。
- 当前代码/数据表已存在退款观察和候选识别基础。

结论：保留交易原始同步和人工案件记录是合理的；自动判断“疑似退款”和退款 Bark 提醒应停用/不纳入当前需求。D-016 已失效。

### F-04：Provider 状态描述过期（确定）

- D-018 写“新卡台和充值供应商尚未确定”。
- 当前实际主路线已经是 HNSKJ 卡台 + ZZSHU 直充，并有真实 PoC 和生产调用证据。
- 未来备用卡台尚未确定。

结论：应改为“当前主 Provider 已确定；备用/替代 Provider 尚未确定”。

### F-05：正式主流程仍是每单开新卡（确定）

V1_SPEC §1、§7 仍描述：

```text
订单创建 → worker 每单开新卡 → 等卡 active → 直充
```

最新确认的目标流程是：

```text
订单创建 → 优先分配合格库存卡
         → 库存不足则等待补卡 + 通知
         → 阈值触发自动补 1 张（受每日 5 张上限）
         → 人工补卡仍可并存
```

结论：正式规格已经落后于当前需求，且会误导接手模型继续优化错误主流程。

### F-06：成功终态与取消续费规则冲突（确定）

- 用户明确：完整链路最终必须确认取消自动续费。
- V1_SPEC §7 写“取消续费状态异步补查，不阻塞充值成功”。
- 当前状态机在 Provider 返回 success 后即可进入 RECHARGE_SUCCESS。

第一性原理：充值已经成功但取消状态未知时，不能把订单判失败，也不能再次充值；但也不应向客户宣称整套履约最终完成。

建议状态：

```text
RECHARGE_PROCESSING
→ RECHARGE_PAID / CANCELLATION_PENDING
→ RECHARGE_SUCCESS（仅 is_subscription_cancelled=1）
→ CANCELLATION_REVIEW_REQUIRED（超过期限仍无法确认）
```

对外在取消确认前显示 PROCESSING 或 REVIEWING，不能显示 FAILED，也不能重付。

### F-07：Session 更换与现有客户状态机冲突（确定）

- 最新确认：原订单最多更换 Session 3 次。
- 当前客户 API 只暴露 QUEUED / PROCESSING / REVIEWING / SUCCESS / FAILED。
- 当前无客户更换 Session 接口；FAILED 在前端属于终态并停止轮询。
- Provider 40030 当前落入 RECHARGE_FAILED。

结论：账号已是 Plus、Session 失效等客户可修复问题，不应进入不可恢复的普通 FAILED。需要明确“等待客户更换 Session”的可恢复状态、剩余次数、窗口截止时间和提交接口。

### F-08：D-024 的表述不够准确（确定）

D-024 写“新卡开通、符合规则账号成功充值仍未验证”，容易被理解为从未成功开过新卡。

真实证据：

- 2026-08-18 独立 Provider PoC 已成功开出 $16 新卡、完成 ZZSHU Plus 充值并确认取消续费；
- 尚未验证的是“正式 CDK → MySQL 订单 → Worker → 新卡/库存 → 成功 → 取消续费”的生产订单闭环。

结论：必须区分“独立 Provider PoC 已成功”和“正式系统成功订单未验收”。

## 三、卡片余额充值接口审查

### 已核实事实

2026-08-21 直接读取 HNSKJ 当前官方文档 `https://card.hnskj.vip/docs/open-api.md`，确认：

- `POST /cards/{id}/recharge`；
- 需要 write scope；
- 必须携带 16–128 字符的 `X-Idempotency-Key`；
- 仅 active 卡可用；
- amount 必须是正整数 USD，且不低于卡的 minRechargeAmount；
- 从卡台账户扣除 amount + 手续费；
- 未确认结果可能返回 `success:false, pending:true`；
- pending 时只能查询卡余额/流水，禁止更换幂等键再充值。

当前 v1 `HnskjCardProvider` 没有该方法，脚本没有调用路径。

### 第一性原理结论

“接口存在就用”是正确方向，但不能对每张新卡无条件再调用一次：

- `POST /cards/purchase` 的 openCardAmount 已经向新卡注入余额；
- 再无条件调用 recharge 会重复加余额、增加手续费和资金占用；
- 在“一卡一单”原则下，已经用于客户付款的卡不能因为余额不足重新补钱并分配给另一订单；
- 合理用途是：一张 active、未绑定订单、从未产生客户消费的库存卡，当前余额低于本订单最低要求时，按差额和 minRechargeAmount 补足；
- recharge 也必须有独立持久化幂等键、资金尝试记录、pending 未知状态和人工对账路径。

因此正确流程不是“永远充值”或“永远不充值”，而是：

```text
新开卡时直接设置足够 openCardAmount
已有未使用库存卡余额不足时才调用 /cards/{id}/recharge
已消费/已绑定卡禁止为新订单补余额复用
```

## 四、“未充值卡”定义存在逻辑错误

最新口头规则使用了“active 且没有充值过”。

但 HNSKJ 的真实交易中，新卡初始入金本身就显示为 `CARD_RECHARGE`。2026-08-18 成功 PoC 的新卡就有一笔 $16 CARD_RECHARGE。

因此不能用“没有 CARD_RECHARGE 交易”判断卡是否可分配，否则所有正常新卡都会被排除。

建议将术语改成：

> 未履约卡 / 未消费库存卡：active、未绑定任何订单、没有客户支付 PURCHASE 证据、资料完整、余额满足门槛，且不存在资金未知或退款争议。

这项是逻辑纠错，不是新增业务偏好。

## 五、仍未闭合的业务边界

### Q-01：72 小时从何时开始

当前文档只写“更换窗口 72 小时”，没有冻结起点。

用户原话方向更接近“第一次 Session 被明确判定无效后给两三天”。从客户体验和库存等待角度，合理起点是：

> 从第一次出现可由客户修复的 Session/账号错误时开始，而不是从 CDK 生成、兑换或订单创建时开始。

否则库存不足或 Provider 排队会无故消耗客户更换时间。该起点仍应由用户最终确认后写入正式决策。

### Q-02：更换 Session 是否允许换账号

用户举例是当前账号已为 Plus时换一个账号，因此事实上需要允许 chatgpt_account_id 改变。实现必须保存账号变更审计、旧账号标识和次数，但不应长期保存旧 Session 明文。

### Q-03：CDK“生成即付款”与批量预生成

如果所有 CDK 都只在客户付款后生成，逻辑成立；如果运营者提前批量生成库存码，“生成即付款”就不成立。

建议区分：

- GENERATED：已生成但尚未登记交付；
- ISSUED：已发给已付款客户，可兑换；
- REDEEMED / REVOKED。

如果业务坚持生成后立即可兑换，也必须至少保存批次、交付/补发记录和操作人，承认 CDK 是无记名付款凭证。

### Q-04：自动补卡 5 张与 200–300 单/日

每天自动最多 5 张适合作为当前灰度保护，但在一卡一单下无法支撑 200–300 单/日。

这不是当前参数错误，而是缺少明确升级门槛。路线图至少应说明何时从 5 张调整到按销量预测补货，以及卡台账户余额、开卡限额、API 60 次/分钟和失败率的容量验收。

### Q-05：库存不足与 Session 生命周期

订单等待补卡期间 Session 可能自然过期。库存等待不应消耗“客户更换 Session 3 次”；只有客户主动提交新 Session 才计一次，系统因库存/Provider 原因重试不得计数。

## 六、建议的最终主链路

```text
后台生成并交付 CDK（代表外部已付款）
→ 客户兑换 CDK + 提交 Session
→ 本地结构/有效期检查
→ 优先分配合格未履约库存卡
   ├─ 库存不足：WAITING_FOR_CARD + 后台/Bark 通知
   └─ 阈值触发受限自动补卡；人工补卡并存
→ 必要时仅为“未履约但余额不足”的 active 卡幂等补余额
→ 建立单订单资金尝试栅栏（不是逐单人工审批）
→ ZZSHU create_direct
   ├─ Session 无效/账号已 Plus：WAITING_FOR_SESSION，可原订单更换，最多 3 次
   ├─ 明确失败：按客户原因/内部原因分层
   ├─ 结果未知：冻结，人工对账，禁止 API/Browser 重付
   └─ 创建成功：持续查询
→ Provider 支付成功
→ 等待并确认 is_subscription_cancelled=1
→ 最终 SUCCESS
→ 保留订单、CDK、卡片、Provider 调用、交易和人工案件追溯
```
