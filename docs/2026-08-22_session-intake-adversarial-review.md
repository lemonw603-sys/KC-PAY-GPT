# Session 本地接入方案对抗式审查（2026-08-22）

## 结论

采用“仓库外本地文件 + 一次性整理/校验脚本 + 临时 BrowserContext 内存注入”作为测试输入方案。它是当前简单性、敏感数据暴露面和现有 Browser Loader 改动量之间的最佳折中，但必须避免生成第二份长期保存的规范化 Session 文件。

## 候选方案比较

| 方案 | 操作便利 | 暴露面 | 主要问题 | 结论 |
|---|---:|---:|---|---|
| 直接粘贴聊天 | 高 | 很高 | 聊天记录/附件承载真实 Token，无法可靠清理 | 否决 |
| 加密后粘贴 | 中 | 中 | 解密密钥仍需传递；密文无法脱离密钥被执行 | 否决 |
| 仓库内 Session 文件 | 高 | 高 | 容易误提交、被测试日志或备份收集 | 否决 |
| 仓库外 `0600` 文件 + 本地脚本 | 高 | 低 | 仍需严格禁止日志输出和路径误用 | 采用 |
| 系统钥匙串/外部 Secret Manager | 低 | 最低 | 测试阶段部署成本和跨模型接班成本过高 | 后续可选 |

## 必须收紧的边界

1. 输入文件必须位于仓库外，并检查 POSIX 权限；脚本拒绝宽权限文件。
2. 脚本只读取首个 JSON 文档，拒绝警告文本和尾随内容，不修改原文件。
3. `sessionCookieName` 必须由用户按真实来源显式指定，禁止从 Token 猜测 `authjs`/`next-auth`。
4. 规范化对象只在进程内存中生成；若需要落盘，仅生成短期 `0600` 临时文件并在结束时清理，默认不落盘。
5. 日志只输出字段存在性、长度、哈希摘要、有效期和 Cookie 家族，不输出 Token、Cookie、邮箱或 URL。
6. 整理器只服务于 `AUTH_READ_ONLY` 测试，不创建 Checkout、不填写卡片、不付款，也不改变订单/资金状态。
7. 失效、过期、家族不明或解析异常均停止，不自动刷新、换 Session、换卡或换执行器。

## 未解决事实

- 当前附件第一行字段齐全，但缺少 `sessionCookieName`；不能据此判断账号是否已过期或仍可登录。
- 非菲律宾基线不能证明菲律宾出口下的风控或容量表现。
- 真实 BrowserContext 观察仍需用户当次确认，且只允许身份/页面/Checkout 只读证据。

## 验收

- 先通过纯本地结构校验，再由用户确认进入临时 BrowserContext。
- 观察结束后必须做 cohort 级对抗式审查；未通过不得进入付款或规模化。
