# AI充值业务｜项目规划地图

> **唯一用途**：回答“整个项目做到哪、当前在做什么、下一步是什么”。  
> **最后核对**：2026-08-31 11:20 CST；已对照前端、后端、main、生产 release、MySQL、systemd 与日志。代码以 `main` 为准，生产事实以 `docs/CURRENT_STATE.md` 为准。
> 历史计划、研究报告和旧候选记录只能作为证据，不能覆盖本地图的当前顺序。

> **当前最高优先级事实**：生产已部署本轮前后端/配置收敛修复，并按用户确认长期打开 API Worker 的最小真实充值权限。当前默认 API、接单、自动派发和 Worker 最终充值能力已经对齐；通用 Provider 写、卡片写和 Browser 付款仍关闭。下一优先级是用首笔真实低余额订单验收“精确补余额后原订单自动继续”，而不是继续增加控制面。

## 1. 项目最终目标

建立一套自用的 ChatGPT Plus 充值运营系统：客户提交 CDK 和 Session 后，系统自动选择充值路线、准备卡片和余额、完成充值、取消续费、同步资金证据并提供异常处理；在资金安全优先的前提下，尽量减少人工操作和按次收费的 Provider API 调用。

目标运行形态：

1. **Plus 运营后台是中枢大脑**：订单、CDK、Session、卡片、资金、审计、通知和路线选择都在这里统一管理。
2. **两条执行路线共用同一业务核心**：API 当前可用；Browser 是未来重点。两者共用订单、卡片、消费次数、资金栅栏和审计，不建设两套账。
3. **默认充值方式全局切换**：选择 API 或 Browser 后只影响新订单，不要求逐单选择；既有订单按创建时冻结的路线继续。
4. **自动补给**：订单缺资源时，优先给合格低余额卡精确补足；没有合格卡才自动开一张带目标余额的新卡。
5. **可放量但不过度设计**：先用真实订单证明稳定，再从 3–5 单、10–20 单逐步扩到 100–300 单/日。

## 2. 不变边界

- 当前产品只做 ChatGPT Plus；Pro 5X/20X 后置。
- 资金结果未知时不重付、不换卡、不换路线，先核对。
- 一张卡同一时刻只服务一个活动订单；订单完成后，可在全局可配置的 1–4 次成功上限内服务下一单；当前生产值已核对为 3 次。
- 运营覆盖不会被 Provider 同步结果覆盖：`4744` 仅用于 Claude；当前旧失效批次（含 `8590`）永久停用；未来新卡按实时证据接管。
- 这是个人内部系统：稳定、顺畅、资金安全高于复杂的敏感信息隔离。
- 不删除真实订单、交易、资金、退款和审计证据；后台简化以隐藏/下沉噪音为主。
- 普通发布不会隐式打开 Browser 真实付款；真实 Browser 首单仍需单独确认。

## 3. 总体架构地图

```text
客户：CDK + Session
        │
        ▼
订单核心：校验 → 冻结默认路线 → 任务/租约 → 状态机
        │
        ├── 资源准备：卡片资格 → 消费次数预留 → 低余额精确补足 / 无卡自动开卡
        │
        ├── API 执行器（当前默认路线；生产常驻最小真实充值权限已开启）
        │
        └── Browser Worker（未来主路线，当前真实付款关闭）
        │
        ▼
结果闭环：Plus 确认 → 取消续费 → Provider 交易/余额 → 对账/UNKNOWN 锁定
        │
        ▼
运营后台：营业控制、默认路线、订单、卡片、CDK、资金证据、异常和 Bark 通知
```

## 5. 当前主项目｜运营控制面收敛与自动补给

这不是另一个项目，而是整个 AI充值业务当前的运营化阶段。

### 已完成

- 后台第一版控制面已收敛：保留日常营业入口、默认充值方式和就绪摘要，把底层开关降为高级控制。
- 就绪检查已区分：系统自动恢复、可直接跳转、需要明确确认、必须人工核对。
- 卡片跨订单复用和全局 1–4 次上限已部署。
- 自动补余额改为订单驱动，删除“空闲时扫描并预充全部低余额卡”的旧设计。
- 自动补余额生产 gate、数据库能力开关和 timer 已开启；无订单时已经证明零 Provider 充值调用。
- 前后端与生产权限已对齐：默认 API 的最小真实充值权限已开启，后台和只读体检会按 Worker 真实能力放行或阻断。

### 尚未完成

1. **首笔真实自动补余额验收**：验证低余额卡精确补差额与原订单自动继续。
2. **控制面真实运营复核**：用下一批订单验证“客户提交后系统能否自动处理；不能处理时是否给出正确说明/入口”，不继续凭想象增加卡片和开关。
3. **连续运营验收**：自动补给首单通过后，立即进入 3–5 单连续真实 API 订单。

### 本阶段退出条件

- 有低余额卡时只补精确差额，Provider 写调用唯一且幂等；到账后卡恢复并让原订单继续。
- 没有合格卡时只开一张目标余额卡，不因轮询重复开卡。
- 失败可继续时系统自动重试；真正无法继续或资金未知时才停下，并给出明确入口/核对信息。
- 日常充值不再要求人工逐个打开底层开关；管理员只需保持营业状态和默认路线。
- 3–5 单连续订单没有重复扣款、卡片错分、资金差异或骚扰式错误提醒。

## 6. 从现在开始的唯一执行顺序

### P0｜前后端与生产配置收敛（已完成）

- 已部署本轮修复：后台和应用只读 readiness 会识别 API Worker 真实充值权限，不能再出现“开始营业成功但订单无法最终提交”。`pojia-ops check` 继续只负责服务/备份完整性，不冒充业务 readiness。
- 自动开卡 timer 无真实需求时只查本地数据库，不再每 60 秒刷新卡台规则/余额；有真实需求且规则过期时才刷新一次。
- 取消订单后关闭“等待卡片”提醒；余额变化继续发 Bark/留审计，但不再占用后台“内部提醒”；自动补给开启时不再发送需要人工处理的低库存提醒。
- 已按用户确认只开放 `PROVIDER_RECHARGE_WRITES_ENABLED=true`；卡台开卡写、通用 Provider 写和 Browser 付款继续保持关闭。migration 044、v20 后台资源和 60 秒 timer 描述均已部署。

### P1｜自动补余额首笔真实验收（现在）

- 等待真实订单遇到一张符合运营规则的低余额卡。
- 记录卡、补前余额、订单目标金额、精确补款、幂等键、Provider 调用次数、到账/交易证据、库存恢复和订单继续时间。
- 出现 UNKNOWN 时停止自动重补，只进入核对。

### P2｜3–5 单连续 API 运营验证

- 保持接单、派发、自动开卡和自动补余额按当前生产设置运行。
- 验证卡片 1–4 次容量、补卡/补钱、15 分钟按需同步、Plus 成功、取消续费、Bark 和对账。
- 只修真实链路暴露的问题；不新增推测性模块。

### B｜Browser 并行线（不阻塞 P0/P1）

- 以当前 `main` 和当前生产合同重新跑生产形态非付款闭环，包含新的跨订单容量和自动补给。
- 非付款闭环通过后，提交一笔真实 Browser 付款的独立确认请求。
- 真实首单通过后，再讨论把全局默认路线从 API 切到 Browser；不逐订单选择。

### P3｜运营后台二次收敛

- 根据 P0/P1 的真实操作记录修正入口、跳转、重复信息和错误提醒。
- 必要数据保留在详情/审计，首页只展示“能否营业、正在处理什么、哪里必须处理”。
- 不为没有发生的故障增加新卡片、新状态或新服务。

### P4｜小规模放量与运营保障

- 10–20 单受控并发；检查重复付款、资金差异、卡片容量、延迟和 API 调用数。
- 完成费用视图/价格变化通知、异地备份与恢复演练。
- 达标后再进入 100–300 单/日；未达标就回到最早失败环节修正。

## 7. 当前明确不做

- 不给每笔订单增加人工路线选择。
- 不恢复空闲全库存预充值或高频全量 Provider 扫描。
- 不把超过 15 分钟本身当成失败；有订单时按需刷新证据并继续。
- 不建设复杂微服务、策略中心或第二套 Browser 订单/资金账。
- 不物理删除历史订单、卡片、交易和审计证据。
- 不在 Browser 首单前承诺其已经可以生产真实付款。

## 8. 地图维护规则

只有下列事件发生时更新本地图，不为每次小修追加流水账：

1. 用户确认新的业务方向或推翻旧决策；
2. 一个板块从“代码完成”变为“已部署”，或从“已部署”变为“真实验收”；
3. 生产真实事实变化（release、开关、服务、迁移、重大风险）；
4. 当前唯一下一步或优先顺序变化。

更新动作必须一次完成：

- 本地图：更新总体进度、当前阶段和唯一执行顺序；
- `CURRENT_STATE.md`：更新生产事实；
- `DECISIONS.md`：仅记录为什么改变；
- `HANDOFF_LOG.md`：记录执行证据与历史；
- `ROADMAP.md`：只保留详细历史清单，不再单独决定下一步。
