# 两笔真实订单全链路复查｜2026-08-31

## 审查范围

以两笔真实 API 订单为事实样本：

- 第一笔：客户页/CDK/Session/分卡/Provider 调用，因账号已是 Plus 收到 `40030`，正确进入失败终态，未确认扣款。
- 第二笔：CDK/Session/分卡/Permit/API 创建/状态轮询/Plus 开通/取消续费，最终 `RECHARGE_SUCCESS`，卡台消费余额也得到独立证据。

本次不把 Browser 当成已完成事实；Browser 当前仍是独立、未付款路线。

## 已确认做对的地方

1. CDK 只能消费一次，订单与 Session 绑定；Session 替换有边界。
2. Provider 明确拒绝（40030）与提交结果未知分开处理，不会因未知自动换卡或重付。
3. 第二单 `create_direct` 只出现一次；成功后取消续费也有独立确认。
4. 卡余额扣减与 Provider 订单金额有独立核对；交易未结算时不重付。
5. 卡片资料、余额、交易同步均为只读；同步任务有去重、租约、分页校验。
6. API 与 Browser 路由、资金栅栏和 Browser Worker 心跳已解耦；Browser 付款仍关闭。

## 发现的主要问题（按优先级）

### P0：后台开关显示与实际可执行能力可能不一致

生产 readiness 可以显示“接单/派发开启”，但 Provider 写入仍关闭。运营人员容易误以为客户提交后会自动完成充值，实际订单会停在配置阻断。必须在总览明确区分：

- 接收订单；
- 自动派发；
- API 写入；
- Browser 执行器在线。

### P0：订单驱动补给与执行定时器存在断点

代码可以为订单创建补余额任务，但生产 `pojia-card-funding.timer` 当前 inactive。若没有专用执行进程，任务只会排队而不执行。必须在启用订单驱动补余额前证明：任务有执行者、写权限范围正确、失败会进入 UNKNOWN/人工核对。

### P1：卡片“资料同步”和“交易同步”的时间门槛仍容易误解

真实订单已证明：详情刷新成功不等于交易证据新鲜。卡 `1013` 在详情同步后仍被阻断，补做交易同步后才变为 READY。后台已改按钮文案，但总览仍应直接展示两个时间和阻断原因，不应只显示一个“同步成功”。

### P1：供应商账户余额不足与卡余额不足没有统一运营提示

卡 `1013` 自身余额足够，但卡台账户约 `$19.72` 低于供应商 `$25` 最低账户余额。前者影响现有卡分配，后者影响新开卡；后台必须分开显示，避免把“不能开新卡”误报为“没有可用卡”。

### P1：自动补卡规则已写入，但生产边界需要再验收

自动补卡按订单需求和每日上限运行，方向正确；但当前账户余额不足时，必须明确进入“无法购买新卡”的可解释状态，不得高频重试或反复 Bark 告警。

### P1：完整集成测试入口仍有环境边界问题

v1 全量测试会加载 Browser 测试文件，而 v1 独立 release 不包含 Playwright，造成环境性失败。应拆分 `v1` 与 `browser-mvp` 测试入口，避免把依赖问题误判为业务失败。

### P2：成功订单的卡台交易最终结算仍可能滞后

第二单 Provider/Plus/取消续费均成功，但卡台 PURCHASE 曾处于 `PROCESSING/UNSETTLED`。当前“不重付”是正确的；应继续只读补证，并在后台显示“充值成功、卡台交易待结算”，不要显示为三方完全一致。

## 从运营视角必须优化的功能

1. 总览增加“当前真正能否完成充值”的单一结论卡片，列出阻断项，而不是让运营人员自行拼接多个开关。
2. “完整只读同步”统一入口，完成后同时刷新详情、余额、交易，并显示各自时间。
3. 订单详情只保留影响决策的字段：订单状态、Session 状态、充值路线、卡尾号/余额、交易证据、下一动作；其余审计字段折叠。
4. 订单等待资源时只提醒一次并显示原因；无订单不发送“库存不足”骚扰提醒。
5. 任何“可自动执行”状态必须同时检查对应 Worker、写开关和供应商账户余额。

## 当前结论

- API 成功链路已有两笔真实证据，失败分支也已验证；资金未知处理正确。
- 系统尚未达到“客户提交后无条件自动完成”的状态：Provider 写入关闭、卡台账户余额不足、补余额 timer 未启用，都会阻断自动执行。
- 当前最优顺序不是再增加业务模块，而是先修正 P0/P1 的运营可见性和执行断点，再决定是否开启下一笔真实充值。
