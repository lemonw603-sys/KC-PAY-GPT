### 关键设计分界：两类操作，只有一类能远程

今天（2026-09-12）恰好把两类都碰到了，这个分界必须先定，否则做出来一半用不上：

| 类别 | 例子 | 能否远程 |
| --- | --- | --- |
| **纯决策类**——人只是给个判断，动作由系统执行 | 「确认核实结果 / 未付款」「取消订单并释放」「打开或关闭付款开关」 | **可以**，正是本需求的目标 |
| **必须在浏览器前动手** | 人机验证勾选「I am human」（D-153/D-154 定死不绕过、不自动完成） | **不能**。机器人只能通知，人还是得到电脑前点 |

所以机器人能解决的是「决策要人但动作不用人」的那一半。人机验证那一半无解——除非远程桌面，
那是另一件事。

### 做之前要想清楚的（按业务流程检验，不是技术清单）

1. **决策依赖的信息也得一起送到手机上**。「确认未付款」的前提是先去卡台看那张卡真实余额
   （库里余额对 MANUAL_IMPORT 卡是快照，不是权威）。按钮远程了、核实还得开电脑，等于没解决。
   要么把卡台余额查询一并接进来，要么这个按钮就不该远程化。
2. **资金动作的确认强度**。现有后台这些操作都带确认语（如 `确认核实结果 <run>`）。聊天窗口里
   点一下比在后台点一下轻得多，误触代价却一样，需要二次确认或短时效。
3. **幂等**。消息可能重复点、网络可能重投；每个动作要有幂等键，重复提交不得产生第二次效果。
4. **鉴权**。机器人能触发生产写操作，必须确认发起人身份，不能只凭群里谁发了消息。
5. **审计**。现有后台操作都落 `order_events` / 审计表并记 actorId；远程通道要落到同一套里，
   不能出现「不知道是谁点的」。

## 报错单的自动处置（2026-09-12 定，Lemon：「出问题也尽量自动化处理」「客户有报错单要怎么快速便捷解决，这个我非常关心」）

### 现状盘点：五单真实失败，四单已全自动

2026-09-12 连跑五单全部失败，正好覆盖了各类情况：

| 失败类型 | 处置 | 要人吗 |
| --- | --- | --- |
| 窗口里是上个客户的登录态 / `PAGE_DRIFT` / Session 刷新链断 / 找不到唯一升级按钮 | 付款前安全中止 → **自动**释放卡与账号槽、卡密退回 `AVAILABLE`、客户页显示「可以直接重新兑换」 | **不要**（D-188） |
| **付款结果不明**（`SUBMIT_UNKNOWN`）| 锁死卡与卡密防重复扣款 → 升级人工核实 | **要**，且今天是唯一一个 |
| 人机验证弹窗 | 只能人点（D-153/D-154 定死不绕过）| **要**，且无解 |

**所以「报错单要人处置」现在只剩两类**：付款结果不明、人机验证。后者是业务约束，前者可以自动化——下面两步就是干这个。

### 为什么付款结果不明现在必须要人

`browser-card-transaction-reader.js:68-71`：对 `MANUAL_IMPORT` 卡（我们现在用的每一张 highvcc 卡）
**不去读卡台，直接返回占位标记 `MANUAL_CARD_BROWSER_CONFIRMED`**。于是验证 lane 拿不到
「卡有没有被扣」的客观证据，只能升级人工。

**不是设计上要人做，是证据源没接。** 验证服务本身早就支持自动落定
（`browser-payment-verification-service.js`：`CONFIRMED` / `DECLINED` 自动收口，
只有 `CONFLICT` 或超期才升级人工），只是我们的卡喂给它的是假数据。

highvcc 的交易接口是存在的，摸前端包时撞见过：`/api/cardTrade/authTrans/page`、
`/api/cardTrade/authTrans/pageForSub`、`/api/cardTrade/authTransDown`。
`v1/src/providers/highvcc-card.js` 只实现了 `list/detail/wallet/cost/ranges`，缺 `transactions`。

### 第一步（低风险，先做）：接通交易接口 + 手动核实工具

- 给 highvcc provider 加 `transactions()`，走 `/api/cardTrade/authTrans/page`（接口合同先摸清）
- 做成**人工触发的核实工具**，用法同 2026-09-12 查余额那次
- **不碰自动链路**：请求量极小，先验证接口合同对不对、返回结构是什么、卡台反应如何

### 第二步（稳定后再做，需 Lemon 拍板）：接进自动验证 lane

- `BrowserCardTransactionReader` 支持 highvcc 来源，不再返回占位
- 本机 worker 要能拿到 highvcc token（token 在服务器数据库加密存着，需确认 worker 有无解密密钥）

**必须带的节流**（Lemon 问「会不会大量请求把我列为不当」，这个担心成立）：

| 措施 | 为什么 |
| --- | --- |
| 卡台查询独立最小间隔 30–60 秒，与 5 秒的验证 tick **解耦** | 现默认 `verificationIntervalMs=5s`、`windowMs=5min`，每单最多 60 次 tick；若每 tick 都拉一次卡台（而 `readAllCardTransactions` 还是分页读全量）会变成每天上千次突发请求 |
| 间隔内复用上次结果 | 中间的 tick 一个请求都不发 |
| 只查这张卡、只取最近几条（接口支持分页）| 不拉全量 |
| 先用便宜证据：账号是不是 Plus（ChatGPT 侧）能判就不查卡台 | 多数情况根本不碰卡台 |

改造后估算：100 单/天、10% 结果不明 → **约 100 次/天**，平摊几分钟一次，与一个正常用户在后台翻交易记录同量级。

**第一步稳定运行一段时间后，由我主动提醒 Lemon 决定要不要做第二步。**

### 还缺的一环：运营侧的集中处置台

即使上面两步做完，仍有「人机验证」这类必须人做的。今天暴露的问题是**入口太深**
（UX_PUNCHLIST 第 6 节）：唯一能解开锁定的按钮埋在 Browser 控制面的 run 行里，
而首页「今天要处理的」只展示、不可操作。

方向：**把「系统卡住了、只有人能解开」的单集中到首页那一块，并带上处置按钮**。
判断标准很清晰——需要人做判断或动手的，就该在那里。与「飞书机器人远程处理运营决策」
是同一件事的两面：先把这个集合定义清楚，界面收拢和远程化才有共同基础。
