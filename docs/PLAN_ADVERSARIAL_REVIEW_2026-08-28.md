## 审查结论

总体阶段顺序没有方向性错误，但“一卡多充计数”原方案有一个必须修正的时序缺口：不能只在订单成功后增加次数。

### 必须修正：容量必须在付款前原子占用

如果未来允许一张卡服务多个订单，仅在 `RECHARGE_SUCCESS` 后计数，可能出现：

1. 两个订单同时看到同一张卡仍有剩余次数；
2. 两个订单都进入付款流程；
3. 其中一个尚未成功时，另一个也已经提交；
4. 失败/超时恢复时无法安全判断是否已占用次数。

因此必须在付款授权/资金栅栏阶段，在锁定卡片的同一事务中预留一次消费额度；订单成功后将预留转为已消费，明确失败且未提交时才释放。Provider 交易仍用于确认和补账。

这不是为了增加复杂度，而是“一卡最多 3 次”在并发下成立的必要条件。

## 其他审查结果

- “先做计数基础，再清理库存”顺序正确：先保留证据，避免清理破坏回填。
- “卡段人工刷新+持久选择”与 API 成本目标一致；不应恢复每单读取卡段目录。
- “余额不足可恢复、资料缺失待刷新”方向正确；但后台必须明确显示原因，不能只显示一个 BLOCKED。
- 费用监控应读取 Provider 快照并记录变化，不能把当前 `0.50/0.5%/0.40` 当作永久常量。
- 历史消费卡复用策略必须默认“占用次数不因退款自动归还”；退款只进入人工核对，避免重复使用造成资金风险。

## 修正后的实施顺序

1. 设计并实现“消费额度预留→成功确认→明确失败释放”的最小账本；
2. 接入现有资金栅栏和卡片锁，验证并发下每卡最多 3 次；
3. 用真实订单结构做历史回填和 Provider 补账；
4. 增加后台只读次数/余额/原因视图；
5. 再做库存状态收敛与低价值指标下沉；
6. 最后做费用变化监控和生产恢复评估。

## 卡片状态规划二次审查（2026-08-28）

### 事实核对

- `eligibleInventoryCardSql()` 当前只按 `inventory_status='AVAILABLE'`、Provider 状态、余额、资料新鲜度和历史交易判断，未包含“永久停用”或“产品限制”维度。
- `card-stock-service.js` 的同步路径会依据 Provider 快照重新写入 `inventory_status`；因此直接把现有卡改成 `AVAILABLE` 之外的值而不增加覆盖规则，后续同步可能把人工停用状态覆盖掉。
- 当前生产卡 `493/8590` 仍为 `active/AVAILABLE`；这与已确认的永久不可用事实冲突。
- `4744` 的 Claude 专用限制目前没有出现在统一资格查询的产品参数中；仅改展示状态不能阻止 Plus 分配。

### 必须修正的规划点

1. 不采用“直接批量改 `inventory_status`”作为最终方案；增加最少量的持久化卡片运营策略字段（优先直接放在 `cards`，例如 `allocation_policy`、原因和时间），并让同步与统一资格查询都尊重该策略；不引入独立策略服务。
2. 资格判断必须接收产品维度：`4744` 只允许 Claude，Plus 查询必须排除；不能依赖尾号硬编码。
3. “现有失效批次”与“未来新开卡”必须在数据上可区分，不能把永久失效结论扩展到未来卡片。
4. 8590 的永久停用标记与消费账本历史回填是两件独立事情：前者可先阻止再分配，后者仍需主键证据，不能混为一谈。

### 结论

原规划的方向（先修正状态，再收敛库存）正确，但“增加状态并写入生产”的实现描述过于简单，存在被同步覆盖和产品限制不生效的重大风险。应先完成策略字段/统一查询/测试，再申请生产状态写入；在此之前不修改生产卡状态。

### 对当前规划的修正

1. “6807 当前可用”必须拆成两层：Provider/运营层面的可用，与当前订单分配层面的 `ALLOCATABLE`。真实订单已使用过该卡；在自动跨订单复用尚未启用前，不能因为运营标记就再次分配。

4. Browser 与 API 都必须复用同一套 `ALLOCATABLE` 判断和消费账本，不能为 Browser 另建一套卡片可用逻辑。
