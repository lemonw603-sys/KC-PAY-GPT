# 卡台来源切换、完整快照与付款对账｜D2 最终冻结候选稿

> 版本：D2-FINAL
> 日期：2026-09-06  
> 状态：**用户已于 2026-09-06 确认冻结。后续实现必须逐条遵守；任何方向性偏离须先更新本文件并重新取得确认。**

## 1. 目标

建立一套简单、稳定、能承接多卡台和高频订单的统一履约模型：

- `API 充值` 固定使用 HNSKJ；
- `浏览器自动化充值`可以使用 HNSKJ，也可以使用未来多个无 API 的备用卡台；
- 运营者可以随时直接切换 Browser 当前卡台；
- 系统负责告知风险，但不阻止选择、不自动回退；
- 卡台之间独立归属、独立库存和独立统计，底层仍共用一套订单、卡片、账本、资金栅栏和审计；
- 一笔付款未知只局部核实，不暂停其他订单或整条系统；
- 对账只呈现真实需要处理的问题，不再制造“三方对账”误报。

## 2. 名词与职责

### 充值方式

- `API 充值`：由 API 执行器完成充值；首版卡台固定 HNSKJ。
- `浏览器自动化充值`：由 BitBrowser/浏览器执行器完成购买；卡片可来自 HNSKJ 或备用卡台。

### 卡台来源

银行卡、余额和账单资料的来源，例如 HNSKJ、备用卡台 A、备用卡台 B。卡台来源不等于充值方式。

### 当前 Browser 卡台

运营者预先选择的、供后续 Browser 新订单冻结使用的卡台来源。系统不自行改变该选择。

## 3. 后台职责

### 首页

只负责日常充值方式：

```text
API 充值 / 浏览器自动化充值
```

不在首页重复选择卡台。

### 卡台管理

现有“Plus 卡台路线”页面调整为真正的卡台管理，负责：

- 展示 API 固定卡台 HNSKJ；
- 展示和切换 Browser 当前卡台；
- 按来源展示卡片与库存；
- 为备用卡台导入完整卡片快照；
- 展示最近同步/导入时间和告知性异常。

页面不重复切换 API/Browser，不暴露无关环境变量和底层资金开关。

### 付款核实与对账

现有含义不清的“三方对账”收敛为：

1. `付款结果核实中`；
2. `证据待同步`；
3. `需要人工核对`。

只有第三类计入需要运营处理的异常，并必须存在真实可打开的案例。

## 4. 卡台切换合同

1. Browser 卡台由运营者直接选择；不做 AUTO、评分、整数优先级或自动回退。
2. 目标卡台无卡、余额不足、最近异常或没有 API，只产生提醒，不阻止保存 Browser 选择。
3. API 卡台固定 HNSKJ，不提供无意义的 API 卡台选择器。
4. 高频切换不要求输入固定确认词或十字理由；系统自动记录操作者、旧卡台、新卡台和时间。
5. 切换成功与目标卡台是否能立即执行订单分开表达。
6. 系统不得因目标卡台异常，静默改用其他来源。

## 5. 订单冻结合同

客户提交 CDK + Session 的建单事务必须同时完成：

1. 冻结当前充值方式对应的 `fulfillment_route_id`；
2. API 订单冻结 HNSKJ 卡来源；
3. Browser 订单冻结提交当时的 Browser 当前卡台；
4. 创建后续分卡和 Browser 前置任务。

后续异步分卡只能使用订单已经冻结的来源，不得重新读取全局当前卡台。这样才能保证切换只影响切换后创建的新订单。

## 6. 等待订单批量接管

切换 Browser 卡台时提供两个选择：

```text
只影响新订单
同时接管尚未真正开始的等待订单（预计 X 单）
```

只有同时满足以下条件的订单可以迁移：

- 仍处于允许迁移的等待/创建状态；
- 未分配卡片；
- 没有活动卡片 assignment 或消费预留；
- 没有充值 attempt；
- 没有 Browser run 或付款动作；
- 没有 ACTIVE/UNKNOWN/SETTLED 资金占用；
- 没有需要保持原来源的对账证据。

切换确认前显示预计数量；事务提交后显示实际迁移数量。并发期间已被 Worker 领取或状态变化的订单不强迁、不报系统失败，继续保持原来源。

不提供日常逐订单卡台切换入口。

## 7. 卡台目录与能力

每个卡台来源最少保存：

- 稳定内部 ID；
- 运营显示名称；
- 来源适配器/账户引用；
- 是否支持 API 充值；
- 是否支持 Browser 充值；
- 是否支持 API 同步、自动开卡和自动补余额；
- 最近同步或完整快照时间；
- 运营启用状态与可验证运行证据。

HNSKJ：

- API + Browser；
- 支持 API 同步；
- 支持现有自动开卡与补余额能力。

无 API 备用卡台：

- 只支持 Browser；
- 通过来源专属文件适配器导入；
- 不虚构 API 同步、自动开卡或自动补余额能力。

## 8. 完整快照导入

备用卡台每次导出均为该来源全部卡片，因此导入是完整快照。

### 预览

必须显示：

- 新增数量；
- 更新数量；
- 业务不可用数量；
- 本次快照缺失数量；
- 活动/资金风险卡数量；
- 结构错误和跨来源实体卡冲突。

### 数据分类

- 结构或身份错误：例如缺稳定卡 ID、PAN 格式损坏、文件内重复 ID，阻止整个完整快照提交。
- 业务不可用：例如停用、过期、余额不足，仍属于真实快照，正常记录但不可分配。
- 本次缺失：上一有效快照存在、本次不存在；退出新订单分配，但不删除历史。

### 原子提交

- 上传或预览失败不改变当前有效库存；
- 只有结构完整并经确认的快照整体生效；
- 快照新增、更新、不可用和缺失收敛在一个事务边界内；
- 已有活动 assignment、attempt/run 或 UNKNOWN 的卡保持锁定，不因快照被释放；
- 后续重新出现的卡只有在当前资料、状态、余额、账本和资金条件均通过后才恢复资格。

## 9. 跨卡台实体卡去重

- 文件内按来源稳定外部 ID 去重；
- 同时用 PAN HMAC 对所有来源做实体卡冲突检查；
- 同一实体卡出现在不同来源时，不创建第二个可分配实体、不自动搬家；
- 将其标记为来源冲突供运营核对，历史账本和订单仍归原实体卡；
- 完整 PAN/CVC 不进入普通日志、预览或审计文本。

## 10. 分卡与余额规则

1. 分卡只在订单冻结来源内进行，不在多个来源中按 priority 混选。
2. 可分配资格继续统一考虑卡状态、资料、余额、活动绑定、消费次数、退款/争议和资金状态。
3. 导入器只记录快照事实，不硬编码 `$16` 或其他商品金额；资格由统一业务规则按订单需求动态计算。
4. HNSKJ 使用实时 API 证据和现有新鲜度规则。
5. 手工来源使用最新完整快照、本地消费账本和 Browser 实际支付结果；不因没有 API 而伪造同步时间。
6. Browser 付款确认后按实际结算金额更新消费账本和预计余额；下一次完整快照用于校准。

## 11. 付款结果收敛

付款点击前保留唯一提交意图；点击后：

### 明确成功

观察到付款确认和 Plus 激活后，继续取消续费、更新订单和账本。卡交易可后续同步，不阻塞客户成功结果。

### 明确失败

确认未付款且账号仍为 Free时，记录明确失败；不进入人工对账误报。

### 短时无响应

进入有界的自动 `VERIFYING_PAYMENT`：

- 继续只读观察账号订阅状态；
- 观察 Checkout/账单结果；
- HNSKJ 可读取卡交易；
- 手工来源等待本地/后续快照证据。

具体观察时长和间隔由真实订单证据校准并配置化，不在方案阶段写死。

### 长时间仍未知或证据冲突

只锁定相关订单、账号、卡和 Browser run，生成真实人工案例；同一未决订单不自动第二次点击。其他订单、卡、Profile、卡台、接单和营业继续运行。

## 12. 路线化对账证据

### API + HNSKJ

```text
本地订单 + ZZSHU明确结果 + HNSKJ卡交易
```

### Browser + HNSKJ

```text
Browser提交/结果 + ChatGPT Plus激活/取消 + HNSKJ卡交易
```

### Browser + 手工卡台

```text
Browser提交/结果 + ChatGPT Plus激活/取消 + 本地消费账本 + 后续完整快照校准
```

无实时交易 API 本身不算异常；等待同步属于普通状态。

## 13. 对账展示合同

- 明确失败没有外部充值订单号不算异常；
- 交易尚未结算/同步不算人工异常；
- 一卡多单使用订单冻结卡和消费账本，不再依赖旧 `cards.order_id`；
- Browser 不使用硬编码 ZZSHU 的判断；
- 总览“需要人工核对”数量必须与真实案例队列一致；
- 已解决案例保留审计，不继续计入待处理。

## 14. 并发与容量

- 当前卡台切换与建单使用一致的事务/行锁，明确切换边界；
- 完整快照提交与分卡使用来源/卡行事务锁，避免移除与分配竞态；
- 不因导入、切换或单笔核实暂停整个 Worker；
- 不复制卡表、订单表、账本或对账系统；
- 6 个 Browser Profile 继续独立串行、Profile 间并行；一单 UNKNOWN 不占用或阻塞其他 Profile 的订单调度，相关账号仍保持唯一活动运行约束。

## 15. 通知原则

- 普通“核实中”“证据同步中”不反复 Bark；
- 只有需要运营动作、来源完整快照异常、真实证据冲突或持续不可执行时推送；
- 同一事件去重、限频，恢复后闭环；
- 通知只告知，不自动切卡台或重付。

## 16. 明确不做

- 不做自动卡台评分、优先级或自动回退；
- 不做日常逐订单选卡台；
- 不把 API/Browser 与卡台来源混成一个开关；
- 不因目标卡台异常阻止运营选择；
- 不因一单 UNKNOWN 停止全局；
- 不为每个卡台复制订单、卡片、账本或后台页面；
- 不物理删除完整快照中消失的历史卡；
- 不把无 API 来源伪装成支持实时同步或自动补给。

## 17. 实现前必须修正的现有候选

- 参数化当前写死的 `SOURCE_ACCOUNT_ID`；
- 给导入批次绑定明确来源和解析 adapter；
- 移除 `fulfillment_route_card_sources.priority` 驱动的自动混选语义；
- 在订单建单事务冻结卡来源；
- 实现完整快照缺失卡收敛；
- 区分结构错误与业务不可用卡；
- 加入跨来源 PAN HMAC 实体卡冲突检测；
- 消除新增卡 `$16` 硬编码；
- 修正对账的旧 `cards.order_id`、ZZSHU 硬编码和明确失败误报；
- 统一总览数字和真实案例队列。

## 18. D3 实现与验收最小矩阵

必须覆盖：

1. API 永远只使用 HNSKJ；
2. Browser 可分别冻结并使用 HNSKJ、备用卡 A、备用卡 B；
3. 切换到无卡/异常来源仍能保存且只提醒；
4. 切换不影响已建单，除非明确选择安全批量接管；
5. 并发切换/建单不会冻结错来源；
6. 快照新增、更新、业务不可用、缺失、重新出现和结构失败；
7. 快照提交与并发分卡不会双分配或释放活动卡；
8. 跨来源同实体卡不会双分配；
9. 一卡多单对账使用正确订单/账本；
10. 明确失败不产生三方误报；
11. Browser + HNSKJ 与 Browser + 手工卡分别完成证据收敛；
12. 一单 PAYMENT_UNKNOWN 时其他订单/Profile继续；
13. 总览人工核对数量等于案例队列；
14. 不输出完整 PAN/CVC/Session；
15. migration 从生产 047 和空库均可重放，支持回滚/前滚。
