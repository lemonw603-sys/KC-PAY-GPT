## 发现

### F-61 “解决资金核对”只关闭案例，不处理订单或消费账本
- 板块/严重度：E / P1。
- 观察：工作台data-resolve-wb-case调用resolveReconciliationCase，只让用户输入note，然后POST `/reconciliation-cases/:id/resolve`。server绑定`reconciliationCases.resolve`，该函数只UPDATE reconciliation_cases。
- 结论：不等同于既有RESOLVE_UNKNOWN_PAYMENT或API resolve-unknown-submission；案例可消失，订单/attempt/卡占用/账本仍未收口。与任务书“按钮真处理、写账本”及交接声称不符。
- 证据：`v1/public/admin/assets/admin.js:383-389,577-587,1801-1807`；`v1/src/server.js:274`；`v1/src/services/reconciliation-case-service.js:238-262`。在内存query适配器上执行正式resolve，唯一写SQL原始输出：
  `UPDATE reconciliation_cases SET status = 'RESOLVED', resolution_note = ?, resolved_at = ?, updated_at = ? WHERE id = ? AND status <> 'RESOLVED'`。
- 影响条件：用户从新工作台对付款不明case点击解决；不是付款/销卡操作已经完成后单纯关闭记录。
- 反证：旧关闭案例端点本身可以作为记录管理功能，不要求删它；问题是新工作台赋予其“处理资金问题”的含义。没有生产点击试验，未证明已有客户受损。
- 最小验证：隔离订单付款不明→点击工作台处理→核对订单、attempt、账本、卡占用、case全部权威状态，不只查case已关闭。
- 建议：按case类型带到已有正式收口入口，或明确只叫“关闭记录”；不能把后者当资金问题已解决。
- 置信度：高。

### F-62 真实字段接错，“无法核对30张”显示为0
- 板块/严重度：E / P1。
- 观察：renderWbRecon读取`daily.unverifiableCount ?? 0`；服务输出的是`unverifiableAmountCount`。
- 结论：未知/字段遗漏被默认成零，产生与后台事实相反的看板数字。
- 证据：`admin.js:370`，`daily-reconciliation-service.js:353`。本机Playwright加载git对象`8cd6d7e`的HTML/JS/CSS，拦截所有请求注入`unverifiableAmountCount:30`；实际页面文字输出`0 无法核对 无期初金额`，无pageerror。未提交版本该字段仍相同。
- 影响条件：真实返回该字段且计数非零；不需要异常操作。
- 反证：浏览器数据为明确标识的合成夹具，不冒充生产浏览器会话。字段拼写由当前服务源代码独立核实。
- 最小验证：用服务真实字段结构给浏览器，断言页面30；字段缺失应显示未知/加载失败，不应显示0。
- 建议：固定UI消费的响应样例，未知值与真实零分开。
- 置信度：高。

### F-63 待办数据获取失败被吞成空列表，页面会宣称“没有要处理的”
- 板块/严重度：E / P1。
- 观察：loadOverview把alerts/cases/orders请求失败分别catch为空数组、daily失败catch为null；renderWbQueue在缺少数据时输出“没有要处理的，今天清爽✓”。
- 结论：部分接口失败与已查询确认无待办不可区分，会把数据读取失败呈现为正常。
- 证据：已发布版本`admin.js`的loadOverview（约453行起）及renderWbQueue；本地浏览器对对应空值调用正式渲染函数，输出`没有要处理的，今天清爽 ✓`。查询失败转空值的路径另由源码核实。
- 影响条件：overview成功但待办相关接口失败/超时，且overview残存计数未形成items；不要求全站宕机。
- 反证：catch用于避免单接口拖垮整页有价值，但应同时显示错误，不必让整页报错。
- 最小验证：拦截待办接口返回500，其他成功；应显示“待办读取失败/重试”，不显示正常空态。
- 建议：保留各板块加载状态，把部分失败与空结果分开。
- 置信度：高。

### F-64 队列来源和“看逐张”目标没有闭环
- 板块/严重度：E / P1。
- 观察：renderWbQueue没有消费daily.retirementDueCount，也没读取card-retirement/candidates；alerts一律append标题消息，多数无按钮且未按处置对象去重。无主扣款“看逐张/去处理”只跳diagnostics，diagnostics加载的是旧cases、runs等，不展示daily.discrepancies逐卡报告。
- 结论：按钮能跳页不等于能找到该对象并完成处理；待销到期不能因“完整动作在卡片页”就从工作台提醒消失。任务书要求的核心工作流未完整接上。
- 证据：`admin.js:377-407`的renderWbQueue及switchView的diagnostics加载分支；index.html的“看逐张”仅data-view-jump=diagnostics；全文件daily接口只有loadOverview消费。输入retirementDueCount=4且其他来源为空，不产生任何待销项。
- 影响条件：有到期待销卡、需逐卡核查的差异或需要特定动作的告警。
- 反证：卡片页尚未重做是已明确未完成范围，不要求工作台复制完整卡片功能；可精准跳转而不重复实现。原型本身也有演示性占位，不能将其全部视为已经可操作。
- 最小验证：每个队列来源造一条→可见→点到同一对象→已有正式动作→确认退出条件。
- 建议：只聚合可解释、可定位的业务对象；完整动作可在专页，但跳转须携带定位信息并有真实落点。
- 置信度：高。

### F-65 旧供给开关复用仍会同时打开已弃用的补余额
- 板块/严重度：B/E / P1（既有风险被工作台沿用，不是本次新写后端）。
- 观察：已发布第⑥版营业条保留“能不能开卡补钱”；调用supply-automation。`admin-operations-service.js:158-166`遍历两个键一起写true。生产01:46:06 UTC实际是auto_replenishment=true、balance_recharge=false。
- 结论：保留旧handler不是不变语义的保证；点击开启会改变当前刻意拆开的供给权限，与放弃补余额的基线冲突。
- 证据：8cd6d7e的renderDecisions/data-supply-toggle；当前`admin.js:2429`附近旧handler；`admin-operations-service.js:158-175`；只读SQL原始输出见上。

- 反证：未提交重做版已移走营业条该组控件，说明在修；但迁到设置页时不能继续使用错误组合语义。生产已回滚，第⑥版当前未运行。
- 最小验证：隔离环境从true/false点击自动开卡控制，核对不会把补余额打开。
- 建议：按当前业务决定选择实际开关，不按旧函数名字复用。
- 置信度：高。

## 视觉与交付过程判断（不重复制造缺陷编号）

本轮使用本地Playwright渲染选定原型C与**已回滚提交**，未访问生产管理界面、所有API均被拦截为夹具。观察到营业条从接单/派单/付款三个toggle变成五决定按钮组；搜索从顶栏移至营业条下；外壳仍旧皮；数字墙多个格子为待接入。界面可加载，但与原型显著不同。

**不能把所有差异都说成执行者擅自更改**：D-283明确写“sidebar暂留旧皮”，与原型整体换皮预期及后续回滚说明有冲突；任务书和D-283对待处理队列位置也存在不同描述。应让用户确认哪张原型/哪些差异有效，再作为交付基准，不能挑一份文档追责。

三个待接入指标有明确披露，不算造假；但“诚实占位”不自动意味着用户同意以半成品上线。发布前应列明本次就交付哪些、不交付哪些，由用户确认。当前未提交版把未实现指标替换成可分配卡/告警数，属于改变展示内容，应再次对齐，不作为成品判错。

## 怎样纠正、怎样防止再犯（建议，非已批准任务）

1. **一次冻结一个工作台交付**：选定原型C截图+明确允许的差异+未交付项；不要一边接真实数据一边自行重新设计。
2. **数据和动作各一张小清单**：每个数字列实际接口字段/时间口径/缺失态；每个按钮列真实后端动作与哪些业务状态应改变。名单短到覆盖本次工作台，不扩成项目文档工程。
3. **先闭合最关键一条**：付款不明出现→看证据→正式核实收口→订单/账本/占用/待办同步正确；再做其他队列来源。不要只验证按钮有响应。
4. **隔离环境真浏览器验收**：同尺寸比原型；带有待办、无待办、接口失败、权限拒绝的样例；执行真实后端动作的测试只在隔离库，不用生产客户单试错。
5. **发布门槛分三件**：外观符合选定方案；数据与字段口径正确；动作业务结果正确。测试数量、HTTP200、SQL有返回不能替代任何一件。
6. **用户负责方向与最终体验，不负责帮模型找基础接线错误**：先由执行者提交上述证据，再由审查员验证，最后给用户看实际页面决定是否发布。
7. 现有原生JS/CSS足够，不建议换框架、推倒后端或新建待办系统。能复用的安全逻辑继续用，但先核实职责。
