- 重现（固定目录代码，补齐必需参数）：`300000 constructs OK` / `1800000 THROWS timeoutMs must be an integer between 1000 and 300000`。
- 核实器在付款 handler 里、付款适配器创建之前构造（`shared-live-composition.js:254`）→ **填卡与点击之前报错，不扣钱，但每张真付款单都会失败**。付款不明补核线同值（`live-post-payment-recovery.js:78`）也会报错。
- 为何没暴露：09-18 之后 `browser_runs` 中 payment_state 越过 NOT_STARTED 的 **0 条**；演练在 `shared-live-composition.js:240` 提前返回，不构造核实器。
- 失败后订单归类：按代码与 RUNBOOK §1②应为付款前安全中止（判失败、退 CDK、放卡），**未实测**。
- 建议：立即配置止血（LaunchAgent 环境变量设 300000 + 池重启约 2 分钟）；白天代码修：池配置上限与核实器一致、启动时校验（值不合法池起不来，而不是每单失败）、加跨模块测试；「30 分钟窗口」若仍要，须与 900 秒运行租约一起设计。

## P3｜提速（数据：6 张全自动成功单 09-11～09-16 旧代码 + WAL 51 次运行 + 09-25 一份完整 trace）

一单全自动中位约 **160～195 秒**。主要耗时：

| 段 | 中位 | 性质 |
|---|---|---|
| 点击付款 → 判付款不明 | ~43 秒 | 我们的等待：6/6 内联确认都没成，全靠补核线 7～23 秒确认；为何内联失败无埋点 |
| 结账导航 | ~23 秒 | ChatGPT sentinel + checkout POST（6.4 秒）+ Stripe 首连 TLS 6 秒（n=1）；另有最多 10 秒入口等待 |
| 等 Stripe 支付区 | ~19 秒 | 外部 |
| 注入 + 重载 + 身份探测 | ~17 秒 | 含一次多余整页重载（`executor.js:111-112` 与 `:294-295`） |
| 本地库串行往返 | ~20–25 秒 | 每条 SQL 经隧道约 0.2 秒，每个检查点同步写库 |
| 付款不明 → 成功 | ~10 秒 | 固定 5 秒首查 + 池 3 秒一轮 |

**比提速更大的是可靠性**：15 张 Browser 成功单只有 6 张全自动，另 9 张人工收口，提交到成功中位约 68 分钟。

候选（都不动付款前三件、不改点击 / 重试 / 成功判定）：①点击后只读埋点（先弄清 43 秒）；②核实轮询 5 秒→2 秒（配置）；③新标签不重复 goto；④卡预检与注入 / 探测并行；⑤库时间线异步写（WAL 仍同步）；⑥池轮询 3 秒→1 秒（配置）；⑦入口等待缩短或竞速；⑧代理首连慢先多抓 trace。①②⑥ 不需演练；③④⑤⑦ 动 browser-mvp 需一次演练。
