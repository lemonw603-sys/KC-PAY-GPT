# 需求对齐草案（2026-08-21）

> 状态：历史对齐草案，已由 `FINAL_REQUIREMENTS_BASELINE_2026-08-21.md` 取代。不得将本文仍需确认的旧问题覆盖最终基线。

## 本轮已确认方向

- v1 只做 Plus。
- 目标账号必须是免费账号；当前已经是 Plus 时禁止充值。
- 客户购买后必须走完整链路，最终还要确认取消自动续费成功。
- 客户页面展示客户自身可理解的原因，例如账号已是 Plus、Session 无效；不展示卡片不足等内部资源问题。
- 当前允许手动开一部分卡；未来系统既支持手动补卡，也支持达到阈值后自动开卡。
- 库存不足时订单进入“等待补卡”，后台需要提示并通知运营者。
- 最低余额由运营者配置。
- 目标规模为每天 100–300 单，优先尽快实现稳定自动化。
- 充值不应要求运营者逐单手工确认；客户已付款后应自动执行，并通过系统门禁防止重复充值和内部损失。
- CDK 主要由后台生成后人工发放，支持单个和批量。
- CDK 需要批次作废、补发和完整交易/交付服务记录。
- CDK 绑定产品，不绑定价格；未来需要为更多产品预留能力。
- 后台当前优先级：成功充值、CDK 管理、对账，以及规模化能力（用户回复“A D E/C”）。
- 退款由人工处理，不做自动识别或自动提醒。
- 追溯链至少包含：CDK → 订单 → 卡片 → Provider 订单 → 卡片交易 → 失败/退款案件，以及客户邮箱和充值时间。
- 当前继续沿用现有服务器和平台布局。
- 只有一个管理员。
- 客户邮件、短信和其他外部通知暂不做；后台、内部事件和运营通知仍需同步。
- “卡网”是口误，不属于项目系统，不纳入设计和排查范围。
- 卡台需要提前具备可替换和备用能力：当前尚无第二卡台；未来先由运营者在后台人工切换新订单使用的卡台，旧订单继续保留原卡台路线，暂不做自动故障切换。
- Session 失效时，允许客户在原订单上更换 Session，优先保持原订单和客户体验，不要求重新消耗 CDK。
- 当前自动补卡暂定为：每次 1 张、每张 `$16`、每天最多 5 张；后续参数必须可扩展。
- 客户付款在系统外通过支付宝/微信完成；后台生成 CDK 即代表客户已付款，CDK 兑换后可以进入自动履约。
- 原订单 Session 最多允许更换 3 次，仅限尚未产生充值资金影响前。
- 卡台替换的现实原因包括无法开卡、API 失效、卡片无法付款；备用卡台用于新订单容灾，当前 API 执行器优先，浏览器执行器后续开发。
- 自动补卡的每日 5 张只统计自动开卡，人工开卡不计入；库存以 active 且未充值、未绑定订单、完整卡资料为核心条件。
- Pro 5X、Pro 20X 暂不实现充值；先稳定 Plus，未来再扩展。

## API 已核实事实

## 总体积木式架构（本轮重新确认）

后续系统固定按三端设计：

```text
第一端：可切换的卡台适配层
第二端：运营后台（数据中心 + 操作中心）
第三端：执行/充值台（API 执行器 + 浏览器自动化执行器）
```

运营后台是唯一的订单、库存、审计和控制中心；API 充值和浏览器充值不是两套互相独立的业务，而是第三端的两个执行器，共用订单状态、资金尝试栅栏、审计和对账。所有 MVP 工作都必须服务于未来每天 200–300 单，不为短期能跑而破坏可切换、可恢复和可扩展边界。

### 直充 Provider

- 创建接口固定使用 planType=plus。
- 创建接口没有调用方幂等键。
- 创建成功不等于最终成功，必须查询最终状态。
- 状态查询存在 is_subscription_cancelled 字段。
- 文档要求成功后延迟补查取消续费状态；is_subscription_cancelled=1 才能证明取消完成。
- 真实生产响应 40030：仅支持免费账号提交，当前账号套餐为 plus。
- 当前公开合同没有独立、无副作用的账号套餐预检接口。

### 卡台 Provider

- 卡台负责开卡、卡片详情、余额和交易读取。
- 开卡使用独立幂等键。
- 项目接口合同记录了 HNSKJ Open API 的 `POST /cards/{id}/recharge`（给既有卡追加余额）；但当前 v1 适配器和脚本尚未实现或实测该接口。根目录 `对接api.md` 的 `/bank-cards/{id}/balance` 属于另一套 legacy `/pay` 合同，不能混用。
- 最低余额、卡段和批量开卡规则必须以卡台实时目录为准。

## 仍需确认的关键问题

### 1. 免费账号预检

由于 Provider 文档没有独立套餐预检接口，需要确定规则：

- 是否使用现有 Session 信息接口作为本地预检；
- 如果 Session 信息接口无法明确返回免费/Plus，是否直接拒绝订单；
- 是否允许把 ZZSHU 40030 作为最后一道兜底，而不是首次预检。

当前建议：无法明确证明是免费账号时，不调用直充创建接口。

### 2. 自动化资金门禁

“自动化”理解为客户付款后自动执行，不是每单人工点击。仍需确认自动化的放行条件：

- 客户订单已支付；
- CDK 已兑换；
- Session 有效；
- 账号明确为免费；
- 库存卡状态、余额和凭据达标；
- Provider 路线可用；
- 没有活动 Permit、未知 Provider 调用或资金风险；
- 订单没有历史尝试。

任何条件失败都自动停在可恢复状态，并通知运营者。

### 3. 卡片失败分类

需要确认以下分类是否符合业务：

- 开卡请求明确失败、没有产生卡：订单进入“等待补卡”，内部通知运营者；
- 卡台返回未知结果：禁止再次开卡，进入人工复核；
- 卡已经开出但状态失败/资料不完整：卡进入失败或隔离库存，不能分配；
- 卡余额不足：属于内部库存问题，客户页面不显示；
- 卡片在直充后发生资金结果不明确：订单进入人工对账，不能换卡重提。

### 4. 自动补卡

参数已经暂定：每次 1 张、每张 `$16`、每天最多 5 张自动开卡。仍需实现触发与上限策略：

- 低于固定卡数阈值；
- 低于预计可处理订单数；
- 低于余额达标卡数；
- 还是三者同时满足。

自动创建批次后由开卡 Worker 执行；人工补卡仍保留且不计入每日自动上限。达到每日 5 张上限后，只告警并让订单等待补卡，不继续产生开卡费用。

### 5. CDK 格式

当前代码实际已经生成分组格式，并兼容旧的不分组格式：

- PJ- 前缀；
- 新生成：后面 20 位随机字符，按 5 位分组，共 4 段；
- 导入/兑换：同时接受历史的 PJ- 加 20 位不分组格式。

本轮用户已明确最终新格式为：

PJ-ABCDE-FGHIJ-KLMNO-PQRST

代码已经符合这个生成格式；仍需补齐合同和交接文档的统一表述，并确认历史不分组码继续兼容不变。

### 6. 未来产品目录

v1 仍只启用 Plus，但需要确认未来产品的准确名称和代码：

- Plus；
- Pro 5X；
- Pro 20X；
- Max 是否是独立产品，还是对 Pro 的口头称呼。

价格不绑定到 CDK，但产品代码必须绑定到 CDK/订单/履约路线。

### 7. Provider 路线

当前代码使用 HNSKJ 卡台 + ZZSHU 直充。需要确认：

- v1 是否固定这两个 Provider；
- 是否只做可替换接口，不在近期接入第二个直充 Provider；
- Provider 明确拒绝、容量不足、维护、超时和未知结果是否按不同内部状态处理。

### 8. Session 更换

已确认：Session 失效时允许在原订单上更换 Session，最多 3 次。这里的有效期是原订单允许更换 Session 的窗口，不是 CDK 过期时间；建议初始配置为 72 小时（可配置），且只能在尚未产生充值资金影响前更换，过期后转人工处理。实现时必须保留原订单、CDK 兑换记录、客户邮箱和审计事件。

### 9. 卡片余额与自动充值

项目接口文档列出了 HNSKJ `POST /cards/{id}/recharge`，但当前 `v1/src/providers/hnskj-card.js` 没有对应方法，现有开卡脚本也没有调用路径；本轮未对该写接口发起真实请求。必须先核实请求字段、权限、幂等/重复扣款语义和响应，再决定是否接入余额补充执行器。

结论：在接口完成核验并通过资金安全验收前，库存仍要求 active、未充值、未绑定订单、完整卡资料，并满足配置的最低余额。

实现差距：当前 `assignAvailableCard` 和库存统计主要检查 `active`、未绑定、余额和凭据，尚未用卡交易证据明确排除“历史已有充值”的卡；这属于后续必须补齐的代码条件，不能把现状误称为已经满足新规则。

### 9. 退款与交易

你已明确不做自动退款识别和提醒，但仍需确认：

- 是否继续自动同步卡片交易作为原始证据；
- 是否只在你手动操作时创建退款案件；
- 退款案件是否仍在后台保留状态和人工备注；
- 是否完全不发送 Bark 退款提醒。

## 当前不应立即修改的内容

在以上问题确认前，不应直接：

- 改 CDK 格式；
- 开启自动补卡；
- 改成全自动 Provider 切换；
- 把卡片不足显示给客户；
- 把成功条件只定义为 Provider success；
- 删除已有对账和交易记录；
- 把当前 Plus 账号重新提交给上游。
