## 错误判断及纠正

### E1｜把“充值方式”“卡台来源”“现有卡台路线”拼成同一套控制面

**错误**：直接提出首页“充值方式与卡台”，并假设现有“卡台路线”可以退化为技术配置页。

**事实**：现有“Plus 卡台路线”直接操作 `fulfillment_routes.accepts_new_orders`，与默认 API/BROWSER 方式切换重叠；生产尚无独立 Browser 当前卡源模型。

**纠正**：先重定义现有入口职责，不能在其上直接叠加一个想象中的“当前卡台”。API/BROWSER 是充值方式；HNSKJ/备用卡台是卡片来源。最终入口位置仍待讨论。

### E2｜为 API 与 Browser 各保存一个可切换的当前卡台

**错误**：提出“API 当前卡台”和“Browser 当前卡台”对称保存、对称切换。

**事实/需求**：当前只有 HNSKJ 具备 API 卡能力；用户明确 API 业务上固定现有卡台。只有浏览器自动化充值需要在 HNSKJ 和多个备用卡台之间选择。

**纠正**：首版不为 API 建通用卡台切换器。API 显示其固定来源即可；只给浏览器自动化充值提供卡台选择。

### E3｜引入 AUTO、指定优先、暂停和自动排序

**错误**：提出 AUTO/PREFER/DISABLE、整数优先级和自动候选排序。

**事实/需求**：用户掌握卡台实时运营情况，要求直接选择当前卡台；目标卡台异常时不自动回退。

**纠正**：不做自动优先级、评分或自动跨源回退。Browser 只有一个由运营者明确选择的当前卡台；系统负责展示事实和提醒。

### E4｜将库存/健康/能力作为“切换失败”条件

**错误**：提出目标卡台无卡、不健康或能力不足时“切换未完成”。

**事实/需求**：当前生产的确会用健康字段阻止路线切换，但这不是用户希望的新卡台选择合同。用户要求能够保存选择，系统只尽告知义务。

**纠正**：区分“选择已保存”和“当前能否执行订单”。无卡/异常可产生醒目提醒和后续等待，但不能阻止运营者选择该卡台，也不能自动改选其他卡台。

### E5｜提出日常单订单卡台切换

**错误**：提出在订单详情页增加“本单指定卡台”。

**事实**：订单在客户提交事务中已经创建并立即排队 `ASSIGN_CARD`；Browser 还同时排队 `BROWSER_PREFLIGHT`。系统没有稳定的人工选择窗口，逐单操作也不适合高频自动履约。

**纠正**：不设计日常单订单切换。需要在订单到来前选择当前 Browser 卡台，并由建单事务自动冻结。

### E6｜把卡源冻结点放在“分配卡片时”

**错误**：此前讨论稿写成“分配卡片时冻结卡台来源”。

**代码事实**：订单创建时已经冻结 `fulfillment_route_id`，随后异步执行 `ASSIGN_CARD`。订单可能在等待卡片期间遇到运营者切换。

**风险**：如果到分卡时才读取当前卡台，那么切换会影响切换前已经提交但尚未分卡的订单，违反“只影响之后新订单”。

**纠正**：Browser 当前卡台必须在客户建单事务中被快照并冻结到订单（或不可变的订单卡源选择记录）；后续分卡只按该冻结来源选择。切换只影响事务提交之后创建的新订单。

### E7｜把“配置版本”当成必须的首版结构

**错误**：过早提出复杂 `config_version/source_policy_version` 模型。

**事实**：现有系统已有 `provider_route_switch_events` 审计，但生产没有卡源策略表；用户要求简单、稳定。

**纠正**：首版只需要一个 Browser 当前卡源选择、订单冻结引用和切换审计。是否需要显式策略版本应由并发一致性设计证明，不能预先扩张。

### E8｜声称健康状态可由系统完整自动决定

**错误**：未经完整调用链验证就把“接口失败、连续超时、同步失败”写成已经明确的卡台健康机制。

**事实**：生产 `provider_accounts` 有 `read_enabled/circuit_state/retry_after_until`，现有路线切换读取这些字段；但新手工备用卡源没有 API，不能沿用同一探针语义，生产也没有独立备用卡源健康模型。

**纠正**：HNSKJ 可展示现有运行证据；无 API 备用卡台的“健康”首版应只展示可验证事实（导入是否成功、有效卡数量、最近使用结果等），具体规则仍待讨论，不能假装已有统一自动健康判断。

### E9｜虚构了尚不存在的后台字段和操作

**错误**：提出卡台卡片上已经/应立即展示“活动订单数、最近异常、暂停/恢复、查看健康”等，并写成近似确定布局。

**事实**：当前生产卡台路线页只展示路线、新订单、卡台账户、读写、健康和切换；本地卡库存仅新增来源分组，备用卡策略尚未部署。

**纠正**：这些只能作为候选信息项，必须根据真实运营决策价值逐项取舍，不能写成现有功能或已确定设计。

### E10｜将“切换后已有订单不受影响”说对了，但没有设计出保证条件

**错误**：只写提示文案，没有指出必须由建单事务保存卡源才能实现。

**纠正**：这不是文案规则，而是数据库一致性要求：读取当前 Browser 卡源与创建订单/冻结来源必须处于同一事务一致性边界；否则并发切换时仍可能选错来源。

## 当前仅保留的讨论基线

1. 名称：`API 充值`、`浏览器自动化充值`。
2. API 充值固定当前 HNSKJ 卡台，不设计通用 API 卡台切换。
3. 浏览器自动化充值由运营者直接选择一个当前卡台，可选 HNSKJ 或备用卡台。
4. 系统可以提醒异常，但不阻止选择、不自动回退。
5. 不做日常单订单切换。
6. Browser 卡台选择必须在订单创建时冻结；后续异步分卡不得重新读取全局当前值。
7. 入口位置、显示字段、无 API 卡台健康口径仍未最终确定。
