# 核心规格｜订单生命周期、执行流程、五个决定（草稿 v0，2026-09-07）

状态：草稿。只写决定，不写解释。两个【待验证】项由只读验证填写；真实单跑通前不冻结，跑通那一刻按实测修订一次后冻结。上位文件：`docs/PRODUCT_SIMPLIFICATION_DISCUSSION.md` 末尾「接班实施基线」。

## 1. 订单生命周期

阶段按客户线定义，是现有 `orders / recharge_attempts / browser_runs` 状态的投影，不新增状态机；后台与客户页共用同一个推导函数。

| 阶段 | 含义 | 客户看到 |
|---|---|---|
| RECEIVED | 已收到 CDK+Session，尚未验 | 已收到，正在检查 |
| SESSION_INVALID | Session 验证失败，等客户重贴 | 请重新提供登录信息（无次数与时间限制） |
| QUEUED | 通过验证，等身份或卡 | 排队中，前面 N 单，预计 X 分钟 |
| LOGIN | 身份内注入 Session、核对邮箱与套餐 | 处理中 |
| CHECKOUT | 创建结账、填卡/地址/邮箱、重报价校验 | 处理中 |
| PAYING | 付款意图已落库 → 单次点击 → 等结果 | 处理中 |
| VERIFYING | 核实开通、刷新凭证、取消续费（最终阶段） | 即将完成 |
| UPGRADING | 仅多阶段产品：第二阶段付款（回到 CHECKOUT→PAYING→VERIFYING） | 处理中 |
| DONE | 最终套餐生效 | 已完成，几分钟内生效 |
| CLOSED_NO_PAYMENT | 付款前终止（账号已是 Plus、账号受限、卡被拒、系统原因） | 明确原因；CDK 可再用 |
| PAYMENT_UNKNOWN | 点击后结果不明 | 处理中，请勿重复提交 |
| FAILED_AFTER_PAYMENT | 已付款但未交付 | 请联系客服 |

每次阶段变化写一条 `order_events`（带 stage 与耗时）。停留时长与「需要我做什么」由阶段推导。

## 2. CDK

状态：AVAILABLE → IN_USE（绑定活动订单）→ DELIVERED；CLOSED_NO_PAYMENT 自动退回 AVAILABLE；PAYMENT_UNKNOWN / FAILED_AFTER_PAYMENT 不退回，等人工；REVOKED 由运营作废。产品由 CDK 决定。同码同账号重复提交返回原单。

删除：补发、Session 更换次数上限、修复窗口、CDK 交付记录、10 分钟清空、CDK 操作密码。

## 3. 付款阶段

一单 N 个阶段。Plus = 1。Pro 5x / 20x = 1（09-07 验证：免费账号可直接创建 Pro 结账；付款成功待真实单。先 Plus 再升级只作备选，不走同一结账入口）。每阶段一个 attempt、一次付款、独立未知锁定；阶段间沿用同一身份与登录态；最终阶段成功后才取消续费。

## 4. 供给

按产品配置：开卡金额、最低余额、一卡几单（Plus 由运营者设置，Pro 固定 1）。多卡台可注册，运营者指定，不自动回退；备用卡台以完整快照导入；结清的卡下次快照恢复可分配（`45f953c`）。系统在卡台维护、连续开卡失败、可分配为零时在首页给出切换按钮；备用卡台可分配低于 N 张时提醒。

## 5. 执行流程（形状）

身份池：N 个常驻 BitBrowser 身份（现 6），各自保持登录不关窗（Worker 的 runtime `residentProfile=true`，close 即 detach，不再调用 `/browser/close`）；一单一身份串行，身份间并行；每单结束清登录态、留设备与 Cloudflare cookie，不为每单新建窗口（09-07 用户确认）；Worker 搬到常开机器。

每单步骤，全部在该身份内完成：

1. 注入 Session：CDP 写 `__Secure-next-auth.session-token`（分块规则同上号器）；`/api/auth/session` 取邮箱与 access token；账户检查核对套餐。坏 Session 在客户贴码时即在常驻身份内做这一步，秒级打回。
2. 创建结账：打开定价弹窗，点击目标套餐按钮（Plus=「Upgrade/Rejoin Plus」，Pro 5x/20x=「Upgrade to Pro」+ 档位），由页面自己发 `backend-api/payments/checkout`（页面附带反自动化签名头，裸调会被拒，09-07 验证）；拦截响应取 `checkout_session_id` + `client_secret`（custom 模式无 URL）；付款表单为页面内嵌 Stripe。
3. 结账页：唯一必须用浏览器的一步。卡、账单地址（免税州，按卡固定槽位）、邮箱一次填完；等一次重报价；校验币种 PHP、税 0、金额算术一致。
4. 付款：`BROWSER_LIVE_STOP_BEFORE=SUBMIT`（演练模式，09-07 已实现：同一条 LIVE 单遍填写路径，不申请 permit、不落付款意图、`authorizeSubmit` 恒为不执行，停在点击前，返回严格报价，订单回到 CARD_READY，身份页面保留）；否则付款意图先落库，再单次点击。
5. 结果：观察页面结果 → 账户检查核实开通 → 【待验证 A2】付款后凭证刷新（假设：用仍有效的 session cookie 换新 access token）→ 取消续费走接口（多阶段产品在最终阶段）。
6. 收尾：写回时间线与证据（身份、出口、卡、地址槽位、结果、挑战/拒付）；释放身份，清一次 cookie。

资金三道门，其余闸门删除：数据库 `browser_payment_writes_enabled`；单订单 permit；`PAYMENT_SUBMIT` 唯一 operation。

### 5.2 常驻多身份 Worker（09-07 实现，`production-live-pool-worker.js`）

- 一个进程、N 条 lane（`BROWSER_POOL_LANES=laneId=bitbrowserProfileId,...`，1–6 条），每条 lane 绑定一个常驻 BitBrowser 身份，`workerId=pool:<lane>`，窗口永不由 Worker 关闭。
- 每条 lane 循环：付款后核实（到期 run）→ 订单预检（BROWSER_PREFLIGHT）→ 领取下一个排队 Browser 派发并执行；有活立即再转一轮，空闲按 `BROWSER_POOL_POLL_INTERVAL_MS` 休眠；lane 内异常只记录并退避，run 交给租约过期恢复。
- 模式由确认词决定：`I-CONFIRM-RESIDENT-BROWSER-POOL:REHEARSAL`（全部停在点击前，进程与数据库付款开关必须 false）或 `:PAY`（进程开关与数据库开关、执行器 profile 写权限必须同为 true）。不再有每单单号与每单确认词。
- 订单 COMPLETED 后释放身份登录态（`releaseSessionOnComplete`，只清 session/登录 cookie，留设备与 Cloudflare cookie）。
- 单订单版 `production-live-worker.js` 只留到第一笔真实付款完成，之后按 §5.1 删除。


失败处理：付款前失败保留现场（不清表单、不关页、不覆盖登录）；付款后失败进 VERIFYING 或 PAYMENT_UNKNOWN，不重付、不换卡。

删除的旧编排（真实单跑通后同批删）：`production-readonly-worker`、`shared-dry-run-composition`、`frontloaded-p0-integration`、`nonpayment-simulation`、`BROWSER_PREFLIGHT` 任务、三种 target 模式、`executor` 与 `payment-executor` 中重复的填表/报价分支。保留并复用的组件：`bitbrowser-control-runtime`、`session-bootstrap`、`session-identity-probe`、`checkout-observer`、`billing-address-fill`、卡字段填写、payment safety gate、post-payment verifier、`live-post-payment-recovery`。

### 5.1 现有 Browser 代码的删/留清单（2026-09-07 通读后）

| 文件 | 处理 | 理由 |
|---|---|---|
| `payment-executor.js`（BrowserPaymentExecutor） | 留，作为新流程的付款阶段核心 | permit → 付款意图落库 → 单次点击 → 非确认即 UNKNOWN → 付款后核实/20X 交接，资金安全全在这里，且有 MySQL 证明 |
| `live-chatgpt-payment-adapter.js` | 留，成为唯一的「结账页填写+点击」实现 | 已含卡/地址/邮箱一次填完、严格零税重报价、控件形状校验、点击后清卡 |
| `executor.js` 中 292–314 行（paymentHandler 存在时仍先填地址/邮箱并做严格重报价） | 删 | **这是 09-06 真实单没填表的直接原因**：卡未填前等 30 秒零税重报价必然超时，抛 `CHECKOUT_OBSERVATION_FAILED`，adapter 根本没被调用。有 paymentHandler 时 executor 只做非严格观察，填写全交给 adapter |
| `executor.js` 其余（上号、身份探测、页面复用、导航、卡材料租约、非付款观察） | 留，改名为「订单会话」层 | 与付款无关的公共步骤 |
| `session-bootstrap.js` | 留 | 与上号器同一 cookie 规则；「已有会话不覆盖」正确，但要求终态释放时显式清一次 session cookie，否则下一客户会被跳过 |
| `session-identity-probe.js`、`checkout-observer.js`、`billing-address-fill.js`、`nonpayment-card-fill.js`（选择器）、`chatgpt-post-payment-verifier.js`、`live-post-payment-recovery.js`、`bitbrowser-control-runtime.js`、`payment-safety-gate` / `durable-*` | 留 | 组件，无重复 |
| `production-readonly-worker.js`、`production-readonly-config.js`、`shared-dry-run-composition.js`、`frontloaded-p0-integration.js`、`nonpayment-simulation.js`、`BROWSER_PREFLIGHT` 任务、三种 target、`BROWSER_PAYMENT_EXECUTOR_MODE=MOCK` 运行时分支 | 真实单跑通后同批删 | 同一流程的只读/演练分身；新流程用 `stopBefore=SUBMIT` 覆盖 |
| `MockCheckoutPaymentAdapter`、`MockPostPaymentVerifier` | 移到 test 目录 | 只服务测试 |

必须补的两处：换账号/终态释放时清 session-token **及上一账号的全部登录态 cookie**（`oai-client-auth-info`、`oai-client-session-epoch`、callback-url 等；设备与 Cloudflare cookie 保留。09-07 实测只换 session-token 会得到「Could not parse your authentication token」；已实现于 `session-bootstrap`，终态调用点随新流程接入）；付款后凭证刷新（待验证 A2）。

## 6. 五个决定的数据模型

| 决定 | 唯一载体 | 处理 |
|---|---|---|
| 接不接单 | `accept_new_orders` 改为三态：接单并处理 / 接单但暂停处理 / 停止接单 | 吸收 `dispatch_new_recharges` |
| 走哪条路线 | `fulfillment_routes.accepts_new_orders` | 保持；`browser_dispatch_enabled` 由路线推出，删 |
| 用哪个卡台 | `browser_card_source_selections` | 保持；API 固定 HNSKJ；`fulfillment_route_card_sources` 删 |
| 能不能付钱 | `browser_payment_writes_enabled` | 唯一；`executor_profiles.productionWritesEnabled`、`BROWSER_PAYMENT_WRITES_ENABLED` 环境变量、`recharge_dispatch_mode`、灰度许可/授权界面全部废弃；API 路线的 `PROVIDER_RECHARGE_WRITES_ENABLED` 为部署常量，不作日常开关 |
| 能不能开卡补钱 | 合并为 `supply_automation_enabled` | 吸收 `card_auto_replenishment_enabled`、`card_balance_recharge_enabled` |

改为常量或删除：`poll_existing_orders`、`sync_card_transactions`、`card_stock_low_threshold`、`card_replenishment_daily_limit`、全局开卡金额/最低余额（改按产品）。

## 7. 可观测

每单一条阶段时间线入生产库（不放本机文件）；每单记录身份、出口 IP、卡尾号、地址槽位、结果、任何挑战或拒付。速度优化与风险关联都只看这份数据。

## 8. 待验证

- A：结账接口能否在常驻身份内调用。**结论（09-07）**：能，但必须由页面自己的点击发出。裸调 `payments/checkout` 时 Plus 返回 400「unusual activity」（两账号、两身份一致），页面点「Rejoin Plus / Upgrade」同一请求体即 200；拦截对比证明差别只在页面附带的 `oai-device-id`、`oai-web-deployment-attestation`、`openai-sentinel-token` 等头。Pro 5x/20x 裸调 200，但同样改走页面。custom 模式返回 `checkout_session_id` + `client_secret`，无结账 URL；付款表单为页面内嵌 Stripe。证据 `artifacts/poc-checkout-api-20260907/`，分析 `docs/browser-research/IDENTITY_STRATEGY_RESEARCH_2026-09-07.md`。
- A2：付款后凭证刷新路径（下一笔真实单付款前后各探一次）。
- B：Pro 5x/20x 能否免 Plus 直接购买（同一脚本）。**接口层成立**：免费账号可直接创建 chatgptprolite / chatgptpro 结账 → 阶段数按 1 设计；付款是否成功等真实单。已 Plus 账号对 Pro 返回「User is already paid」，升级路径不走此入口，只作备选。
- C：单笔一分钟目标（实测得出）。**首个样本（09-07 演练，含一次会话替换与重新建结账）**：本机 LIVE 进程从领取到停在点击前约 5 分钟（09:29:14 领取 → 09:35:00 收口，其中首跑因安全字段 10 秒超时中断一次，续跑约 2 分钟）；Stripe 支付元素挂载 >10 秒，观察合同已放宽到 45 秒。

## 9. 完成标准

测试账号跑到付款前 → 一笔真实付款 → 删除旧编排 → 本规格按实测修订并冻结。每步完成的标准是旧实现已删除。
