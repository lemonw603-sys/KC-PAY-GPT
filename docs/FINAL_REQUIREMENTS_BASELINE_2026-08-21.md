# 最终需求基线（2026-08-21）

> 状态：用户已确认。历史文档与本文冲突时，以运行事实、本文和 `DECISIONS.md` 中当前有效决策为准。
>
> 对抗式审查见 `FINAL_REQUIREMENTS_ADVERSARIAL_REVIEW_2026-08-21.md`；其中修正方案已获得用户确认。

## 1. 产品与架构

- V1 只做 ChatGPT Plus；目标账号必须是免费账号，当前已是 Plus 时不能充值。
- Pro 5X、Pro 20X 只预留产品扩展，当前不实现。
- 目标规模每天 200–300 单；当前限额是灰度保护，不是最终容量。
- 三端积木架构：可替换卡台适配层、运营后台、执行/充值台。
- API 执行器优先，未来增加 Browser 执行器；两者共用订单、资金栅栏、审计和对账。
- 当前主路线是 HNSKJ + ZZSHU。备用卡台先人工切换，只影响新订单，旧订单保留原路线。

## 2. 付款与 CDK

- 客户通过系统外支付宝/微信付款。
- 生成并交付 CDK 代表该客户已经付款。
- 支持单个生成或针对一批已付款客户批量生成；不建立未付款预生成库存码。
- 新格式为 `PJ-ABCDE-FGHIJ-KLMNO-PQRST`，历史不分组码继续兼容。
- CDK 绑定产品、不绑定价格。
- 后台记录生成、批次、交付、补发、兑换、作废及关联订单，并可由 CDK 反查客户邮箱、时间、卡片、Provider 订单、交易和人工案件。

## 3. 自动履约与资金安全

CDK 兑换后自动履约，不要求逐单人工批准。保留：

- 全局接单/派发急停；
- 单订单唯一资金尝试栅栏；
- Provider 调用和资金尝试账本；
- 外部结果未知时冻结；
- 禁止 API/Browser 重复付款；
- 人工恢复审计。

旧逐单 Permit 只可作为灰度或紧急工具，不再是正常订单前置条件。

## 4. Session 更换

- Session 无效或目标账号已是 Plus 时，原订单进入客户可恢复状态。
- 最多更换 3 次。
- 72 小时从第一次明确的客户可修复 Session/账号错误开始。
- CDK 生成/兑换、订单创建、库存等待和 Provider 内部等待不消耗窗口。
- 只有客户实际提交新 Session 才计一次；系统重试不计数。
- 允许换账号；保留账号变更、时间、次数和结果审计，不长期保留旧 Session 明文。
- 超时或次数用尽后转人工，不重新消耗 CDK。
- 客户只看到自身可处理原因；库存、卡余额和 Provider 内部问题只在后台显示。

## 5. 库存与补卡

合格库存卡必须：

- `active`；
- 未绑定订单；
- 没有客户消费 `PURCHASE` 证据；
- 资料完整；
- 余额达到配置门槛；
- 不存在资金未知、退款争议或隔离原因。

不能用“没有 `CARD_RECHARGE`”判断未使用，因为新卡初始入金本身可能记录为 `CARD_RECHARGE`。

正常订单优先分配合格库存卡。库存不足时订单进入等待补卡，后台提示并通知；人工补卡与自动补卡并存。自动补卡当前每次 1 张、每张 $16、每天最多 5 张；人工开卡不计入自动上限；参数可配置并按规模提高。只统计成功开通且满足库存资格的卡。

## 6. 卡余额充值

HNSKJ 已确认存在 `POST /cards/{id}/recharge`，仅 active 卡、需要 write scope 和稳定幂等键，金额为满足 minRechargeAmount 的正整数 USD；返回 pending 时禁止更换幂等键重打。

- 新开卡通过 `openCardAmount` 一次开足，不额外重复充值；
- 仅已有、未履约、未绑定且余额不足的 active 库存卡调用 recharge；
- 调用写入独立幂等键、Provider 调用、资金尝试和对账记录；
- pending 时查询余额与流水，禁止直接再打一笔。

## 7. 一卡一单与特殊复用

默认一单一卡；已消费或已绑定订单的卡不分配给其他订单，系统不得自动复用。

特殊情况允许运营者人工例外，但必须核实原订单没有进行中/未知调用、继续扣款风险或退款争议，重新核验卡片状态/余额/资料，并记录原订单、新订单、原因、操作者、时间和交易快照。任一条件无法确认时禁止复用。

## 8. 最终成功

最终成功必须同时满足：

1. Provider 支付/开通成功；
2. `is_subscription_cancelled=1`。

支付成功但取消状态未知时进入 `CANCELLATION_PENDING`；长期无法确认则进入 `CANCELLATION_REVIEW_REQUIRED`。客户显示处理中或人工核对，禁止判充值失败或重付。

## 9. 退款与追溯

- 保留卡交易原始同步和历史。
- 不自动识别退款、不发送退款提醒、不自动提取。
- 需要时由运营者建立人工案件。
- 预留原订单、原交易、退款交易、金额、币种、时间、说明和操作记录。

## 10. 当前实现差距

1. HNSKJ 既有卡 recharge 尚未接入 v1；
2. 正常订单仍受逐单 Permit/authorization 限制；
3. 没有原订单更换 Session 接口和可恢复状态；
4. 40030 尚未完整映射为客户可修复原因；
5. 最终成功尚未以取消续费确认为硬终态；
6. 自动补卡触发尚未接入；
7. 库存资格尚未按无客户 PURCHASE/无资金争议完整实现；
8. 特殊人工复用尚无后台受控入口和审计模型；
9. 正式 CDK→订单→Worker 成功订单仍未真实验收。

## 11. 下一步

用户确认的完整顺序为：

1. 订单/CDK/邮箱/卡片追溯与数据中心；
2. Session 可恢复状态与取消确认终态；
3. 正常订单自动履约，移除逐单审批依赖但保留资金栅栏；
4. 库存资格、HNSKJ recharge 和受限自动补卡；
5. 运营后台统一操作中心；
6. 卡台人工切换；
7. 正式成功单、3–5 单和 10–20 单灰度；
8. Browser 执行器与 200–300 单/日规模化。

详细任务和退出条件见 `IMPLEMENTATION_PLAN_FINAL_2026-08-21.md`。Browser 当前可单独窗口设计，但阶段七稳定前不接生产。
