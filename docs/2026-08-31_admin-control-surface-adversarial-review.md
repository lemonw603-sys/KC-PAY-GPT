# 运营后台控制面盘点对抗式复查｜2026-08-31

## 复查范围
复查 `docs/2026-08-31_admin-control-surface-audit.md`，对照当前 `start-business` 实现、两笔真实 API 订单经验、资金栅栏和用户“少操作、稳定优先”的要求。

## 发现与修正

### 1. “开始营业”不是无条件总开关
盘点报告把它描述为主要入口是对的，但没有强调当前实现会在 `available < 1` 时直接拒绝开始营业。若未来补卡/补余额已经可以订单驱动自动恢复，单纯“库存为 0 就不能接单”会把可自愈问题误当成硬阻断。应区分：
- **硬阻断**：数据库/Worker 不可用、默认路线不健康、资金未知案件、必要写权限未配置；必须阻止。
- **可自愈等待**：交易证据过期、可补余额卡、可按日限额自动开卡；系统自动处理并显示预计动作，不要求用户反复点。

当前自动补给写入尚未完成生产级验收，因此本轮不直接放宽 `available < 1` 的门禁；先把状态呈现和动作分类设计清楚。

### 2. “Provider 写入权限放高级区”不能被理解为系统自动打开
该权限涉及真实资金副作用。它应是一次性的生产配置/明确确认，不是每单按钮，也不能因为点击“开始营业”就偷偷打开。开始营业只读取并报告其状态；缺失时给出“去高级设置完成一次配置”的入口。

### 3. 不能把所有同步都承诺为自动解决
交易只读同步已实现自动排队；自动开卡/补余额仍有生产写入验收边界。因此界面必须显示“已自动排队/等待执行”或“尚未启用自动补给”，不能笼统显示“系统会自动解决”。

### 4. “追踪已有订单”和“同步卡片交易”应默认持续，但仍需故障可见
它们不是日常开关；若执行器停止或失败，开始界面应显示阻断原因和跳转入口，而不是隐藏问题。

### 5. Browser 路线不能只看默认按钮
Browser 当前真实付款仍未生产验收。开始界面只能在 Browser Worker、心跳、配置和路线健康都满足时允许切换；否则应明确显示“Browser 尚未就绪”，不能让用户误以为只是普通开关。

## 第一性原理结论
系统的唯一核心目标是：**客户提交后，在不重复扣款和不制造资金未知的前提下，尽快完成充值。**
因此开始界面的决策不应围绕“有多少开关”，而应围绕每个条件的可恢复性：

1. 能自动恢复的，系统自动恢复；
2. 能安全跳转的，给出直接入口；
3. 需要资金或方向确认的，停在确认点；
4. 无法安全判断的，保留订单和资金栅栏，不自动重试/换路。

## “开始营业”检查后的统一处理模型
| 检查结果 | 系统动作 | 用户看到的内容 |
|---|---|---|
| 全部就绪 | 打开接单和派发 | “营业中” |
| 交易证据过期/缺失 | 幂等排队只读同步，短延迟重试 | “正在自动刷新卡片证据” |
| 有可补余额卡且补给执行器已启用 | 排队一次补余额，不重复排队 | “正在补足卡余额” |
| 无卡且自动开卡已启用且未超日限额 | 排队一次开卡 | “正在准备新卡” |
| 自动补给未启用或达到限额 | 不擅自写资金；跳转卡片库存/补给设置 | “需要你处理：补给未启用或已达上限” |
| 默认路线不健康 | 不自动切换路线；跳转卡台路线/默认充值方式 | “当前路线不可用” |
| Provider 写权限未配置 | 不自动开启；跳转高级设置 | “需要完成一次资金权限配置” |
| Browser Worker/心跳不满足 | 不允许切 Browser；保留 API | “Browser 尚未就绪” |
| 未知资金风险/开放对账案件 | 不自动继续、不换卡 | “必须人工核对” |
| 客户 Session 无效 | 订单转等待客户更换 Session | “请客户重新提交 Session” |

## 是否需要调整原盘点
需要小幅修正，不推翻总体方向：
- 保留“日常一个营业入口 + 默认充值方式”；
- 把开始营业从简单二元按钮升级为“检查→分类→自动动作/跳转/确认”的结果页；
- 不删除底层开关，不把资金写权限变成隐式自动动作；
- 当前不因自动补给规划而提前放宽生产库存硬门禁。

本复查只更新设计结论，尚未修改后台代码或生产开关。
