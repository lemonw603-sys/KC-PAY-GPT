# D-414 第二批：API 失败处理规则表（Lemon 已定，D-414 补记十；10-02 增补见第五节）

2026-10-01 UTC 06:3x 起草。前提（D-414 补记一，Lemon 已定）：
- 失败自动换卡**只做 API 路线**（301）；
- 同时满足才换：**原卡核实没被扣款** + **平台明确说失败**；
- 每单最多换 1 次；设置页可关；
- 「失败算不算次数」做成可调项。

## 一、生产证据（只读，2026-10-01 实查）

API 路线一共 15 次尝试：成功 7。失败、关闭的如下，平台付款结果都是 `failed`：

| 时间（UTC） | 卡 | 平台原话 | 这张卡附近的流水 |
|---|---|---|---|
| 08-21 | 1666 | 建单被拒（业务码 40030） | 只有余额退回 |
| 09-01 | 1013 | 卡片被拒，请换卡后重提 | 只有余额退回 |
| 09-02 ×2 | 4643 | 开通超时，请稍后查询是否已到账 | 无 |
| 09-04 | 9051 | 验证策略失败，请稍后重试 | 余额退回、往卡里充钱 |
| 09-04 | 5980 | 验证策略失败，请稍后重试 | 往卡里充钱 |

- 7 次失败都**没有看到这单的扣款**。这几张都是 HNSKJ 卡，每张卡有流水可查。
- highvcc 没有单卡流水接口（D-401），只能看卡上余额 + 账户流水（补钱核对用的是同一套）。
- **平台原话不一定是真原因**：09-26 测试时卡上只有 $1（真原因是余额不够），平台说的却是「该卡交易过于频繁，请稍后再试或换卡」（`contracts/2026-09-26_zzshu-api-changes-since-0917.md`）。

## 二、规则表（提议）

| 类别 | 平台原话举例 | 卡碰到没有 / 扣了没有 | 算不算这张卡的一次 | 自动换卡 | 客户看到 |
|---|---|---|---|---|---|
| ① 建单前就被拒 | 40030 参数、40020 地区、42902 并发过高、40305 维护 | 没碰到卡 | **不算** | **不换**（和卡无关，换了也一样） | 照旧：失败，卡密可重提 |
| ② 平台明说是卡的问题 | 「卡片被拒，请换卡后重提」「该卡交易过于频繁，请稍后再试或换卡」 | 付款请求到了卡上，被拒；**要核实没扣** | **算**（这张卡被拒过，少用它；见三②） | **换 1 次**：核实原卡没扣 → 换一张再提交 | 多等几分钟，成功就不知道换过卡 |
| ③ 账号 / 风控问题 | 「验证策略失败，请稍后重试」 | 问题在客户账号或 OpenAI 风控，不在卡；没扣 | **不算** | **不换**（换了大概率还失败，还多一次被拒） | 照旧：失败，换号或稍后再提 |
| ④ 说不准扣没扣 | 「开通超时，请稍后查询是否已到账」、提交结果不明 | **可能扣了** | 按现状锁卡对账 | **绝不换**（硬规则：付款不明不换卡不重付） | 照旧：锁卡核对，没扣再「放卡退卡密」 |
| ⑤ 没见过的原话 | — | 不知道 | 按现状 | **不换** | 照旧，进「需要我处理」 |

**「核实原卡没扣」怎么做**（②才用）：
- 平台说失败后等约 3 分钟（授权流水有延迟，和补钱核对同一个等法）；
- 原卡余额没少；
- HNSKJ：卡流水里占卡之后没有成功或授权中的扣款；
- highvcc：账户流水里这张卡没有这单的扣款；
- 任何一项拿不到或对不上 → 不换，按现状锁卡核对。

## 三、要 Lemon 定的

1. **哪几类换卡**：提议只有 ②。③「验证策略失败」要不要也换？我建议不换，理由见表。
2. **失败算不算次数，默认值**：提议「付款请求到了卡上（②）算一次，没碰到卡（①③）不算」。设置页可改成「都不算」。
3. **拒付率风险**：
   - highvcc 拒付率已到 10%，平台写的关停线是 5%（欠账 35）。
   - ② 换卡后如果新卡也被拒，拒付又多一笔。真原因不在卡上时（比如商户侧拒），换卡只会多一次被拒。
   - 提议：每单最多换 1 次（已定）；**新卡也被拒就停**，不再试，单子照旧失败。
   - 要不要再加「同一天自动换卡超过 N 次就暂停自动换卡并推手机」？

## 四、不在这批

- Browser 路线不换卡（失败多在付款前页面打不开，换卡没用；点击付款后的不明状态照旧锁卡，D-254 / `SUBMIT_UNKNOWN` 不变）。
- ①里「排队满 / 维护」的自动重试（欠账 22）：Lemon 定的是不加自动重试，这批不动。

## 五、Lemon 已定（D-414 补记十～十二，2026-10-01 UTC）

- 第三节 1、2、3：**同意**。只有 ② 换卡；失败算次数默认「②算、①③不算」，设置页可改「都不算」；新卡也被拒就停。
- 「同一天自动换卡超过 N 次就暂停」：**不加**（Lemon 不同意）。
- **加进这批**（补记十一第 3 条）：API 单失败后，系统自己核实原卡没扣（同上面「核实原卡没扣」的做法），就**自动放卡、退卡密**；只有查不清才推 Lemon。现在是人工在后台点「放卡退卡密」。
- **与第四节「排队满 / 维护不加自动重试」的关系**（补记十二）：这批仍不对同一单自动重试。另做「丙」：第一次出现平台本身的问题（不是卡、不是账号），**新单**切 Browser；卡住的那一单不挪走（平台可能还在扣）。丙的触发条件待 Lemon 确认后写进这里。
- 顺序：第二批排在「API 单处理太久」（甲乙丙）、「点验证就备卡」、「单张卡手动控制」之后。

## 六、补记十三（2026-10-02）：「核实原卡没扣」不固定等 3 分钟

3 分钟原本照搬补钱核对（`card-top-up-service.js:25`，注释写的是「与客户页 3 分钟对齐」），不是实测的卡台延迟。改为：被拒后立刻查一次，之后每 20 秒查一次；**看到这次被拒的记录就换卡**，看不到才等，**最长 3 分钟**。头几次把「多久看到记录」记下来，再往下调上限。未验证：ZZSHU 那边的被拒会不会在卡台留下被拒记录（highvcc 有 $0.10 被拒费流水，CURRENT_STATE「highvcc 收费」行），以及多久出现。
