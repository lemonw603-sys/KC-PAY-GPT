## 1. 现在的逻辑（一张 highvcc Plus 卡从开到删）

1. **开卡**：供卡调度器每 60 秒看一次「可分配卡张数 < 水位」或「有单在等卡」，钱包过得了预检（余额 − $16 − 开卡费 $0.50 ≥ 底线 $20）就开一张 $16 卡。
2. **分卡**：来单时挑一张「合格」的卡：余额与「注资 − 账本已花」两者取小 ≥ $16、用了不到 3 单、没被占用、卡台上还在、没被停用。排序是余额小的、开得早的优先。
3. **付款**：成功后账本记 CONSUMED（金额 $16——来自全局 `default_open_card_amount`，不是实扣 $15.75），卡被标 DEPLETED、余额置空。
4. **每小时快照**：读到卡台余额约 $0.25，把卡改回 AVAILABLE；余额比库里高时（有人手动补过钱）把差额记进注资（D-354）。
5. **结局**：卡剩约 $0.25，永远过不了「≥ $16」，**不会再被分配，也进不了待销清单**（只有「用满 3 单」「DEPLETED」等才进，D-410 补记七）。于是每单开一张新卡，旧卡挂在客户账号里不提醒删。

**现在已经能「手动补钱」**：Lemon 在 highvcc 网页往用过的卡补 $16，下一次快照（≤ 1 小时，或手动跑一次同步）就把 $16 记进注资，卡重新合格。这是 D-354 的现成路径，只是要人手动、有延迟。D-411 要做的是让系统自己在来单时补。

## 2. 做自动补钱，会撞到哪些现有逻辑

| # | 现有规则（护着什么） | 补钱后撞在哪 | 怎么处理 |
|---|---|---|---|
| 1 | **分卡资格要求余额 ≥ $16**（护：钱不够的卡不分出去） | 用过的卡永远不合格，分卡根本不会考虑它 | 分卡时，没有「现成能付」的卡、或按 D-411「用过的优先」时，另查一类**可补钱复用**的卡：除余额外其他条件都满足、用了 1～2 单、卡台支持补钱。补完再走原资格检查（不改原规则） |
| 2 | **账本每单记 $16**（全局 `default_open_card_amount`，不是设置页的开卡金额） | 补少于 $16 会被判「注资 − 账本」不够（D-412 已定每次补 $16 整） | 每次补的金额＝**这一单账本要记的金额**（订单上的 `open_card_amount`，现在 16），并在同一个事务里把注资 +16、余额写成卡详情读到的真值 |
| 3 | **每小时快照把余额上涨记进注资**（D-354） | 系统自己补的 $16 会被快照再记一次，注资翻倍；补钱接口返回前那 10～17 秒里若恰好跑快照，也会重复 | 补钱前先记一条「补钱进行中」，快照导入遇到进行中的卡不做补钱识别；补完由补钱流程自己写注资 |
| 4 | **付款成功把卡标 DEPLETED**（护：付款后余额未知，别再分） | 待销清单把 DEPLETED 当「该去删」——用过 1 单、本该复用的卡会在下一次快照前短暂出现在「该去删」里，Lemon 可能照着删掉 | 待销清单的 DEPLETED 条件改为只对「不能再补钱复用」的卡生效（用满、或卡台不支持补钱）；用满 3 单照旧 `USED_UP` |
| 5 | **水位＝保几张可分配卡**（调度器按库存口径数，含余额条件） | 可复用的旧卡不算数 → 水位 1 时调度器照样开新卡，D-411 省不到钱 | 调度器数「可用卡」时，把「可补钱复用、且钱包补得起」的旧卡也算进去；有这样的卡就不开新卡 |
| 6 | **钱包预检**（开卡：余额 − 开卡金额 − 手续费 ≥ 底线 $20） | 补钱也花钱包的钱；调度器开卡和补钱若同时发生，各自预检都过、合起来跌破 $20 押金 | 补钱用同一个预检（金额 $16、手续费 0）；开卡与补钱对同一卡台的钱包检查串行化（锁卡台那一行） |
| 7 | **推送「钱包不够开下一张卡，还差 $Z」** | 有可复用旧卡时，真正需要的是「够补一次」（约 $36），不是「够开一张」（$36.50）；文案和门槛会不准 | 按实际缺的那一步写：能补就算补的钱；推送白名单不新增类型 |
| 8 | **Browser 付款许可带着卡余额快照**（护：付款前卡的状态不能变） | 如果补钱发生在交给付款池之后，许可会因余额变了而中止 | 补钱必须在交单前完成（分卡阶段），两条路线都在服务器端做完，不碰 browser-mvp（D-254） |
| 9 | **客户页阶段**：分到卡是第 3 步「正在排队」 | D-412 定补钱时显示第 2 步「正在准备支付卡」 | 补钱期间订单用现有状态 `CARD_PROVISIONING`（客户页本来就映射成第 2 步），到账后进 `CARD_READY`；3 分钟提醒不动（补钱只多 10～20 秒） |
| 10 | **一卡同时只服务一单、失败 / 不明保留占用**（CLAUDE.md 硬约束） | 补钱结果不明时，钱包可能已扣、卡上没到 | 补钱不明 → 这张卡锁住不分配、不重补（D-412 幂等规则），这一单改用别的卡或等卡，客户不失败；系统先自动读卡详情 / 账户流水判定，判不清才叫人（进人工兜底合同 + 推送白名单「叫人」类） |
| 11 | **日对账**：卡台扣款笔数 vs 账本 | 补钱不是扣款（highvcc 授权流水里没有补钱），不会造成差异 | 不用改；另可用卡台账户流水（`/api/account/flowPage` 有 Add Balance 记录）核对补钱，属欠账 37 一类，可后做 |
| 12 | **「今天花了」**只算成功单账本 + 开卡费 + 拒付 | 补钱是钱包 → 卡，本身不是花费；每单照样按账本记 $16 | 不用改 |
| 13 | **API 失败放卡**（D-404）：卡被拒类失败约 1 小时内自动放回 | 补过钱的卡放回后卡上有约 $16.25，账本那单 RELEASED 不计 → 直接又合格，不用再补 | 不用改，测试要覆盖这条 |
| 14 | **worker 进程没有卡台写权限**（`PROVIDER_CARD_WRITES_ENABLED=false`，也没有 highvcc 客户端） | 补钱要在 worker 里调 highvcc | ~~给 worker 加一个只管「补钱」的窄权限（systemd 环境变量）~~ **实施时改（D-413 补记四）**：worker 总带 highvcc 补钱客户端，会不会补只由资格规则决定（「自动开卡」总闸 + 能力位 + 钱包够）。环境开关调度器看不见，关着时调度器会把旧卡算成有卡而 worker 不用，客户一直等卡 |
| 15 | **卡台能力标记** `supports_auto_funding`：hnskj 1（旧补余额线留下的）、highvcc 0 | 若按这个标记笼统判断「能补」，会误把 hnskj 算进来（hnskj 补钱接口本方没接） | 能不能补＝标记为 1 **且**该卡台有补钱适配器（只做 highvcc）；迁移把 highvcc 置 1，hnskj 的标记保持但因为没有适配器不生效 |

## 3. 设置页：要不要加设置项

**结论：不需要新增设置项。** 补钱用到的每个数，现有设置里都有：

| 补钱需要的数 | 用哪个现有设置 | 现值 |
|---|---|---|
| 允不允许自动补 | 「自动开卡」总闸 `card_auto_replenishment_enabled`（D-412 补记三：不新增开关） | 开 |
| 哪个卡台能补 | 卡台能力 `supports_auto_funding` + 有适配器 | 迁移后 highvcc 1 |
| 一张卡最多用几次 | 每卡单数（Plus 3） | 3 |
| 补完至少要有多少 | 最低余额（Plus） | $16 |
| 每次补多少 | 这一单账本记的金额（订单 `open_card_amount`，来自全局 `default_open_card_amount`） | $16 |
| 钱包至少留多少 | 钱包底线 | $20 |
| 每天最多补几次 | 不设：每单最多补一次（按订单唯一）、每张卡最多补「每卡单数 − 1」次，再加钱包底线兜底 | — |

**但有三处要改显示或说明**（页面改动先给演示）：
1. **水位的意思变了**：从「保几张新卡」变成「保几张随时能用的卡（新卡 + 能补钱复用的旧卡）」。数字不用改，标签说明要改。
2. **工作台「剩 N 张 · 能充 N 单」**现在不数用过的卡，补钱后要把可复用的旧卡算进去，最好标出「其中 N 张要补钱」。
3. **有两个「开卡金额」，页面只显示一个**：设置页那格（按卡台 × 产品，highvcc Plus $16）只决定**新卡里放多少钱**；每单账本记多少、每次补多少，由页面上看不到的全局 `default_open_card_amount`（$16）决定。现在碰巧相等。如果以后只改设置页那格（比如改成 $17），新卡会是 $17，但账本和补钱仍按 $16——不会出错，只是两处不一致、看不出来。建议把全局那个值在设置页只读显示出来，或者让两者统一（要不要统一，Lemon 定）。

## 4. 按业务流程走一遍（客户任意时间来、运营不在场）

1. 客户凌晨提交 → 分卡：先找「用过 1～2 单、能补钱」的卡（D-411 用过的优先），找不到再用新卡，都没有就等卡（调度器开新卡）。
2. 选中旧卡 → 同一个事务里占住卡、记账本预留、记「补钱进行中」、订单进 `CARD_PROVISIONING`（客户看到「正在准备支付卡」）。
3. 调一次 highvcc 补 $16（不重发）→ 读卡详情直到到账（实测 10～17 秒，最多等 5 分钟）→ 注资 +16、余额写真值、补钱记录完成、订单进 `CARD_READY` → 往下走 API（ZZSHU 建单）或 Browser（交池子），与现在完全一样。
4. **分支**：
   - 补钱接口明确拒绝（没动钱）：放开这张卡，本单改用新卡或等卡；这张卡不算坏卡。
   - token 失效：补不了，本单改用现成新卡或等卡；token 推送照旧（一段失效期只推一次）。
   - 钱包不够补：跟现在「钱包不够开卡」一样推一条，本单等卡。
   - 超时 / 结果不明：卡锁住、不重补；系统自动读卡详情和账户流水判定；判不清推「叫人」类提醒；本单改用别的卡，客户不失败。
   - 服务器在补钱中途重启：「补钱进行中」的记录重启后按「结果不明」走同一条判定，不会重补。
5. 付款成功 → 第 3 单付完 → 用满 → 待销清单「用满」→ Lemon 手动删（剩约 $0.75 删卡时全额退回钱包，D-412 补记三流水实证）。

**需要人在场的步骤**：只有「补钱结果不明、系统自己判不清」这一种，会推手机；其余全部无人值守。

## v2（2026-09-30）整体影响地图：逐处读代码后的结论

**做法**：把 v1 / 脚本里所有读写卡余额、卡状态、账本、资格规则的地方全搜出来（`eligibleInventoryCardSql` 14 个文件、`stockCountingCardSql` / `countEligibleCards`、`ledgerSpendSql`、`maxPaymentsSql`、`detectTopUp`、`walletPreflight`、账本预留 / 转移 13 个文件、`UPDATE cards` 25 处），逐处读。v1 版 §2 的 15 条之外，**新发现 8 处**（下表带 ★）。

### 一、补钱这一单怎么走（业务流程，客户任意时间来、运营不在场）

1. 客户提交 → 分卡：先找「用过 1～2 单、卡台支持补钱、没被占、卡台上还在、没停用、没跑过 Pro」的 Plus 旧卡；有就用它（旧卡优先），没有就用现成新卡，都没有就等卡（调度器开新卡）。
2. 选中旧卡：同一个数据库事务里——占住卡、账本预留这一单、登记一条「补钱：待发」、订单进 `CARD_PROVISIONING`（客户页「正在准备支付卡」）。
3. 另一个任务**只发一次**补 $16 请求，登记「已发」；再排一个每 3 秒查一次卡详情的小任务（不占着 worker）。
4. 卡详情显示到账 → 注资 +16、余额写真值、补钱登记「已到账」、订单进 `CARD_READY` → 往下走 API（直充建单）或 Browser（交付款池），和现在完全一样。
5. 异常：卡台明确拒绝（没动钱）→ 放开这张卡，本单改用新卡或等卡；token 失效 / 钱包不够 → 同上并按现有推送叫人；超时或结果不明 → 卡锁住不重补，系统读卡详情 + 账户流水（`/api/account/flowPage` 有 Add Balance 记录）自动判定，判不清推手机，本单改用别的卡；服务器中途重启 → 按登记状态接着查，不重补。
6. 第 3 单付完 → 用满 → 待销清单提醒删；删卡时卡上余额自动退回钱包（D-412 补记三流水实证）。

### 三、核对过、不受影响的

- 推送「卡台余额变化必推」只管 hnskj（`card-provider-snapshot-service.js` 只写 hnskj；最近 4 条全是 hnskj），highvcc 补钱不会多推。
- hnskj：本方没接它的补钱，$50 卡本来就一卡三单。5X / 20X：每卡 1 单，永远不走复用。
- 下单入口只查执行器心跳和直充点数，不查卡（`order-intake-repository.js:43,57`）。
- 放卡路径（D-404 失败放卡、换 Session 放卡、人工核实没扣款）：补过钱的卡放回时约 $16.25，直接可用。
- 日对账（数卡台扣款笔数，补钱不是扣款）、今日花费（按账本记）、每周自检的账外扣款检查。

### 四、业务上可能出的问题

- 补钱到付款那约一分钟里，前面用过这张卡的 1～2 个客户点升级 / 买点数能扣到钱（D-411 已接受，概率小）。
- 同一张卡给 3 个不同账号付款：历史上 Browser 路线 3118 / 1657 / 3159 各 3 单、5371 2 单，API 路线 1652 2 单，都成功（生产账本实查）；卡台对「一卡多冲」有没有额外风控规则，没查到。
- 拒付率：补过钱的卡不会因「钱不够」被拒；10% 的现状由 Lemon 去问客服。
- 卡月费：一张卡跨月用满会多交一次 $0.10（很小）。
