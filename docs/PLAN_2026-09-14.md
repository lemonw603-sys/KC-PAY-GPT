## 2. 路线选择：Browser 主线，API 顶班

D-217 的审查结论：ZZSHU 把我们的卡和客户 Session 拿去做的是同样的浏览器自动化，
**失败时零原因**（响应只有 `status: failed`）。它不会变好，因为我们改不了它。
Browser 今天已有 stage、「找到几个」、现场保留，死点缩到一个函数三种可能。**能改进的那条才配当主线。**

但 Browser 现在 36%，Lemon 每天要接手一半的单。所以：

- **API 这几天顶着接单**（它今天 95 秒跑通一单），减少人工
- **Browser 在夜间无单时段用 rehearsal 拿诊断、修死点**——不停生产，不占白天
- Browser 达到"连续 5 单"后转正；API 退回"供应商还在时的应急"

**止损点**：Browser 修完当前死点后再跑 10 单，若成功率仍 < 60%，**重新评估**——那说明失败模式是发散的，不是收敛的，届时要么接受 API 的黑盒，要么换架构（提链）。这个判断到时候由数据说话。

## 7. 这份方案自己的弱点（写在这里，免得下次审查时才发现）

- **"连续 5 单"是 Lemon 定的标准，但没定"多长时间内"**。4 单/天的量下，攒 5 单要一两天；若中间夹一单失败就重来。建议改成"最近 10 单 ≥ 9 成"。
- **A5 依赖 rehearsal 能复现死点**。rehearsal 用的是 Lane 3 窗口和一个演练账号，与真实客户单的账号状态不同（免费试用、历史绑卡）。**可能复现不了。** 若两晚复现不了，改用真单——那时至少诊断存库已上线，一次失败就够。
- **API 顶班期间的失败没有诊断**。这几天若 API 失败，只能人工。这是接受的代价。
- **大脑今天的时间估计全部偏乐观**（D-211）。表里"1 周"按经验该乘 1.5。
