# 全项目对抗式审查（2026-08-22）

## 目的与证据边界

本审查不是只审自动补卡，而是把当前项目的产品规则、CDK、订单、Session、库存、卡台、Provider、资金账本、后台、Browser 和生产状态一起复核。

证据优先级：运行/生产事实 > 测试和数据库迁移 > 当前代码 > 规划文档。无法由当前证据证明的内容不写成“已完成”。

## 一、已确认的正确方向

1. V1 只做 Plus；Pro 5X/20X 仅预留，不进入当前充值实现。
2. 目标账号已经是 Plus 时不能充值；上游 ZZSHU 已真实返回 40030 拒绝。
3. 客户通过系统外支付宝/微信付款；生成并交付 CDK 代表已付款。
4. CDK 绑定产品、不绑定价格；格式和批次、交付、作废、补发、订单追溯已形成数据底座。
5. Session 更换按原订单进行，最多 3 次，窗口 72 小时；系统重试不消耗次数。
6. 客户只看到自己的可处理原因；库存、卡余额和 Provider 内部问题留在后台。
7. 正常订单目标是自动履约，不要求逐单人工确认；结果未知时必须冻结，禁止换卡或重付。
8. 最终成功必须同时满足支付成功和取消自动续费确认。
9. 一卡一单是默认规则；已消费或已绑定卡不自动复用，特殊复用只能人工、二次核验并完整审计。
10. 整体架构仍是可替换卡台 + 运营后台 + API/Browser 执行台；当前不做自动卡台故障切换。

## 四、方向、逻辑和体验方面的盲区

### P0：必须纠正

#### 1. Plus 资格判断与 API 路径的边界需要纠正

业务规则要求“目标账号当前为 Plus 时在本地尽早拒绝”，但当前旧 API 路径只有 Provider 提交后的 40030 反馈。虽然本次真实 40030 没有产生外部订单号，也没有证据表明发生扣款，但它仍然意味着系统在未完成本地账号资格确认前已经进入 Provider create 流程。

API 本身就是充值动作，因此 API 路径不应为了 Plus 再增加独立账号探测。正确边界是：Provider 在充值请求中明确返回 40030 等充值前拒绝时，系统保留 Provider 调用和资金尝试审计，清除本地资金风险，把原订单转为客户可恢复的 Session 状态，不删除账本、不重复提交、不换卡；只有结果未知时才进入 UNKNOWN 并禁止任何回退重付。Browser 路径仍可在同一 Context 的必要只读页面步骤中判断账号状态，但不能把它强加到 API 路径。

#### 2. 阶段四代码与生产状态不能混写

阶段四新增迁移 029/030、自动补卡和卡余额账本目前只在代码和隔离数据库验证，尚未生产部署。生产报告、后台展示和交接文档必须继续明确“未上线、未产生资金写”，否则接手模型可能误以为已经具备生产补卡能力。

### P1：必须在下一轮灰度前解决

1. 卡余额充值必须补齐：执行器、Provider call、幂等、pending 查询、余额/交易确认、未知结果人工恢复。
2. 每日补卡上限后台配置必须加入受保护写入、今日用量/剩余展示、旧值/新值/操作者/时间审计。
3. 自动补卡当前写死旧 HNSKJ 账户 ID；在实现卡台切换前必须明确“当前单 Provider 限制”，不能假装已经支持备用卡台。
4. 特殊人工复用必须在后台完成原订单风险核验、卡片重新同步、二次确认和历史归属；不能提供简单的“释放卡片”按钮。
5. 正式成功灰度前必须使用目标账号不是 Plus 的测试账号，验证支付成功、取消自动续费、Provider 订单、卡交易、余额和资金账本一致。

### P2：规模化前解决

1. 卡台人工切换只影响新订单，旧订单必须固定原路线并可追溯。
2. Browser 只能接入现有订单/卡片/资金栅栏，不能形成第二套订单或资金账。
3. 350 单等效仿真不能替代并发竞争和连续 24 小时 soak；在 200–300 单/日目标前仍需补齐。
4. 后台总览必须区分客户问题、库存问题、资金未知、Provider 故障和人工案件，不能把所有失败都归入同一状态。

## 六、审查结论与执行顺序

当前没有发现需要推翻整体“三端积木架构”的证据；但不能进入真实自动开卡或卡余额充值，直到以下顺序完成：

1. API 路径采用 Provider 充值响应作为资格判断，完善明确拒绝的本地回退和审计；Browser 路径再单独验证同 Context 的必要只读资格步骤，不把两者混成一个独立预检接口；
2. 完成每日补卡上限后台配置、用量和审计；
3. 完成卡余额充值执行器及 pending/unknown 对账；
4. 完成人工特殊复用和卡台人工切换底座；
5. 用免费目标账号完成一笔受控成功单，验证取消自动续费和全链路账务一致；
6. 对以上改动再做一次独立对抗式审查，确认无 P0/P1 后才进入 3–5 单灰度。

本报告不把“代码测试通过”写成“生产成功”，也不把“研究/仿真完成”写成“Browser 真实充值完成”。
