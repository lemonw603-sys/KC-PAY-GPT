## 0. Lemon 的需求，一句话

**客户拿到 CDK 就等于付了钱，剩下的系统自己走完；运营只做三个选择（哪条路、哪个卡台、接不接单），只在系统真的解决不了时被叫。系统要简洁、稳定，不要花里胡哨。**

## 2. V2 的中心思想：CDK 驱动

V1 是**功能驱动**——每个功能一块积木。V2 是 **CDK 驱动**——一切围绕客户一次购买的生命周期，六个面各管一段。（D-219 审查把中心从「订单」改为「CDK」：订单是尝试，CDK 才是购买；chenxing 那 12 单在 V2 里是一个 CDK 的 12 次尝试。）

```
                         ┌─────────────┐
                         │    CDK      │  ← 唯一真相：客户的一次购买
                         │ (一次购买)   │     D-219：1 个 CDK 平均 1.43 单、最多 12 单
                         └──────┬──────┘     订单只是 CDK 下的一次尝试
                                │ 1..N 次尝试
       ┌──────────┬─────────────┼─────────────┬──────────┬──────────┐
       ▼          ▼             ▼             ▼          ▼          ▼
    展示面      执行面        资源面        控制面     通知面      对账面
   (客户页)   (执行器)      (卡供给)       (后台)     (告警)    (账本vs卡台)
```

- **展示面**只读 CDK 的交付状态，不知道路线、不知道第几次尝试
- **执行面**是可插拔接口（submit / verify / cancelRenewal），两种实现（API / Browser），CDK 不知道用的哪个
- **资源面**按执行器分池（卡台不同），但管理方式一套
- **控制面**是三个开关 + CDK 生成 + 需要我队列 + 今日订单表，一页工作台
- **通知面**按类别决定推不推，不按数量
- **对账面**每日自动比对账本与卡台，差异进"需要我处理"队列

**今天的事故对照这个图，每一个都是某个面越界了：**

| 事故 | 越界 |
|---|---|
| chenxing 12 单被当 12 个陌生单 | 订单不认 CDK——12 次尝试被当成 12 次购买 |
| 切 API 卡在等卡 | 控制面不知道资源面的状态 |
| 客户看到"可重兑"时运营正在接手 | 展示面、控制面各看各的 |
| 你一天做了 8 种后台操作 | 控制面暴露的是功能，不是订单 |

## 3. 六个面的 V2 边界

### 3.1 执行面：一个接口，两种实现

```
interface RechargeExecutor {
  submit({ attempt, card, session, product, fromPlan })   → { status, evidence }
  verify({ attempt })                                      → { plan, activated }
  cancelRenewal({ attempt })                               → { cancelled }
  // 交付 = 三段都成功（D-219 发现 2：成功一单在生产里是 PAYMENT_SUBMIT →
  //   PAYMENT_CONFIRMED → PLUS_ACTIVATED → CANCELLATION_CONFIRMED 四步，
  //   原稿只写了第一步）。每段可独立重试、独立标 UNKNOWN。
  // submit 的 status ∈ SUCCESS | FAILED_BEFORE_PAYMENT | UNKNOWN_AFTER_PAYMENT
  // FAILED_BEFORE_PAYMENT 必须带 stage + diagnostic
}
```

- **APIExecutor**：包 ZZSHU。它零原因，接口层把它的 `failed` 统一映射成 `FAILED_BEFORE_PAYMENT { stage: 'provider', diagnostic: null }`——**诚实地标"不知道"**
- **BrowserExecutor**：现有 52 模块收进来。它已经有 stage/诊断
- **切换**：`fulfillment_routes.accepts_new_orders` 已有；V2 加**切换前校验**——目标执行器的卡池有可用卡、执行器健康——不满足就拒绝并说原因。**这是"一键切回"的全部含义：一键，且不会切到一个跑不起来的地方**
- **切换必须解耦卡台**（D-219 发现 5）：今天 06:36 Lemon 切一次路线，后台 7 秒内同时动了路线和卡台两条记录——运营看到一个按钮，背后是两个耦合开关。V2 把卡台做成执行器自己的属性：切路线不动卡台；要换卡台是另一个明确的操作
- **5X/20X 的两件事**在接口里是两个参数：`product`（充哪个套餐）和 `fromPlan`（当前是什么）。Free→5X 和 Plus→5X 走同一个接口，执行器内部按 `fromPlan` 决定走"新订阅"还是"升级"

### 3.2 资源面：按执行器分池，管理一套

```
卡池 A (hnskj)    ──▶ APIExecutor    （绑死合理：API 是那家做的）
卡池 B (highvcc)  ──▶ BrowserExecutor（可接任何卡台，已有 browser_card_source_selections）
                       ↓
              统一管理：库存阈值 · 自动开卡 · 余额同步(5min) · 缺卡告警 · 账本推算
```

- **自动开卡**：highvcc `openCard` 去掉人工确认词，改为"库存 < N 张就开一张"，每天上限由设置定。**200 单/天 = 67 张/天，这条不自动化其余全白做**
- **余额口径**：MIN(同步余额, 账本推算)——代码已改好但**不能直接发**：D-218 实跑发现它会把「手动补过钱的卡」判成不可分配（`funded_amount` 不随补余额更新，`1652` 卡上 $50 被判 −16）。**先由 Lemon 在 D-218 三选一**（补钱时抬 funded_amount / 放宽规则 / 放弃补钱只开新卡），再发
- **矛盾五**（两个卡台能否共用）：**待 Lemon 与大脑一起测**。技术上 ZZSHU 接受任何卡号；业务上是否允许未知

### 3.3 控制面：从基线 5 页收成 4 页（Lemon 开放调整后，按真实使用量重排）

三周实际操作分布：**CDK 生成 53 次（最高频）**、付款开关 19 次、其余零星。基线的"首页 + 订单"
在实际使用里是同一件事——看订单、处理需要我的——所以合并：

| 页 | 内容 | 对应今天的操作 |
|---|---|---|
| **工作台** | 顶部：三个开关（接单 / 路线 / 卡台）+ **CDK 生成按钮**（最高频，不该在二级页）· 中间：**需要我处理**队列 · 下面：今日订单表（客户、产品、阶段、卡、停留、需要我做什么） | 每天打开只看这一页 |
| **CDK** | 单码列表 · 作废 · 按批次筛选 | 作废、查某个码 |
| **卡片** | 两个池并列：库存、余额、开卡、导入 | 开卡、看余额 |
| **设置** | 三个决定的默认值 · 每卡几单 · 最低余额 · 按产品开卡金额 | 改阈值 |

**诊断 / 审计 / 对账明细 → 折叠成"高级"入口**，日常导航不出现。对账的**结果**不折叠：差异直接进"需要我处理"队列（§3.6）。

**"需要我处理"队列是控制面的核心**：只放系统真的解决不了的事——付款结果不明、人机验证、缺卡且自动开卡失败、同一客户连败 N 次。**其余一律不进队列，不推手机。**

### 3.4 展示面：四态 + 一个时间承诺

```
处理中（预计 X 分钟）        ← X 按最慢的执行器 + 一次重试算（Lemon 定：留足时间）
需要你重新提供登录信息       ← WAITING_FOR_SESSION（D-219 发现 4：客户必须行动的状态不能并进"处理中"）
已开通                       ← CDK 交付完成
没成功，请联系客服            ← 终态失败；不再显示"卡密可重兑"，由客服判断
```

九阶段圆环**降级为内部诊断视图**，客户不看。理由：它按 Browser 的阶段画，API 路线 95 秒就完，两条路体验完全不同——而你定了"客户不感知路线"。

### 3.5 通知面：只在需要人时响

现有 18 类告警收成 **4 类**，且**推不推手机由类别决定，不由数量决定**（D-219 发现 3：两天 77 条告警推了 76 条，真需要人的只有 10 条；而唯一没推的 `CARD_STOCK_EMPTY` 恰是最该推的）：
- **需要你**：进"需要我处理"队列的那几种——付款结果不明、人机验证、同一 CDK 连败 N 次——**推**
- **供给**：缺卡、开卡失败、余额低于阈值——**推**，单独通道，不可静音
- **资金异常**：重复扣款、账本与卡台交易对不上——**推**，最高优先级（原稿漏了这类）
- **信息**：提交、成功、同步、余额变化——**只进后台，永不推**

### 3.6 对账面：账本 vs 卡台，每日自动（原稿漏了，Lemon 明确要的"基础对账能力"）

现状：`card_transactions` 41 行、12 张卡、最近同步 09-14 11:39；`card-consumption-audit.js` 是只读比对，**从未接进任何流程**。
V2：每日一次自动比对「消费账本」与「卡台交易记录」，差异进「需要我处理」队列，并作为"资金异常"告警的唯一数据源。
**不做**：三方对账、退款自动识别（基线已定不做；`refund_cases` 代码引用仅 3 文件 7 行，与对账零交集，可删）。

## 5. Browser 迁服务器：路径与前提

**前提未验证**：BitBrowser Local API 绑在本机 `127.0.0.1:54345`，**项目从没调研过它有没有 Linux 版**。`chrome-control-runtime.js` 是 headless 但**没有代理、指纹、扩展**，是测试用的。

两条路：
- **路 1**：BitBrowser 有 Linux 版 → 装服务器，代码几乎不改
- **路 2**：没有 → 给 `chrome-control-runtime` 补代理（mihomo 已能在服务器跑）+ 指纹 + 上号器扩展，等于重做 runtime 层

**放在 V2.2**，前提是先调研 BitBrowser。在此之前，Mac 必须开着——这是 V2.0/V2.1 期间接受的约束。

## 8. 这份方案的弱点

- **接口统一要动付款路径**，是全系统最敏感的地方。缓解：先在 Browser 侧做（它已有 stage/诊断），API 侧只包一层，不改 ZZSHU 调用
- **后台 4 页是重做不是改**，2366 行前端要重写。缓解：先做工作台一页，其余三页沿用 V1 直到 V2.1
- **5X/20X 的 `fromPlan` 逻辑没有真实样本**——D-138 之前决定不做升级，是因为"业务量很小"。V2.1 做之前要 Lemon 确认现在业务量是否支持
- **"连续 N 天不求助"依赖大脑在场记录**，V2.2 之后大脑可能不在场，那时要换成后台自动统计
