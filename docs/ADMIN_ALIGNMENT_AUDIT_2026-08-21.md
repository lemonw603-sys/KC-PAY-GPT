# Plus 运营后台与最终方案对齐审查（2026-08-21）

> 审查范围：当前仓库中的生产 v1 后台页面、后台 API、服务层、状态机、Worker、MySQL 迁移和自动化测试；并对线上 `ops.vibebridge.top` 做无登录只读核验。
>
> 对齐基线：`FINAL_REQUIREMENTS_BASELINE_2026-08-21.md`、`DECISIONS.md` 当前有效决策。
>
> 本文只报告事实与差距，不修改业务代码，不把“已有表/接口”写成“后台已经可用”。

## 1. 证据与验证边界

### 已直接验证

- 线上 `/health/live` 返回 `{"status":"ok"}`；
- 线上 `/health/ready` 返回 `{"status":"ready"}`；
- 未登录访问 `/api/v1/admin/overview` 返回 HTTP 401；
- 线上 `/admin/assets/admin.js` 与当前本地 `v1/public/admin/assets/admin.js` SHA-256 完全一致，说明本次审查的前端脚本就是线上正在提供的版本；
- 本地全量测试：283 项，262 通过、0 失败、21 跳过；跳过项均因未配置 `TEST_DATABASE_URL`，不能当作本轮生产数据库实测。

### 本轮没有验证

- 没有使用已登录后台会话，因此没有读取生产订单数量、当前开关、卡片数量和 Provider 账户配置；
- 没有执行生成 CDK、开卡、卡充值、直充、退款或余额提取；
- 后台 HTML 登录后页面以当前同版本静态代码为依据，交互结果没有再次逐按钮目视验收。

## 2. 当前后台已经具备的能力

### A. 登录与操作保护（已实现，方向一致）

- 服务端后台 Session；
- 登录限流；
- Cookie/同源保护；
- 敏感操作 step-up 密码复核；
- 生成/下载/作废 CDK、开卡、充值放行等写操作分级保护；
- 操作事件和 Provider 调用审计基础。

判断：底座保留，不与最终方案冲突。

### B. 总览、订单和异常（已实现，部分需要改口径）

已实现：

- 总览指标、最近订单、Worker 心跳、过期租约、滞留 Provider 调用；
- 订单分页、状态筛选；
- 按订单查询码、CDK、邮箱、ChatGPT 账号 ID、外部订单号查询；
- 订单详情：状态、客户、卡片、任务、事件、Provider 调用、交易、取消续费字段；
- 异常队列；
- 三方资金证据核对案件；
- CSV 安全导出。

与最终方案的冲突：

- 总览仍有“待确认充值”“需要你逐单确认”；
- 订单筛选仍有 `AWAITING_CONFIRMATION`；
- 详情仍以人工 Permit 为正常付款入口；
- 成功率仍按出现 `RECHARGE_SUCCESS` 事件统计，没有把 `is_subscription_cancelled=1` 作为最终成功硬条件；
- 没有 `WAITING_FOR_SESSION`、`CANCELLATION_PENDING`、`CANCELLATION_REVIEW_REQUIRED` 的正式状态和展示。

### C. CDK 管理（核心已实现，交付操作只完成后端）

已实现：

- Plus CDK 单个/批量生成；
- 新分组格式和历史无分组格式兼容；
- 批次列表；
- 恢复下载、原始批次下载、逐码状态报告；
- 作废未兑换 CDK；
- 兑换后关联订单；
- 订单搜索支持 CDK；
- 数据库只保存 HMAC，恢复副本独立加密；
- 已有 `cdk_delivery_events` 和 `POST /api/v1/admin/cdks/deliveries`，支持 DELIVERED / RESENT / DELIVERY_FAILED。

差距：

- 当前后台页面没有“登记已交付/补发”的操作入口；交付 API 只有测试和服务端能力，正常运营页面没有调用它；
- 页面明确允许“生成但尚未交付”，系统无法证明生成前客户已经付款；
- 当前 CDK 状态仍以 AVAILABLE / REDEEMED / REVOKED 为主，没有直接的 ISSUED 业务状态；交付事实位于独立事件表；
- 因此“CDK → 客户交付/补发 → 订单”的追溯只完成了数据底座，没有形成完整后台操作闭环。

判断：不是重做 CDK；应把现有 delivery API 接到后台，并让生成/交付操作符合“只针对已付款客户”。

### D. 卡片库存与手动补卡（主要底座已实现）

已实现：

- HNSKJ 卡片列表发现；
- 新卡隔离、两次稳定快照验证和人工接管；
- 卡片完整资料加密；
- 卡台目录、卡段、费率、账户余额、额度快照；
- 卡片库存列表、完整卡号、余额、交易和同步状态；
- 可配置低库存阈值；
- 低库存后台告警；
- 订单优先原子分配库存卡；
- 库存为空时订单安全等待，`ASSIGN_CARD` 每分钟重试，最大尝试数 10080；
- 人工创建付费开卡任务；
- 开卡幂等、费用/余额/额度预检、单活跃任务和中断隔离；
- 取消未提交订单时，可在严格条件下人工释放卡片回库存。

与最终方案的差距：

- 低于阈值只告警，不会自动创建“1 张、$16”的开卡任务；
- 没有“每天最多自动 5 张”的自动计数和硬上限；
- 人工开卡和自动开卡尚无独立统计口径；
- 库存为空时订单内部仍保持 `CREATED`，客户只看到 QUEUED；没有显式 `WAITING_FOR_CARD` 状态；
- 可用卡 SQL 只检查 AVAILABLE、active、余额、卡资料和未绑定，没有排除历史成功客户 `PURCHASE`、资金未知或退款争议；
- 低库存统计部分查询没有统一带最低余额条件，不同页面/服务的“可用卡”口径可能不同；
- 当前人工“取消并释放卡片”是一个已存在的特殊复用入口，但只证明直充未开始、卡片新鲜且余额达标；没有明确检查卡交易 PURCHASE、退款/拒付争议，也没有独立复用审批记录。

### E. 卡片余额充值（缺失）

- HNSKJ 官方已有 `POST /cards/{id}/recharge`；
- 当前 `HnskjCardProvider` 没有 recharge 方法；
- 后台没有卡片补余额按钮/API；
- 没有卡充值幂等键、pending 状态、资金尝试或余额/流水对账链。

判断：最终方案中已确认，但后台目前完全没有实现。

### F. 正常充值执行（资金底座强，但业务入口冲突）

已实现并应保留：

- Provider 账户/路线绑定；
- 订单冻结 fulfillment route；
- 进程写开关、数据库派发开关、Provider 账户 write_enabled；
- recharge_attempts 资金尝试；
- ACTIVE / UNKNOWN / SETTLED 资金围栏；
- Provider 调用意图先持久化；
- `SUBMIT_UNKNOWN` 禁止自动重付；
- API 与未来 Browser 共用栅栏的数据基础；
- ZZSHU 创建、轮询和取消续费复查。

确定冲突：

- `recharge_attempts` 创建前强制要求有效 `recharge_authorization_items`；
- Worker 没有授权就拒绝 Provider 调用；
- 后台要求逐单或批量人工签发 10 分钟许可；
- 页面文案反复强调“真实充值仍需逐单确认”。

判断：不要删除资金围栏；应把“人工授权记录”改造成“系统策略自动产生正常履约授权/意图”，后台人工 Permit 降级为灰度/紧急工具。

### G. Session 与客户错误（缺失）

当前：

- 只在订单创建时保存 Session；
- 客户状态 API 仅返回 QUEUED / PROCESSING / REVIEWING / SUCCESS / FAILED；
- 不返回客户可理解的失败原因；
- 没有原订单替换 Session 的 API；
- 没有替换次数、首次可修复错误时间、72 小时截止时间和账号变更审计；
- Provider 40030 会落入普通充值失败路径。

判断：与最终方案直接冲突，是下一次真实成功单前的 P0。

### H. 最终成功与取消续费（部分实现，终态错误）

已实现：

- ZZSHU 状态读取 `is_subscription_cancelled`；
- 支付成功后创建取消续费复查任务；
- 未确认时重试；
- 尝试耗尽后设置 `cancellation_review_required`；
- 后台详情展示“等待确认/需要人工处理/已取消”。

冲突：

- Worker 在 Provider 返回 success 时立即把订单改成 `RECHARGE_SUCCESS`；
- 取消确认只是成功后的附加字段，不阻塞成功；
- 客户会在取消确认前看到 SUCCESS；
- 没有 `CANCELLATION_PENDING` 独立状态。

判断：基础调用已经有，不需要重写 Provider；需要调整状态机、成功率口径和客户映射。

### I. 退款（实现内容超过最新需求）

当前代码会：

- 同步卡交易；
- 对明确 refund 类型自动分类；
- 自动创建/更新 `refund_cases`；
- 自动写 `REFUND_CANDIDATE` operator alert；
- 更新卡片 `refund_status`；
- Bark outbox 会处理这些运营告警。

最终规则是：

- 保留原始交易同步；
- 不自动识别退款；
- 不自动提醒；
- 人工建立和处理案件。

判断：这是确定冲突。应停用自动 candidate/alert 路径，但保留表结构、历史记录和人工案件能力。

### J. 卡台人工切换（数据基础已完成，后台入口缺失）

已实现：

- `provider_accounts`；
- `fulfillment_routes`；
- 订单创建时解析并冻结路线；
- 旧订单不会因默认路线变化而改写；
- Provider 账户 write_enabled 门禁。

缺失：

- 后台没有 Provider 账户/路线管理页；
- 没有人工选择“之后的新订单使用哪个卡台/路线”的 API；
- 没有切换前健康、余额、卡段、权限检查；
- 没有切换操作审计页面。

判断：架构正确，操作闭环未完成。

## 4. 我的判断

后台不需要推倒重做。约 60%–70% 的运营与资金安全底座可以保留；主要问题是它仍服务于旧的“小批量、逐单人工放行、自动退款观察”模式。

正确改法是：

1. 保留认证、step-up、订单/卡/CDK/交易/核对、Provider 路线和资金围栏；
2. 替换正常订单的人工 Permit 入口，不删除资金栅栏；
3. 增加客户可恢复状态和 Session 更换；
4. 将取消续费确认并入最终成功；
5. 接入卡充值和自动补卡；
6. 停用自动退款候选/提醒；
7. 补齐卡台人工切换、CDK 交付和特殊卡片复用的后台入口。

## 5. 建议开发顺序

### P0：下一次真实成功单前

1. `WAITING_FOR_SESSION` + 更换 Session API/页面；
2. 40030/Session 无效客户原因映射；
3. `CANCELLATION_PENDING`，取消确认后才 SUCCESS；
4. 正常订单自动创建资金尝试，取消逐单人工审批依赖；
5. 保证 provider_calls 与 recharge_attempts 一一关联。

### P1：下一轮小批量前

1. HNSKJ 卡 recharge；
2. 库存资格统一：无客户 PURCHASE、无资金未知、无退款争议；
3. 自动补卡 1 张/$16/每日 5 张；
4. 停用自动退款 candidate/alert；
5. CDK 交付/补发后台入口；
6. 受控人工释放/复用入口和审计。

### P2：容灾与规模化

1. 卡台/路线人工切换页；
2. Browser 执行器；
3. 3–5 单、10–20 单容量灰度；
4. 根据销量将自动补卡上限从 5 张逐步提高；
5. 200–300 单/日限流、延迟、余额和失败率验收。
