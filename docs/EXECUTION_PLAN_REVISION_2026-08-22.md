# 执行规划修订（2026-08-22）

## 结论

不修改已确认的业务方向：V1 只做 Plus；订单、CDK、卡片、运营后台和资金账保持唯一核心；Browser 是未来主执行链路；不自动跨订单复用、不自动故障切换、未知结果不重付。

需要修改的是**执行顺序、阶段退出条件和完成状态口径**。原因是本轮横向审查发现：阶段四/Browser 代码与生产 release 尚未对齐，卡台实时凭据尚未重新核验，且若干关键运维动作仍只有代码没有生产闭环。

## 修订后的执行顺序

### R0：生产只读基线（已完成）

只读核对 `/opt/pojia/current`、systemd、迁移版本、关键运行开关、任务/租约/资金未知数，以及 HNSKJ profile/balance/card-types/cards。保存脱敏证据；不做任何 Provider 写调用。

退出条件：生产 release、数据库和卡台只读状态有同一份现场证据；已于 2026-08-22 满足。生产写入仍保持关闭。

### R1：可重建交付与事实源收敛

整理并提交 Browser 工作树；把当前代码已实现但旧文档仍写“未实现”的 HNSKJ recharge 改为“代码/隔离测试完成，生产未验证”；把历史报告标为历史快照。固定可重建提交和部署清单。

退出条件：从一个明确提交可以重建当前 v1/Browser 测试结果，文档不再出现当前状态冲突。

### R2：关闭 v1 生产前 P0/P1 缺口（写开关继续关闭）

1. 核验每次 Provider 调用与 `recharge_attempts` 资金账的关联；
2. 将自动补卡/自动开卡调度从固定旧 account ID 改为按 Provider account/route（已完成代码，待测试/部署核对）；
3. 补齐 HNSKJ card detail、refresh-balance、withdraw 的运行时 Schema 校验；
4. 增加 UNKNOWN 卡余额充值的后台人工对账结论动作，禁止直接重付（已完成代码，待生产部署）；
5. 完成卡台 Provider account/路线人工切换基础，切换只影响新订单，旧订单保留原路线。

退出条件：危险状态可审计、可恢复，且不需要人工 SQL。

### R3：阶段四安全部署（只读/非资金写）

部署库存等待、自动补卡参数展示、卡余额风险总览、只读队列和后台追溯能力；保持开卡、卡充值、直充和 Browser 付款写开关关闭。完成后台现场验收和数据口径核对。

### R4：共享链路受控验收

在上游仍可用且用户单独确认时，用符合规则的免费账号完成一笔正式 API 成功单，验证 Plus 激活、取消自动续费、卡交易、余额、本地订单和资金账一致性。若 API 路线不可用，不把失败伪装成完成，直接记录为历史兼容路线未闭环并转向 Browser 共享底座验收。

### R5：Browser 非付款真实观察

先完成真实但不付款的 BrowserContext/Session/Checkout 观察。菲律宾 sticky 出口到位后，新增独立 PH cohort；此前 NON_PH 结果只能作为功能基线，不能晋级生产。

### R6：Browser 受控付款与放量

通过 cohort 对抗审查后，才进行 1 单、3–5 单、10–20 单灰度；未知结果必须对账，不重付。连续 soak、并发队列和容量证据通过后，才讨论 200–300 单/日。

## 明确延期事项

- 特殊卡跨订单人工复用入口；
- Browser 真实付款；
