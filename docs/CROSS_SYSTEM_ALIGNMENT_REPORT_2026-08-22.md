# 运营后台、充值系统、卡台系统横向对齐报告（2026-08-22）

## 1. 审查范围和证据边界

本报告对照了：

- 当前 `v1` 运营后台、客户充值 API、Worker、Provider 适配器和数据库迁移；
- HNSKJ 卡台 API 合同、当前 HNSKJ 适配器和卡片库存同步代码；
- ZZSHU 直充 API 合同、当前直充适配器和订单状态机；
- Browser 控制面代码与 Browser 当前基线；
- 生产发布记录、阶段验收报告和当前工作树。

本轮没有发起新的真实开卡、卡充值、直充、提现或 Browser 付款请求。因此外部平台的“当前实时可用性”仍须以现场只读请求重新确认。

本次追加的只读运行时核验记录见 [`LIVE_RUNTIME_AUDIT_2026-08-22.md`](./LIVE_RUNTIME_AUDIT_2026-08-22.md)：公网 Web 两端的 live/ready 均返回 HTTP 200，运营后台未带会话访问按预期跳转登录；生产 release、数据库和 HNSKJ 当前凭据仍未由本地工具现场核对。

## 2. 结论先行

三套系统的**数据模型和主要业务方向基本对齐**，但**生产状态没有对齐到最新代码**：

- 运营后台最新阶段四页面和接口在代码中已经存在，但生产仍是阶段三 release；
- 充值系统已经具备 API 自动履约底座和 Browser 离线控制面，但正式成功订单和 Browser 真实付款未验收；
- 卡台适配器已经有开卡、既有卡 recharge、卡详情、余额、交易和提现方法，但 recharge 真实写入未验证，卡台人工切换尚未接入；
- 订单路线模型支持 Provider account/route 固化，但低余额补卡调度器仍写死一个旧 HNSKJ account ID，这与未来可切换卡台架构尚未完全对齐；
- 部分历史文档曾把已完成或已修正的事项写成未完成，本轮已修正主要事实源，但历史快照仍需明确标注。

## 3. 运营后台：已做、没做、需要改

### 3.1 已完成（代码/测试；部分已有生产安全部署）

- 管理员登录、Session、step-up、敏感写保护和域名隔离；
- 总览、订单列表、订单详情、状态筛选、CDK/邮箱/账号/外部订单号搜索；
- CDK 批次生成、下载、逐码状态、交付、补发和作废；
- 卡片库存、待验证新卡去重、卡片同步、卡台目录快照；
- `WAITING_FOR_CARD`、低库存提示和运营告警；
- 自动补卡每日上限配置、今日使用量/剩余量和设置修改审计；
- 对账案件列表、分配、解决和安全 CSV；
- 卡余额充值风险总览；
- 卡余额充值只读详细队列，可按 `PENDING`、`UNKNOWN`、`MANUAL_REVIEW` 等状态查看；
- Browser 运行、租约、artifact 和人工控制的脱敏追溯视图。

### 3.2 尚未完成

- UNKNOWN 卡余额充值的后台人工恢复/对账结论动作（代码和增量迁移已完成，尚未生产部署）；
- 特殊卡跨订单复用的核验、二次确认、原/新订单关联和交易快照；
- Provider account/履约路线的人工切换页（后端只读列表、健康门槛、单路线切换和审计 API 已实现，前端页面与生产部署未完成）；
- 卡台健康、余额、卡段、写权限检查与切换审计；
- 卡余额充值 Runner 的生产注册、后台操作和现场验收；
- 生产环境阶段四页面和接口部署。

### 3.3 已发现的后台问题

- 历史后台审查文档曾把每日上限入口、卡余额充值和 Session 能力写成缺失；当前代码已完成这些部分，文档已补校正，但旧报告仍是历史快照；
- 后台只读队列目前展示卡余额充值状态，但不负责完成 UNKNOWN 的最终人工结论；不能把“能查看”写成“能处理”；
- 后台已有路线/Provider 数据基础，但没有真正的人工切换操作中心；
- 总览中卡余额风险统计与订单 `recharge_attempts` 风险统计是两个不同来源，运营界面必须继续保持标签区分，不能合并成一个含义不明的“资金风险”。

## 4. 充值系统：已做、没做、需要改

### 4.1 客户充值 API 和 Worker

已完成：

- CDK 原子兑换、订单创建、Session 加密保存；
- 订单、任务、租约和有界重试；
- 正常模式自动履约；
- 单订单唯一资金 attempt；
- Provider 调用和资金栅栏；
- 结果未知锁定；
- 40030 映射为 `TARGET_ACCOUNT_ALREADY_PLUS` / `ACCOUNT_ALREADY_PLUS`，回到原订单 Session 可恢复状态；
- Session 最多 3 次、72 小时窗口；
- 取消自动续费未确认时不进入最终成功；
- 客户页轮询直到终态；
- 客户只展示客户自身可行动原因。

未完成或未验证：

- 符合规则的免费账号正式成功单；
- 正式成功单的 Provider 订单、卡交易、余额、取消续费、本地成功状态和资金账一致性；
- 真实 `SUBMIT_UNKNOWN`；
- 新卡真实开通链路；
- 3–5 单灰度和 200–300 单/日容量。

### 4.2 API 直充 Provider

- ZZSHU 仍保留为旧 API 兼容路线；不再作为 Browser 新链路依赖；
- 真实 40030 已验证；
- 创建接口没有调用方幂等键，因此本地唯一 create intent 和 UNKNOWN 锁定是硬边界；
- API 路径不增加独立套餐预检，40030 由 Provider 充值响应作为权威拒绝；
- Provider 成功只是入队，最终成功仍需状态查询和取消续费确认。

### 4.3 Browser 充值

已完成的是控制面和离线/隔离仿真，不是生产充值：

- WAL、lease、artifact vault、订单/attempt 映射、dispatch queue、后台追溯和隔离 Worker shell 已有代码；
- 菲律宾 Session/sticky 出口、真实页面观察、真实 Browser Worker、真实付款、连续 soak 和灰度均未完成。

## 5. 卡台系统：已做、没做、需要改

### 5.1 当前适配器能力

`HnskjCardProvider` 当前代码包含：

- `/account/profile`；
- `/account/balance`；
- `/card-types`；
- `/cards`；
- `/cards/{id}`；
- `/cards/purchase`；
- `/cards/{id}/recharge`；
- `/cards/{id}/refresh-balance`；
- `/cards/{id}/transactions`；
- `/cards/{id}/withdraw`。

开卡和 recharge 都要求稳定 `X-Idempotency-Key`，金额按正整数 USD 校验；PENDING 不允许换 Key 重打。

### 5.2 卡台方面尚未证明的事实

- 相同开卡幂等键重放的真实响应行为；
- 新卡开卡成功、失败、超时和卡 ID 恢复的生产样本；
- 既有卡 `/cards/{id}/recharge` 的真实写入成功、PENDING 和 UNKNOWN 样本；
- 真实交易、退款、余额回退和提现关联；
- 当前生产 API Key 的实时可用性。

历史合同曾记录同一 HNSKJ Key 后台显示有效但 `/account/profile` 返回 401；后续生产记录又写卡片只读同步正常。这是凭据/时间层面的证据冲突，必须通过当前只读请求重新确认。

### 5.3 当前卡台代码问题

- `card()`、`refreshBalance()` 和 `withdraw()` 路径现已补上对象形状的运行时 Schema 校验，并有隔离测试；生产 release 是否包含该修复仍需 R0/R1 现场核对。字段级业务解释仍由后续 mapper 负责，未知字段不会被猜测为成功。
- 自动低余额补卡和自动开卡调度现已按当前 Plus `fulfillment_route` 解析 HNSKJ card Provider account；代码有隔离测试覆盖，尚未生产部署。`card-stock-service` 仍保留 legacy 默认 account 作为显式兼容入口，真正启用多卡台前必须要求调用方传入已选 account，不能依赖默认值。
- 卡台切换基础数据模型已存在；后端切换 API 已增加健康检查、确认词和审计事件，余额/卡段现场检查、后台 UI 和生产部署仍未完成。

## 6. 三套系统之间的对齐关系

| 联动关系 | 当前状态 | 结论 |
|---|---|---|
| CDK → 订单 | 已联通 | CDK 绑定产品，订单保存套餐和追溯关系 |
| 订单 → 卡片 | 已联通 | 订单固定路线，卡片一单一卡；特殊复用未完成 |
| 订单 → Provider account | 已建模 | 正常充值 attempt 使用冻结路线；低余额补卡调度器仍有固定 HNSKJ 例外 |
| 卡片 → 卡台 | 已联通 | 卡台 ID、Provider account、余额和交易同步均有字段/任务 |
| 充值 attempt → Provider call | 已联通 | API 资金账与 Provider 调用有唯一关联；卡余额账也有独立关联 |
| Provider 成功 → 取消续费 | 已建模 | 隔离测试通过，正式生产成功单未验证 |
| 卡交易 → 订单/成本 | 已联通 | 交易、成本和追溯底座存在；真实成功订单一致性未验证 |
| 后台 → 上述数据 | 部分联通 | 订单/CDK/库存/对账较完整；UNKNOWN 人工恢复和卡台切换缺口存在 |
| Browser → 现有订单资金账 | 已设计/部分落盘 | 控制面和 MySQL 映射存在；真实 Browser Worker 未接入 |

## 7. 必须修改的优先级

### P0

1. 阶段四代码、后台页面、卡余额 Runner 与生产 release 明确分离；生产部署前不能开启任何资金写开关。
2. 重新核对当前 HNSKJ API Key 的 profile/balance/card-types/cards 只读可用性；结果写入当前合同和生产事实源。
3. 整理并提交 Browser 工作树，形成可重建提交；未提交文件不能作为部署证据。

### P1

1. 完成卡余额 UNKNOWN 人工恢复和对账案件关联；操作只能改变审计状态，不能直接重付。
2. 将低余额补卡调度改为按冻结的 Provider account/route 选择，不再依赖固定旧账户 ID。
3. 为 HNSKJ 卡详情、余额刷新、提现补齐运行时 Schema 校验。
4. 完成 Provider account/卡台人工切换页、健康/余额/卡段/写权限检查和审计。
5. 用免费目标账号完成正式成功单，核对充值、取消续费、卡交易、余额和资金账。

### P2

1. 特殊卡复用后台入口；
2. Browser 真实但不付款观察；
3. 并发/24 小时 soak；
4. 3–5 单灰度；
5. 200–300 单/日容量。

## 8. 最终判定

三套系统的**业务目标和主要数据模型已对齐**，但**实现、部署和真实运行证据还没有完全对齐**。当前不能说“运营后台、充值系统和卡台已经整套完成”。准确表述是：

> 运营后台与充值系统的基础链路已完成较多代码和隔离验证；卡台适配器已覆盖主要 API；生产写入仍关闭；卡台充值、正式成功单、人工恢复、卡台切换和 Browser 真实充值仍未完成或未验证。
