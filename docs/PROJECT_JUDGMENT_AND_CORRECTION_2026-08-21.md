# 项目判断、纠偏与未来路线（2026-08-21）

> 本文是基于本轮重新检查源码、部署文件、规格、测试和历史聊天后的判断稿。事实、纠偏和建议分开写；未替代正式决策。

## 一、这次检查到底做了什么

上一条回答不是“刚刚把每个外部系统重新打通一次”，而是把当前代码、已有真实测试证据和历史文档合并提炼。本轮重新做了三类核对：

1. 重新扫描当前 `v1` Web、Worker、脚本、迁移、后台接口、部署单元和测试；
2. 重新读取 2026-08-16 至 2026-08-21 的相关 Codex 会话，核对项目从浏览器方案转为 Provider API 方案的过程；
3. 把“代码存在”“本地测试通过”“真实 Provider 调用”“生产真实订单”“未来规划”分开，不再混写。

## 二、项目的实际定位

项目不是单纯的后台页面，也不是单纯的卡片工具，而是一个订单编排系统：

```text
人工生成/交付 CDK
  → 客户提交 CDK + ChatGPT Session
  → 订单与卡片分配
  → HNSKJ 卡台卡片读取/开卡
  → ZZSHU Plus 直充
  → 结果轮询
  → 自动续费取消确认
  → 卡交易、失败、退款和对账留痕
```

v1 的产品范围是 Plus；目标账号必须是免费账号，目标账号已经是 Plus 时不能充值。

本轮进一步确认的长期架构是三块积木：

1. **可切换的卡台适配层**：当前卡台、未来备用卡台；旧订单固定原路线，新订单可切换；
2. **运营后台**：唯一的数据中心和操作中心，管理订单、库存、CDK、授权、告警、审计和对账；
3. **执行/充值台**：API 执行器与浏览器自动化执行器，统一接收后台任务，共用订单状态和资金尝试栅栏。

因此，MVP 不是只追求“当前 API 能跑”，而是要在不增加重复业务逻辑的前提下，为每天 200–300 单保留切换、恢复、审计和扩展能力。

## 三、历史方向变化及判断

### 已确认的有效方向

- 初始浏览器/上号器思路后来被 Provider API + 自有订单/Worker/审计系统替代；v1 已隔离旧浏览器、Stripe、hCaptcha 和代理运行时。
- HNSKJ 负责卡片，ZZSHU 负责直充；两者不是同一个系统。
- 一卡一单、资金不确定时禁止自动重试、成功后确认取消续费，这些是合理且应保留的安全边界。
- CDK 由后台人工生成、人工交付；需要批次作废、补发和完整可追溯记录。

### 已被后来需求纠正的旧方向

1. **“寻找支持当前 Plus 账号的 Provider”是错误方向。** 真实 ZZSHU 40030 已证明目标账号当前为 Plus 时应拒绝，不应换 Provider 绕过。
2. **“永久逐单人工确认充值”不符合当前业务目标。** 它适合上线前资金保护，但不适合客户付费后自动充值和 100–300 单/日目标。应改成规则/批次授权 + 全局急停 + 单订单资金围栏。
3. **“库存不足只等待人工补卡”已不再是最终方向。** 当前需求是人工补卡和阈值自动开卡并存。代码已有开卡脚本/Runner，但自动触发尚未接通。
4. **“客户只看到笼统 FAILED”不符合当前要求。** 客户原因和内部原因必须分层；库存不足不能作为客户责任展示。
5. **“卡网”目前不是已确认系统。** 当前代码只识别 HNSKJ 卡台和 ZZSHU 直充，没有独立卡网 API 适配器。

6. **关于卡片余额充值的前次表述需要纠正。** 项目接口合同确实记录了 HNSKJ Open API `POST /cards/{id}/recharge`；但 v1 适配器/脚本目前没有实现或真实调用它。根目录 `对接api.md` 的 `/bank-cards/{id}/balance` 是另一套 legacy `/pay` 合同，不能据此宣称 HNSKJ 充值已接通。当前准确结论是“有文档接口，尚未实现/验证”，不是“没有 API”。

7. **备用卡台先人工切换。** 适配层保留可替换边界；后台人工切换只影响切换后的新订单，既有订单固定原路线，暂不实现自动故障转移。

## 四、当前系统是否合理

### 合理的基础

状态机、任务租约、Provider 调用审计、幂等开卡、资金围栏、敏感信息加密、库存卡并发分配、交易证据和对账结构，整体方向合理，足以作为 V1 的技术底座。

### 必须纠正的结构性问题

1. **免费账号校验缺失**：没有无副作用的账号套餐预检；当前在 ZZSHU 创建阶段才知道 40030。
2. **自动充值机制缺失**：Worker 的提交路径仍要求 `recharge_authorization`，和“客户已付款后自动执行”冲突。
3. **自动补卡机制缺失**：低库存只告警，未自动建立预配置开卡批次。
4. **客户失败原因缺失**：客户 API 只返回有限状态，不返回可理解原因。
5. **同单 Session 更换能力缺失**：当前没有替换 Session 的客户接口；Plus/无效 Session 时是否允许原订单继续，需要明确业务规则后实现。
6. **正式成功链路尚未完成验收**：已有独立 Provider 成功 PoC，但正式 CDK→订单→Worker→成功→取消续费的非 Plus 真实订单仍未验证。

## 五、我的执行判断

当前不应继续堆页面或直接放量。正确顺序是：

### 阶段 0：事实基线

冻结当前生产写入；完成 API、数据库、systemd、Caddy、备份、告警和 Provider 账户的逐项状态表。“卡网”已确认是口误，不属于系统范围。

### 阶段 1：先修业务正确性

- 核实 Provider 文档中是否有免费账号无副作用预检；
- 40030、Session 无效、卡片问题、库存不足分别建内部原因；
- 设计同一订单 Session 更换/补偿规则；
- 客户只看到自己的原因，不看到卡片库存和内部资金信息。

### 阶段 2：实现混合库存

- 可用余额低于配置阈值时自动创建预配置开卡批次；
- 保留人工补卡入口；
- 单活跃批次、余额/额度门禁、幂等键、失败隔离和 Bark 告警必须保留；
- 只统计成功开通且达到最低余额的卡。

### 阶段 3：把人工 Permit 改成安全自动化

- 正常订单自动执行；
- 全局停止开关、Provider 账户写开关、产品/路由能力门禁、余额围栏继续保留；
- `SUBMIT_UNKNOWN`、资金风险和外部状态不明时自动锁定并人工处理；
- 不再要求每个订单人工点击确认。

### 阶段 4：真实验收

使用目标账号确实不是 Plus 的测试账号，完成一单完整成功链路，并验证：订单成功、ZZSHU 外部订单、HNSKJ 卡交易、余额变化、自动续费取消和本地资金账本全部一致。

### 阶段 5：小批量到规模化

先 1 单，再 3–5 单，并发从 1 逐级增加；稳定后再接近每天 100–300 单。规模化前必须有库存自动补充和可行动告警。

## 六、当前最重要的结论

现在真正的问题不是“项目有没有做”，而是：

> 技术底座已经有了，但业务规则、自动化策略和当前实现还没有完全对齐。

因此下一步应优先做**规则和执行机制纠偏**，而不是继续把现有代码包装成“已经完整可运营”。

## 七、本轮补充核对的细节

### 1. 卡台替换

历史讨论已经明确：卡台必须可替换。当前 Foundation v2 的代码已按“供应商账户 + 环境 + 不可变履约路线”建模：新订单可以切换到新的卡台账户，历史订单保留原路线；不能把已有订单运行中强行改到新卡台。这个设计比单纯修改一个 Provider 名称更安全。

当前事实是：**替换模型已经存在，完整的真实换卡台演练尚未完成**。后续验收必须验证新账户接单、旧订单继续查询、卡片归属不串、凭证和写开关隔离。

### 2. 浏览器自动化

历史决策 D-019 已确认浏览器充值是下一阶段能力，不是 v1 当前生产路径。当前仓库没有浏览器充值执行器接入；旧浏览器模块被隔离。未来浏览器和 API 必须共享同一订单级充值尝试资金围栏：API 结果未知时禁止自动切浏览器，浏览器付款后崩溃也禁止自动重付。

### 3. CDK 是否可追溯

当前代码已经可以追踪：

```text
CDK 批次 → 单个 CDK 状态 → 兑换订单 → publicNo → 客户邮箱/账号 → 卡片 → Provider 订单/交易
```

并支持批次状态清单、作废、失败订单补发和订单详情反查。CDK 投递事件表和 API 已存在，但依赖独立的 `CDK_DELIVERY_HMAC_KEY_BASE64` 配置；当前后台界面主要展示批次和兑换状态，投递/补发记录的操作界面还不完整。因此结论是：**数据库/API 层基本可追溯，后台可视化和交付记录闭环仍需补齐**。

### 4. “总览”是否被取消

没有证据表明总览被取消。当前代码仍注册 `GET /api/v1/admin/overview`，后台仍有“总览”页面和指标卡；Git 历史显示总览最初由 `ea4168e feat: add protected read-only operations dashboard` 引入，后续 Foundation v2 继续使用。之前报告没有展开总览字段，不等于总览被删除。

### 5. 新需求与旧判断的冲突处理

处理原则：用户后来明确表达的业务目标优先于早期“暂缓/默认”方案，但安全不变量不能被顺手删除；正式文档要等确认后再改，不能静默覆盖。

| 旧记录 | 新要求 | 判断 |
|---|---|---|
| D-006/D-008：手动开卡为默认、自动开卡暂缓 | 未来人工补卡和阈值自动开卡并存 | 当前阶段仍手动；未来扩展为混合库存，不矛盾，只是范围升级 |
| D-009：充值保留资金闸门、自动策略预留 | 客户付款后自动充值，不逐单确认 | 机制冲突；保留资金围栏/急停/未知锁定，取消逐单点击，改规则或批次授权 |
| D-013：API 与 Browser 共用充值尝试栅栏 | 未来增加浏览器自动化 | 完全一致，必须保留 |
| D-016：退款识别提醒 | 最新要求：不做识别和提醒，人工处理，只留追溯点 | 直接冲突；以最新明确要求为准，正式决策尚未改写 |
| D-019：浏览器下一轮实现 | 用户再次确认未来要加浏览器自动化 | 一致，当前只预留边界，不接入生产 |
| D-001/D-022：v1 Plus、目标账号必须免费 | 用户再次确认 v1 只做 Plus、当前 Plus 禁止 | 一致 |

### 6. 目前发现的遗漏需求

以下不是替用户做决定，而是代码/历史对照后仍缺少明确规则的项目：

1. 卡台替换时新订单切换的生效时间、旧订单保留多久、旧卡台是否只读；
2. Plus/Session 无效后，原订单允许更换 Session 的次数、有效期和后台权限；
3. 自动补卡每批数量、开卡金额、每日金额上限、最低余额和并发上限（当前暂定 1 张、$16、每日 5 张）；
4. 自动充值的授权粒度、全局急停、单订单异常锁定和人工恢复条件；
5. 客户可见错误的最终文案和错误码映射；
6. CDK 投递记录的后台展示、补发记录、发送渠道和接收人标识；
7. 客户购买付款本身是否在本系统发生，以及付款成功如何与 CDK/订单关联；当前代码主要从 CDK 兑换开始，没有内置客户支付网关；
8. 浏览器执行器使用哪种运行环境、是否独立 Worker、人工介入点和结果未知处理；
9. 100–300 单/日对应的延迟目标、并发、Provider 限流和失败率上限；
10. 只有一个管理员时，密码轮换、step-up、操作审计和紧急接管方式；
11. Plus 之外的产品准确命名与产品代码。当前明确提到的是 Plus、Pro 5X、Pro 20X，历史文字中出现过其他名称，不能直接混用。

## 八、本轮用户确认后的更新

- 客户通过系统外支付宝/微信付款；后台生成 CDK 即视为已付款，CDK 是进入履约的业务凭证。
- 原订单 Session 失效时允许更换，最多 3 次，且只能发生在没有充值资金影响之前；窗口初始建议 72 小时、可配置。该窗口针对 Session 更换，不是 CDK 过期时间；CDK 兑换记录仍归属于原订单。
- 卡台备用的现实原因包括无法开卡、API 失效和卡片无法完成付款；备用卡台面向新订单容灾，API 执行器优先，浏览器自动化执行器后续开发。
- 自动补卡当前参数为每次 1 张、每张 `$16`、每天最多 5 张；人工开卡不计入该自动上限。
- 自动库存的核心条件为：卡片 `active`、未充值、未绑定订单、卡资料完整；余额门槛暂时保留。
- HNSKJ 文档存在既有卡片充值接口，但当前 v1 尚未实现或实测；因此不能设计成“系统已经能自行补卡余额”。在完成接口核验和资金安全验收前，最低余额门槛仍是必要的工程约束。
- 充值执行顺序确定为 API 优先；浏览器自动化属于后续开发的第二执行器。
- CDK 记录必须在运营后台可查，并能通过 CDK 反查订单的大部分业务情况。
- Pro 5X、Pro 20X 暂不实现充值，先稳定 Plus，未来再扩展产品代码和路线。
