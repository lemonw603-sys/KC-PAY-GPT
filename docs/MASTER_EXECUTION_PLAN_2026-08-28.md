将此前分散的路线图、库存简化、一卡多充和 Browser 计划收敛为一份执行主线。它不改变已确认业务规则，只统一顺序、依赖和验收门槛。

- API 真实订单 `PJV1-FqFnMiSKBtLGN14GyP7W` 已成功并完成取消续费；使用卡 `1477/6807`。该订单完成时本地交易同步滞后于 Provider。

- Browser 控制面、租约、恢复、仿真和非付款测试已完成部分；Browser 独立 adapter、非付款端到端联调和真实页面付款尚未完成。

## 不可改变的业务边界

1. V1 只做 Plus；Pro 5X/20X 后置。
2. API 与 Browser 共用订单、卡片、attempt、资金栅栏和消费账本。
3. 外部结果未知不得重付、换卡或换执行器。
4. 历史订单、交易、退款和审计证据不删除。
5. 这是个人内部系统：优先稳定、顺畅和资金安全；只做必要的信息保护，不建设过度复杂的隔离架构。
6. 真实生产写动作和真实 Browser 付款必须单独确认。

## 主线与并行线

### 主线 A：运营后台与库存收敛

#### A1 卡片运营策略（当前最高优先级）

- 在 `cards` 上采用最小字段表达：正常、Claude 专用、永久停用及原因/时间。
- 同步逻辑不能覆盖运营策略。
- 资格查询必须带产品维度，并继续检查余额、资料新鲜度、绑定、消费账本、Provider 交易和资金争议。
- 不把尾号写死成未来永久白名单；未来新卡按实时证据接管。

验收：8590/失效批次不可分配；4744 不进入 Plus；6807 不因运营标记绕过消费/余额规则。

#### A2 库存最小模型

- 先只读盘点，再收敛后台主视图，再软停用，最后才评估极少量物理清理。
- 主视图只保留“可分配、使用中、暂不可用、永久停用”；余额不足、资料待刷新、同步失败显示为原因。
- Provider 对账、发现批次、同步层级等低价值指标下沉到详情/审计页。
- 不删除真实卡、订单、交易或审计数据。

#### A3 消费账本与对账

- 保留“付款前预留→成功 CONSUMED→明确未提交才 RELEASED→UNKNOWN/付款后失败 RECONCILIATION”。
- Provider 成功交易用于确认/补账，不作为唯一实时计数来源。
- 8590 历史消费事实与账本主键回填分开处理；无主键证据不自动回填。

### 并行线 B：Browser 自动化

1. 接入独立 Browser adapter，共享唯一 attempt/资金栅栏。
2. 完成非付款端到端联调和故障注入：租约丢失、崩溃、页面漂移、数据库重启、付款前安全退出。
3. 验收零付款、零重复提交、零资金残留、未知状态只核对不重付。
4. 完成真实运行环境/Session 的非付款观察和必要的菲律宾 sticky cohort；不把 NON_PH 结果外推为生产结论。
5. 通过后才申请一单受控真实 Browser 付款，再逐步扩大。

## 执行阶段

### 阶段 1：当前修复（先做）

- 实现最小卡片策略字段和产品感知资格查询。
- 加入同步覆盖保护。
- 为 8590/失效批次、4744、6807 和真实订单同步滞后增加测试。
- 本地与隔离 MySQL 验证。

### 阶段 2：库存后台收敛

- 只读盘点并生成分类清单。
- 收敛后台主视图和原因展示。
- 增加软停用入口和审计，不做物理删除。
- 生产只读复核。

### 阶段 3：Browser 非付款联调（与阶段 1/2 并行）

- 接 adapter、跑 dry-run 和故障注入。
- 保持所有生产写开关关闭。
- 形成 Browser 交叉验证报告。

### 阶段 4：受控生产验证

- 先确认备份、readiness、无活动 UNKNOWN/资金风险、开关状态。
- 单独确认后才写入卡片运营状态。
- API 成功订单小批量复验；Browser 真实付款另行确认，不自动连带开启。

### 阶段 5：放量前验收

- 3–5 单逐单核对，再 10–20 单受控并发。
- 完成费用快照/变化监控、异地备份和恢复演练。
- 通过重复付款、资金差异、失败率和延迟门槛后，才考虑 100–300 单/日。

## 当前不做

- 自动跨订单复用卡片；
- 自动退款识别、提醒、提取；
- 卡台自动故障切换；
- Pro 产品；
- 微服务、复杂策略中心或额外敏感信息隔离层。
