## 主线与并行线

## 窗口分工（最小并行）

- **统筹/后端主窗口**：负责生产事实核验、Provider 卡运营覆盖、统一库存资格、后台库存简化、集成测试、合并审查和最终部署判断。
- **既有 Browser 窗口**：只负责 Browser adapter、非付款联调、故障注入和 Browser 证据；使用独立 worktree/分支，禁止自行修改库存业务规则或真实付款。

- Browser 分支成果必须先由统筹窗口核对基线、提交、测试和共享合同，再合入 main；不得从 Browser worktree直接部署生产。

### 主线 A：运营后台与库存收敛

#### A1 卡片运营策略（当前最高优先级）

- 用一个最小 Provider 卡运营覆盖结构表达正常、产品专用、永久停用及原因/时间；它必须能覆盖已进入 `cards` 和仍在 discovery 的卡，不建设独立策略服务。
- 同步逻辑不能覆盖运营策略。
- 资格查询必须带产品维度，并继续检查余额、资料新鲜度、绑定、消费账本、Provider 交易和资金争议。
- 不把尾号写死成未来永久白名单；未来新卡按实时证据接管。

验收：8590/失效批次不可分配；4744 不进入 Plus；6807 不因运营标记绕过消费/余额规则。

#### A2 库存最小模型

- 先只读盘点，再收敛后台主视图，再软停用，最后才评估极少量物理清理。
- 主视图只保留“可分配、使用中、暂不可用、永久停用”；余额不足、资料待刷新、同步失败显示为原因。
- Provider 对账、发现批次、同步层级等低价值指标下沉到详情/审计页。
- 不删除真实卡、订单、交易或审计数据。

#### A3 消费账本与对账

- 保留“付款前预留→成功 CONSUMED→明确未提交才 RELEASED→UNKNOWN/付款后失败 RECONCILIATION”。
- Provider 成功交易用于确认/补账，不作为唯一实时计数来源。
- 8590 历史消费事实与账本主键回填分开处理；无主键证据不自动回填。
