# Browser 真实订单测试方案对抗式复查｜2026-09-04

## 结论

方案方向正确，但原方案有三处需要收窄，避免把“计划”说成“当前可执行事实”。

## 复查结果

### 保留

- 先做只读体检，再切换默认路线、创建新订单；订单创建后路线冻结。
- API 已有历史成功证据，本轮 Browser 的边际价值更高。
- 付款前必须稳定核对金额、税费和账号，证据不足即停止。

### 修正

1. **自动补给不是必然被本单验证**：订单只会命中直接分配、补余额或开卡其中一个分支；不得把未命中的分支写成已验收。
2. **Browser 切换有前置阻断**：当前后台 Browser 按钮实际为禁用，且“卡台允许开卡”与“自动补卡未就绪”同时出现。必须先定位 readiness 真实条件，不能把切换当作下一步必然成功。
3. **时间只能是估计**：20–40 分钟、5 分钟等只能标为目标/估计，不能承诺；Cloudflare、卡台余额、Profile 心跳和 Checkout 页面都会改变时长。
4. **真实付款是独立闸门**：即使 Browser 到达 Checkout，也必须再次核对 `₱982.14 + ₱0 tax` 并取得当次明确确认；不能把“允许真实测试”理解为预先授权所有付款。

## 第一性原理检查

测试目标是证明“客户提交后能完成 Browser 充值”，最短证据链是：路线冻结→资源就绪→Session 登录→Checkout 事实→付款前停点/付款→结果收尾。与该目标无关的高频扫描、重复 API 测试、额外人工开关和人为制造库存条件都应排除。

## 修订后执行顺序

1. 只读体检并记录冲突；
2. 只修阻断 Browser 的真实原因并复验；
3. 在后台确认 Browser 可切后，切换默认路线（仅影响新订单）；
4. 创建一笔 Browser 订单并观察到 Checkout；
5. 价格/税费不满足时安全停止；满足且用户再次确认时才付款；
6. 完成 Plus、续费取消、交易、余额、对账、通知和资源清理；
7. 只有订单实际命中补余额/开卡分支时，才记录对应分支的生产验收结果。

本复查未改变生产配置，未创建订单，未调用 Provider 写接口，未付款。
