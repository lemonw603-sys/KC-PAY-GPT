## 1. 首页

1.1 **「五个决定」按钮组没有悬停反馈**（对应 Lemon 原话：入口混乱，哪些能点分不清）
核实：`.decision`、`.ghost-button`、`.primary-small`、`.danger-small` 在 `admin.css` 里都**没有** `:hover` 规则；同一页面的 `.metric-card`（今天的数字）、`tbody tr[data-order]`（订单行）、`.stock-preset` 都有明确的 hover 效果（边框/阴影变化）。真实问题不是"完全没反馈"，是"同一页面一部分元素有反馈、最重要的五个决定按钮反而没有"这个不一致。
位置：`admin.css:60-71`（有 hover 的对照）vs `admin.css:204-270`（五个决定相关，无 hover）。

1.2 **"开工检查"和"需要核对"标题被推到卡片两端**（原话 (b)）
核实：`.card-heading { display:flex; justify-content:space-between }`，这两张卡片在宽屏下会占满整行宽度，标题簇贴左、"只读"徽章贴右，中间留白很大，视觉上像是断开的两段文字。
位置：`admin.css:129`。
另：`alerts-card`（"需要核对"）默认 `hidden`，只有真的有内部提醒时才出现——平时看不到是设计如此，不是坏了，值得跟 Lemon 确认这点是否已经清楚。位置：`index.html:57`。

1.3 **"开始营业"按钮与「五个决定→接单并处理」重复**（对应 Lemon 单独问的"开始营业是不是早就没用了"）
核实：`#start-business` 调 `/api/v1/admin/operations/start-business`；「五个决定」卡片里的"接单并处理"按钮调 `order-acceptance` + `recharge-dispatch` 两个接口——两条路径最终落到同一组开关状态。现在生产 `accept_new_orders` 长期是 `true`，运营模型已经是"持续在线、靠开关控制"，不是"每天开工"仪式。**这条判断 Lemon 的直觉是对的，建议里优先级最高**（真删除按钮前需要确认"开工检查"这个只读体检本身要不要保留成别的入口，不能连检查一起删掉）。
位置：`admin.js:1785-1800`（start-business）、`admin.js:2168-2181`（决定卡片里的 intake 按钮）。

## 3. CDK

3.1 **"Plus 都不在框里"，产品名和统计数字堆在一起**（原话 (a)）
核实：批次一行的渲染是 `<strong>批次号 · PLUS 状态徽章</strong><small>总数 X·未使用X·已兑换X·已作废X·时间</small>`——产品名只是加粗文字里的纯文本拼接，没有独立的颜色/边框/标签样式，跟后面一串统计数字之间也没有视觉分组，全挤在一行小字里。
位置：`admin.js:817-826`。

3.2 **生成结果框生成后不会消失，下次打开还在**（原话 (b)，已精确坐实）
核实：`elements.cdkResult.hidden = false` 全文件只出现这一处赋值，**没有任何地方把它重新设回 `true`**。只有整页刷新（回到未登录前的初始 HTML，`hidden` 属性重新生效）才会消失；在同一个后台会话里来回切页面、甚至再生成一批新的，旧框都还挂着，容易分不清是不是刚点的这次生效了。
位置：`admin.js:2075`（唯一赋值处）；`index.html:103`（初始 `hidden` 属性只在整页加载时生效一次）。

3.3 **CDK 码不带产品前缀，光看码认不出是什么产品**（原话 (c)，已精确坐实）
核实：服务端生成函数 `generateCdks(count)` 根本不接收 `planType` 参数，所有产品固定用同一个前缀 `PJ-` + 随机字符；产品信息只存在数据库列里，不体现在码的文本本身。
位置：`v1/src/services/cdk-service.js:9-11`（`CDK_PREFIX='PJ-'`，与产品无关）、`:88-98`（生成函数签名不带 planType）。
备注：改成带产品前缀（如 `PLUS-`/`5X-`/`20X-`）技术上可行，但要考虑历史已发出去、还未兑换的 CDK 格式兼容，不是纯前端改动。

3.4 **批次记录列表"感觉乱、缺功能"**（原话 (d)）
视觉层面同 3.1（信息没有分层）。功能层面：目前批次记录支持按产品/状态/日期筛选、下载原始 TXT、下载状态清单 CSV、作废未使用部分（位置 `index.html:115-125`）。**"缺少很多功能"具体想要什么操作，我核实不出来，需要 Lemon 补充**（例如：按单个 CDK 码搜索？批量操作多个批次？）。

3.5 **"CDK 里面的卡片"实际不在 CDK 页，在卡片页**（原话 (e)，页面归属需要 Lemon 确认）
核实：CDK 页（`cdks-view`）整段 HTML 里没有任何卡片列表相关的 DOM；卡片列表（`#stock-cards`）只存在于卡片页（`stock-view`）。卡片页的列表确实是把三种来源混在同一个列表里：API 实时同步的卡、备用卡台整批导入的卡（`sync_tier=MANUAL_IMPORT`）、人工或 highvcc 单张开出的卡（`card_type_id=MANUAL_BACKUP`）——三种来源目前不分组、不能按来源筛选。
位置：`index.html:88-127`（CDK 页，无卡片 DOM）vs `index.html:224-227`（卡片页的列表）。
**待 Lemon 确认**：说的是不是卡片页这个列表；如果是，"无逻辑"具体是指想按来源分组、还是别的。

4.2 **CSV 导出不知道是干嘛的**（原话 (b)）
核实：4 个导出按钮标签本身写了导出对象（订单/对账案例/批次汇总/订单追溯），但没有任何文字说明"导出了拿去做什么用"；唯一的说明文案只讲安全边界（"不含 Session、完整卡号、密文引用或令牌"），不讲用途。
位置：`index.html:258-260`、`120-122`。

4.3 **"资金证据核对"队列从没用过**（原话 (c)）
核实：这个队列只有在系统自动核实超时、或证据真正冲突时才会生成案例；正常付款流程完全不会进这里。位置文案已经写了这点（`index.html:268`："只有自动核实超时或证据真正冲突时，系统才会在这里留下……"），但容易被忽略。平时是空的、看起来"没用过"是正常状态，属于异常兜底入口，不是常规操作入口——这点值得当面跟 Lemon 讲清楚，而不是改 UI。

4.4 **免税州地址设置的用途不清楚，被误以为是"周期"**（原话 (d)，已纠正）
核实：这不是周期/时间设置。它控制 Browser 浏览器自动化充值时，结账页用哪个免税州（AK/DE/MT/NH/OR）的账单地址库、要不要启用这个地址来源、账单姓名要不要覆盖。表单本身完全没有解释这层含义，只写了"状态：关闭/启用"这种字段名，确实容易猜成别的东西。
位置：`admin.js:1673-1690`（`loadBillingAddressSettings`/`saveBillingAddressSettings`）、`index.html:283-293`。

4.5 **"领取租约、重新投递"等板块没有折叠，一直往下排**（原话 (e)(f)，已精确坐实，且已有现成参照）
核实：卡片页对"不常用/进阶"内容统一用 `<details>` 折叠了 5 处（人工开卡、highvcc 一键开卡、卡余额充值队列、补卡执行记录、新卡接管记录）；诊断页的同类内容——资金证据核对整个队列、Browser 控制面（含账单资料、Dispatch 队列/领取租约/重投递、执行记录三段）——**一个都没有折叠**，全部永久展开、依次往下排，导致翻很久才能看到想找的部分。这是同一产品里两个页面对"进阶内容"处理方式不一致，卡片页已经有现成写法可以直接照搬。
位置：`index.html:157-247`（卡片页 5 处 `<details class="stock-advanced-details">`）vs `index.html:263-311`（诊断页对应内容，纯 `<section>`，无折叠）。

## 6. 操作入口埋得太深、位置不统一（2026-09-12 Lemon 新增）

**Lemon 原话**：「这个核实结果这个地方入口实在太深了……我希望你记下来一个未来改造的需求，

### 6.1 当天撞到的两个实例（都是真实操作中卡住的，不是设想）

**（a）「确认核实结果」埋在三层之下。** 一单付款未知、卡和账号槽被锁住、执行器因此停摆，
要解开它得：滚到「Browser 控制面」板块 → 在「运行、租约与人工接管」的 run 列表里找到对应
那一行 → 行内小按钮「确认核实结果」。这个按钮是**唯一**能解开锁定的入口，却和一堆只读的
运行记录混在同一张表里。
位置：`admin.js:597-601`（`resolveUnknownButton`，条件 `paymentState ∈ {PAYMENT_UNKNOWN, PAYMENT_CONFIRMED}`）。

**（b）刷新卡台 token 有两条路，都不顺。** —— **根因已查明并修复（2026-09-12）**：
`api()` 遇到 401 会 `window.location.replace('/admin/login')`，那一跳把 hash 连同 token
一起丢掉；而 `admin_auth_required` 这一支恰好不给任何提示，于是整件事静默失败。
已改为页面一加载就把 token 从 URL 挪进 `sessionStorage`（能跨过登录跳转活下来，登录回来
自动完成保存），URL 也清得比原来更早。以下是修复前的记录： 书签那条要先把按钮**拖**到收藏栏（不是点），
当天走完整个流程后数据库里的 token 并未更新（`app_settings.highvcc_access_token_ciphertext`
的 `updated_at` 仍停在 09-10），原因没查出来——应用不记 access log，服务器侧看不到请求是否到达。
备用那条是手动粘贴框，但它埋在「卡片 → 备用卡台 A 一键开卡」的折叠里。
位置：`admin.js:2334-2347`（`consumeHighvccTokenFromHash`）、`index.html:207-210`。

### 6.2 这条清单本身能说明问题

首页有「五个决定」，那是**状态开关**的集中入口；但**处置类操作**（确认核实结果、
取消并释放、刷新卡台登录、确认 20X 已升级……）散落在各自的板块深处，没有对应的集中入口。
运营真正着急要点的恰恰是后者——**前者是日常态，后者是出事时**。

### 6.3 建议方向（待拍板，未实施）

- 把**需要人做判断、且系统在等这个判断**的操作，集中到一个固定位置（首页「今天要处理的」那块
  已有雏形，现在只展示不可操作）。判断标准很清晰：**系统卡住了、只有人能解开**的，就该在那里。
- 同类操作的**位置和措辞统一**：现在有的叫「确认核实结果」、有的叫「确认执行」、有的是行内小按钮、
  有的是折叠里的表单。
- 与 `ROADMAP.md` 里「飞书机器人远程处理运营决策」是同一件事的两面：**先把"哪些操作需要人"
  这个集合定义清楚**，界面收拢和远程化才有共同的基础。定义不清，两边都做不对。
