# Browser 付款结果未知的收敛范围讨论（2026-09-06）

> 状态：讨论稿，尚未最终冻结。依据：当前 Browser/v1 代码与 OpenAI 公开帮助中心；未执行付款或生产变更。

## 用户提出的关键纠偏

网络延迟或页面断开时，付款可能已经成功，只是结果尚未返回。此时不应把整个 Browser 链路、卡台或所有订单全部暂停；ChatGPT 账号一旦已激活订阅，页面通常也不会继续按正常未订阅流程购买。

## 代码现场

当前 Browser 实现会在提交意图后发生异常时：

- 将该 `browser_run` 置为 `RECONCILE_ONLY/PAYMENT_UNKNOWN`；
- 将该 `recharge_attempt` 置为 `SUBMIT_UNKNOWN/UNKNOWN`；
- 将该订单置为 `SUBMIT_UNKNOWN`；
- 将该卡的消费记录置为 `RECONCILIATION`；
- 建立该订单的对账案例。

任务领取 SQL 按订单排除已有 `ACTIVE/UNKNOWN/SETTLED` attempt，并不会由一笔 UNKNOWN 自动阻止所有其他订单。运营诊断 `readiness-audit.js` 会把全局 UNKNOWN 数量列为 blocker，但“开始营业”的 `admin-readiness-summary.js` 当前并不以该全局计数停止营业。两种口径需要后续明确，避免诊断文案被误解为全链路停机。

当前缺口：`BrowserPaymentExecutor` 在提交点击后的异常/非确认结果上会直接进入 UNKNOWN，尚未实现一个有界的 `VERIFYING_PAYMENT` 自动观察阶段。

## 不能采用的绝对假设

不能把“账号已订阅后无法再买一单”提升成“重复支付绝不可能”的资金不变量：

- 页面不再提供正常购买入口，可以作为强验证信号；
- 但网络丢响应发生在平台状态尚未被本地观察到的窗口内；
- OpenAI 官方资料明确说明跨 Web/iOS/Android 可能存在多个有效订阅和多次扣费，证明产品层并不存在普遍的“账号永远只能扣一次”保证；
- 当前没有官方合同证明 chatgpt.com 同一账号、同一时间窗口、重复提交一定不会产生第二次支付动作。

因此不应暂停全局，但仍需避免对同一未决支付再次点击。

## 推荐的最小模型（待确认）

1. 点击付款前记录唯一提交意图。
2. 点击后短时无结果不立即当失败，进入 `VERIFYING_PAYMENT`，继续只读检查：账号订阅状态、Checkout/账单页状态和可获得的卡交易证据。
3. 确认 Plus 已激活：按成功继续取消续费、更新订单和卡账本。
4. 获得明确拒付且确认账号仍为 Free：按明确失败处理。
5. 在有界观察期后仍无法判断：只锁住该订单、该账号、该卡和该 Browser run，进入人工核对；不重付该单。
6. 其他订单、其他卡、其他 Profile 和整个 Browser 链路继续运行；不自动暂停卡台或营业。
7. 无 API 的手工卡源无法实时查交易时，优先依赖账号订阅与账单页证据；证据仍不足才局部核对，不扩大停止范围。

## 保留的最小防重复边界

只保留一条必要规则：同一订单的付款点击已经发生且结果尚未收敛时，不再自动点击第二次。它是局部互斥，不是全局停机，也不要求运营逐单干预正常订单。
