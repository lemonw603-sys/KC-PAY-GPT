# 卡台管理、完整快照与付款对账方案对抗式审查（2026-09-06）

> 状态：对已确认运营方向的实施前审查；不等于代码完成。依据为当前代码、migration、生产只读配置与数据库。未执行生产变更或资金动作。

## 总结

整体方向成立，且比 AUTO/优先级/逐单切换更简单。没有发现需要推翻“API 固定 HNSKJ、Browser 人工选源、完整快照、局部付款核实、路线分证据对账”的重大问题。但当前本地候选不能直接部署，存在 6 项必须在实现前收口的问题。

## P0-1｜当前导入器写死单一备用卡台

`manual-card-import-service.js` 将 `SOURCE_ACCOUNT_ID` 写死为 `...0103`，migration 048 也写死 `manual_excel/backup-primary`。这只能支持一个模板和一个备用来源，无法承接未来 2–3 个卡台。

**修正**：卡台来源必须作为导入请求的明确上下文；批次表记录 `provider_account_id` 和 importer adapter。不同卡台可以有独立解析适配器，不做一个猜测所有格式的万能解析器。

## P0-2｜当前本地分配仍会在多个启用来源中自动挑卡

`workflow-repository.js` 当前只要求卡所属来源存在于 `fulfillment_route_card_sources` 且 enabled，然后按余额/创建时间选择；migration 048 又给 HNSKJ priority 100、备用源 200。这仍是自动混池/优先级模型，与“运营者直接指定 Browser 当前卡台、不自动回退”冲突。

**修正**：订单创建时冻结一个明确 `card_provider_account_id`；分卡 SQL只允许该来源，不读取所有 enabled 来源，也不使用 priority 自动回退。

## P0-3｜完整快照不能把“不适合使用”当成“数据无效”

当前解析器把非 active、过期、余额不足等行归为 REJECTED。完整快照中这些行仍是该卡台真实存在的卡，应该被接收并记录为不可分配；否则系统无法区分“卡存在但不可用”和“文件损坏/身份不完整”。

**修正**：

- 结构/身份错误（缺卡序列号、PAN 格式损坏、重复序列号等）阻止整个完整快照提交；
- 业务不可用（停用、过期、余额不足）正常进入快照，但状态为不可分配；
- 只有完整快照结构有效后，才允许收敛本次缺失卡。

这避免一个坏行导致系统误以为卡从全量清单消失。

## P0-4｜同一实体卡可能跨来源重复入库并被双分配

当前导入只按 `(provider_account_id, external_card_id)` 查重；`pan_hmac` 只有普通索引，不是全局唯一约束。同一 PAN 若出现在两个来源/文件中，可以形成两张本地卡记录并被并发分配。

**修正**：导入预览必须做全局 PAN HMAC 冲突检查。发现跨来源同卡时，不自动搬家、不创建第二份可分配记录，标记来源冲突等待运营核对。历史订单和账本仍归原实体卡。

## P0-5｜完整快照提交必须与分卡并发安全

完整快照可能正在把卡标记为移除时，Worker 同时选择该卡；当前候选没有来源级快照版本或等价的事务边界。

**修正**：提交快照、更新/移除卡的可分配状态与订单分卡必须使用一致的来源/卡行锁和提交边界。导入不需要暂停整个 Worker；已被分配的卡保持活动绑定，快照只阻止新的分配。

## P1-1｜当前 `$16` 资格判断存在硬编码不一致

当前导入更新已有卡时读取 `default_minimum_required_card_balance`，新增卡却硬编码 `item.balance >= 16`。生产当前设置恰好为 `$16`，但配置变化后新增和更新会得出不同资格。

**修正**：导入只记录真实余额/状态；可分配资格统一由同一业务规则动态计算，不在导入器硬编码金额。

## 付款 UNKNOWN 与对账审查

- 当前 Browser 数据库已经有活动账号唯一约束，UNKNOWN 会锁相关账号/run/attempt，不需要全局停机。
- 当前执行器点击后异常直接进入 UNKNOWN；已确认的目标应增加有界自动核实阶段，但时间参数应通过真实订单观察校准，不在方案阶段拍脑袋固定。
- Plus 激活是客户成功的核心证据；HNSKJ 交易可随后同步。无 API 手工卡源不能因缺实时交易接口被判异常。
- 现有“三方异常”动态 SQL的明确失败误报、旧 `cards.order_id` 和 ZZSHU 硬编码必须在 Browser 真实付款上线前修复，否则后台会继续产生不可信数字。

## UI 审查

确认将充值方式与卡台来源分开是正确的：

- 首页只切 `API 充值 / 浏览器自动化充值`；
- 卡台管理页显示 API 固定来源与 Browser 当前来源，负责切换、快照导入和来源分组库存；
- 风险提醒不阻止 Browser 卡台选择；
- 高频切换不要求确认词和十字理由，但必须自动写操作者、旧值、新值和时间；
- 批量接管等待订单必须显示预估数与实际迁移数，因为确认期间 Worker 可能先领取部分订单；未迁移项不算失败，也不能强制抢锁。

## 不增加的复杂度

- 不增加自动评分、自动回退或通用规则引擎；
- 不复制订单、卡表、账本或对账系统；
- 不为每个备用卡台复制页面，只使用卡台目录 + 对应导入适配器；
- 不为一笔 UNKNOWN 暂停全局；
- 不要求每单人工选择。

## 结论

方案可以继续进入最终冻结讨论，但本地 migration 048 和导入/分配代码必须视为候选而非可部署成品。P0-1～P0-5 是为了保证已确认业务语义，不是新增业务复杂度。
