# MVP 前置能力对抗式复核（2026-08-26）

## 复核问题

后期路线中的哪些东西，如果不提前放进 MVP，MVP 实际上就不能完成“多次自动化充值”的核心目标？

## 结论

需要前置的不是完整后台或高并发，而是所有直接防止“重复扣款、错卡、续费失控、结果无法解释”的最小能力。

| 后期路线能力 | 是否前置 | 前置到什么程度 |
|---|---:|---|
| Session/账号核验 | 是 | 实际上号器 lane 或批准的等价 source + 真实身份核对 |
| Browser runtime 可替换 | 部分 | 先 Chrome control lane；保留 runtime 接口，指纹浏览器不阻塞 |
| 持久队列/租约 | 是 | 单 Worker 也要有 durable job、lease、heartbeat |
| 卡片生命周期 | 是 | ready 证明、独占锁、卡材料 lease；补余额/销卡动作可后移 |
| 幂等/UNKNOWN/人工接管 | 是 | 付款前 fence、提交后 UNKNOWN 锁定、只读对账 |
| 权益/扣款/订阅核对 | 是 | 三方核对最小实现，至少支持人工处理异常 |
| 运营后台 | 部分 | CLI/JSON 或极简详情即可，不能没有追溯入口 |
| Artifact Vault | 部分 | 保存页面摘要、截图和外部引用；完整检索后移 |
| 速率/并发/背压 | 部分 | 可配置参数和单机低并发；不做分布式扩展 |
| 多 Provider fallback | 否 | 单路线先证明稳定 |
| 多机高可用 | 否 | 后续阶段 |
| 退款/提现/销卡自动化 | 否 | 预留状态和人工入口 |

## 关键纠偏

当前实现的 `cardRef` 只是引用，真实付款还缺“卡片材料如何在付款瞬间到达 Browser”的实现；当前直接 Cookie adapter 也没有验证实际扩展上号器。两者都不能被文档描述成已完成 MVP。

## 当前 F0 必须补齐的四个硬缺口

1. 实际上号器扩展 lane 或明确等价路径的运行证据；
2. 卡片材料 lease/填充边界；
3. 付款后权益、扣款、订阅状态三方核对；
4. UNKNOWN 锁定、最小人工处理和停止开关。

只有这四项和现有 Chrome/Session/Checkout 前置切片合在一起，才构成我们说的核心真实付款 MVP。
