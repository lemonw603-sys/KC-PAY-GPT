# 竞品后台截图观察

来源：用户提供的后台截图（2026-08-25）。  
证据等级：L0 观察线索。截图不能证明后端实现、真实库存或真实成功率。

## 可见模块

截图中可见一个公司/租户详情页，包含：

- 公司编号、绑定用户数量、CDK 前缀；
- “卡台线路”路由，显示 `ZZSCARD`、`HNSKJ`，以及当前使用中的 `KIMOOX`；
- “凭据已安全配置”，显示脱敏 API Key、API Secret 已加密、私密卡信息解密已启用；
- “自动补充卡片”，包含目标库存、自动开关、默认卡段和使用次数；
- “满次自动销卡”，包含执行频率和每次处理上限；
- “公司功能配置”，显示模块级开通状态；
- “公司基础服务”，显示订阅和到期时间。

## 可以推断的产品结构（不是后端事实）

1. **多 Provider 路由层**：卡台不是写死在充值流程里，而是通过当前路由选择 `ZZSCARD/HNSKJ/KIMOOX` 等供应商。
2. **凭据保管层**：API Key/Secret 与私密卡信息有独立的配置和解密开关，说明供应商凭据与业务操作分离。
3. **库存策略层**：自动补卡以目标库存、推荐卡段、默认金额和可用次数为输入，属于“库存水位→补货任务”的策略，而非简单手工导卡。
4. **卡生命周期层**：满次销卡是独立后台任务，有频率和单次上限，说明开卡、使用、报废/销卡可能是不同作业。
5. **租户/公司级开关**：业务模块和服务订阅按公司隔离，可能存在公司级权限、配额和功能开关。

## 对我们项目的可借鉴点

### 值得借鉴

- Provider route 抽象：把卡台选择作为配置化、可审计的路由，而不是让 Browser Worker 直接绑定某个供应商。
- 凭据 Vault：凭据配置、解密授权、实际使用分离；普通后台只显示脱敏摘要。
- 库存水位策略：目标库存、补货批次、单次上限、频率和 kill switch 作为显式设置。
- 生命周期作业：开卡、充值、绑定、耗尽、销卡、对账拆成独立状态机。
- 公司级权限和模块开关：Browser、卡台、补货、销卡、人工接管分离授权。

### 不能直接照搬

- 截图没有证明其 API 是否真的加密、是否有审计、是否有幂等或未知结果锁定。
- “使用中”“目标库存”“剩余次数”等文案不能证明当前真实状态。
- 没有看到订单、Checkout、付款许可、UNKNOWN 恢复或 Plus 权益核验，不能据此判断其 Browser 充值闭环。
- 不能把竞品的供应商名称、默认金额、卡段或执行频率直接作为本项目配置。

## 建议转化为本项目问题

后续验证竞品或设计本项目时，重点问四个问题：

1. Provider 路由切换是否冻结在任务/订单开始时，还是运行中可变？
2. 自动补卡和销卡是否有独立幂等键、并发租约和 UNKNOWN 状态？
3. 凭据解密是否需要一次性授权，明文是否会进入日志、任务或截图？
4. 公司级开关是否分别控制“读、准备、写、销卡、人工接管”，还是只有一个总开关？
