# Browser 自动化充值未来能力路线图（草案，待确认）

## 文档定位

这是 Browser 线的长期能力方向，不等于当前已实现，也不自动授权真实付款。路线图按“先证明核心价值，再逐步增加规模和运营能力”组织。

## 已确认方向

- 卡台 API 和运营后台是 Browser 的上游；
- 卡台发行/管理项目自己的 Visa 虚拟卡；
- Browser 只消费 `cardRef`、`routeRef`、`cardReadyEvidence` 等共享引用，不直接持有 Provider 密钥；
- Session Bootstrap 是必要能力，上号器只是其中一种输入/注入实现；
- Google Chrome 保留为 control lane；本地指纹浏览器作为可替换 runtime；
- 真实付款必须能被核对到订阅权益、卡台交易和资金账本；
- 不把任何单一厂商、卡段、上号器或 worktree 写死为业务核心；
- 未来目标是支持稳定的多次自动化充值，并为每天 200–300 单预留基础能力。

## 阶段路线

### F0：核心真实付款 MVP

目标：用一张卡台 Visa 卡、一个测试账号和一个 Google Chrome Profile 完成真实付款闭环。

能力：

- 卡台就绪卡只读投影；
- Session 注入和账号核验；
- 单 Worker 顺序任务；
- 卡片独占、幂等、失败/UNKNOWN 停止；
- Checkout 观察、付款提交、权益确认；
- 卡台交易和扣款核对；
- 最小订单/attempt/run/审计记录；
- 默认关闭的真实付款开关和人工闸门。

验收：1 笔真实付款通过后，再受控验证 2–3 笔连续流程。任何资金差异或 UNKNOWN 都停止扩展。

### F1：受控多次充值

目标：同一套代码稳定完成小批量、顺序或低并发充值。

能力：

- 持久化队列和租约；
- 可配置并发和节流；
- 卡片/订单互斥；
- 重试和人工队列；
- 续费观察；
- 最小运营列表和失败诊断；
- Chrome Profile 生命周期清理。

不追求：高并发、跨机、自动 Provider 切换。

### F2：Browser Runtime 可替换化

目标：在不改变订单、资金和审计合同的情况下切换运行时。

能力：

- Google Chrome control lane；
- 一个本地指纹浏览器适配器；
- Profile/Context/代理/locale/timezone 绑定；
- Session 重启恢复验证；
- runtime 对照指标。

指纹浏览器不负责订单或资金逻辑，只负责隔离运行环境。

### F3：200–300 单/日基础能力

目标：具备向该量级扩展的调度和观测基础，不在此阶段承诺生产容量。

能力：

- 无状态 Worker；
- 可扩展队列和持久化租约；
- 并发、速率、背压和卡片占用配置；
- 任务年龄、成功率、失败类型、耗时和资源指标；
- Profile 池和清理回收；
- 失败/UNKNOWN 隔离；
- 回放数据压测，不用真实卡批量压测。

### F4：生产化运营和资金闭环

目标：让运营人员能追踪、干预和对账，而不是只依赖日志。

能力：

- 运营后台任务列表和详情；
- 订单、attempt、browser run、卡台交易和资金账本关联；
- 预计/实际扣款、手续费、前后余额和外部引用；
- 人工结案和对账；
- 退款、提现、销卡等后置生命周期（单独设计、单独审批）；
- 审计和 artifact 保留策略。

### F5：多 Provider/多路由扩展

目标：在已证明单一路线稳定后，再增加路由和供应商选择。

能力：

- 配置化 Provider route；
- route 健康度和能力矩阵；
- 受控 fallback；
- 旧订单固定原路线，新订单按当前有效路线；
- 不在 UNKNOWN 状态下盲目切换 Provider。

## 长期能力地图

```text
卡台与库存
  → 卡片就绪/补余额/生命周期
Session 与身份
  → 上号器/Session source/账号核验/过期处理
Browser Runtime
  → Chrome/Profile/指纹浏览器/代理/环境一致性
Worker 控制面
  → 队列/租约/并发/幂等/恢复/人工接管
Checkout Engine
  → 页面识别/套餐/币种/付款/3DS/权益确认
资金与审计
  → 扣款/交易/余额/账本/对账/证据
运营与规模
  → 任务视图/告警/指标/回放/容量/多路由
```

## 明确不作为方向的内容

- 把某个指纹浏览器品牌写死；
- 把现有上号器扩展写成唯一 Session 核心；
- 把第三方虚拟卡服务当成项目卡源；
- 把卡台补余额和 Browser Plus 付款混成一个 attempt；
- 只用“支付页面成功”判断订阅成功；
- 通过盲目重试、切换地区或更换卡段来绕过未知失败；
- 在没有资金和权益核对的情况下追求吞吐量。

## 待用户确认的路线问题

1. F0 是否按“Google Chrome 先完成第一笔真实付款，指纹浏览器作为并行 Spike”推进；
2. F0 的连续真实验证数量是否采用 1 笔 → 2–3 笔；
3. F1 是否先做顺序/低并发，而不是立即做多机调度；
4. F3 的 200–300 单/日是否只作为容量目标和接口预留，不作为 MVP 验收指标；
5. 退款、提现、销卡是否统一放到 F4 单独立项。
