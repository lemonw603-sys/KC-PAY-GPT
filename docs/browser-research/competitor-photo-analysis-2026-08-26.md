## 二、最有价值的结构性启发

### 1. Provider 路由被做成了独立控制面

照片 1 显示卡台不是写死在业务代码中，而是以线路/Provider 路由形式选择。这提示我们把：

```text
业务订单 → 资金/卡片准备 → Provider route → Browser/Provider 执行
```

分开建模。Provider 切换应在任务开始前冻结、写入审计，不能在付款未知时临时换线路。

这与 c566 worktree 中已有的 provider route、card catalog、card funding 方向一致，但不能仅凭照片证明两者实现相同。

### 2. 凭据配置与业务执行是两层

照片显示 API Key/Secret 配置、私密卡信息解密和业务功能开关分开呈现。可借鉴为：

- 凭据配置页面只显示脱敏摘要；
- 读取/解密和实际调用分成独立授权；
- Provider route、卡片库存、Browser 执行各自有开关；
- 所有解密和使用都留下审计事件。

但“私密卡信息解密已启用”这种全局状态本身是风险信号。我们的设计不应使用长期全局明文解密开关，而应使用单任务、短时、最小范围的 credential grant。

### 3. 自动补卡和满次销卡是独立后台作业

照片 1 显示：补卡有目标库存、默认卡段/金额和自动开关；销卡有次数阈值、频率和单次最大处理数。

这说明卡生命周期可能被拆成：

```text
库存水位 → 补卡任务 → 开卡/准备 → 可用库存
→ 充值使用次数累计 → 耗尽/隔离 → 销卡任务
```

可借鉴：目标库存、批量上限、执行频率、暂停开关和任务审计。不能直接复制其默认“5 次”“5 分钟”参数，必须由卡台合同和资金风险数据决定。

### 4. 自动化任务与凭证管理可能是两个队列

照片 2 是 `automation_jobs`；照片 4 是“凭证管理”订单/凭证列表。两者字段和状态明显不同，提示竞品可能把：

```text
凭证/订单接收 → 自动化任务 → 结果/交付凭证
```

拆成不同的实体，而不是一张任务表包办全部事情。

对我们的启发是：订单、Browser attempt、Session credential、Checkout artifact、交付状态应分开存储，通过引用和状态关联，不能把完整 Session JSON 直接塞进普通任务行。

### 5. “待处理”是需要单独运营的队列状态

照片 4 有大量“待处理”记录。这不能证明系统卡死，但说明竞品后台至少需要：

- 队列年龄；
- 当前租约/Worker；
- 重试次数；
- 最后错误分类；
- 人工接管和批量处理；
- 是否已经产生付款副作用。

我们的后台不能只展示 `pending/success` 两个粗状态。

## 三、明显的安全和可运维风险线索

### 原始 JSON 直接出现在任务列表

照片 2 的列名和内容显示“原始 JSON”可在列表中查看，且能看到 `user.id` 等身份字段。

能证明的是：后台数据模型/展示层至少把原始 JSON 当作可展示任务字段。不能证明的是数据库是否明文存储全部 Session。

对我们的明确启发：

- 任务列表只显示 Session 摘要、身份 HMAC 和脱敏诊断；
- 原始 Session 只能进入加密 artifact vault；
- 普通管理员列表不得复制、下载或删除原始凭据；
- 删除应是可审计的销毁/隔离动作，不是列表上的硬删除按钮。

### 删除按钮不等于安全删除

照片 2 每行有删除操作。我们不能判断它是否真正删除了关联 Session、日志、截图、备份和 Provider 任务。

我们的设计要让删除/销毁明确回答：

```text
销毁的是哪类 artifact？
是否仍有可恢复密文？
关联的订单/审计是否保留？
是否阻止后续重放？
```

### 凭证列表中的邮箱和订单号属于敏感运营数据

照片 4 暴露了邮箱、订单号和产品。我们应采用最小展示、分页、权限、审计和导出限制，避免把客户身份和支付关联信息放进 Browser 普通日志。

## 四、对我们 MVP 的具体影响

### 应该吸收

1. **Provider Route Registry**：路线、能力、状态、健康度、版本和切换审计。
2. **Credential Vault**：API 凭据和 Session artifact 分离；短时 grant；脱敏后台。
3. **Card Inventory Policy**：目标库存、补货任务、单次上限、暂停开关和水位告警。
4. **Card Lifecycle Worker**：开卡、绑定、使用次数、耗尽、隔离、销卡分阶段。
5. **Separate operational queues**：订单、Browser attempt、凭证、Checkout artifact 和交付状态分开建模。
6. **Queue observability**：pending 不只显示颜色，要显示年龄、租约、重试、错误、人工状态和副作用状态。

### 不应该吸收

- 把原始 Session JSON 放在普通任务列表；
- 提供长期全局“私密卡解密已启用”；
- 用删除按钮替代可审计的 artifact 销毁；
- 直接复制竞品的默认卡段、金额、5 次阈值或 5 分钟频率；
- 把移动端截图直接当成 Google Play/Android 主充值路线；
- 仅凭“待处理/成功”判断真实付款终态。

## 五、下一步验证问题

如果以后有合法、隔离且不触碰真实客户凭据的观察机会，优先确认：

1. `automation_jobs` 的原始 JSON 是 Session、订单输入还是仅用户摘要？
2. 自动化任务是否先创建 Checkout，还是先完成账号/凭证准备？
3. Provider route 在任务创建时冻结，还是运行中可切换？
4. 自动补卡是否有 idempotency key、资金授权和 UNKNOWN 恢复？
5. “凭证管理”的 GPA 订单是否来自 Google Play，还是仅内部订单编号格式？
6. 照片 3 是 Android App、WebView、模拟器还是人工截图？

在这些问题没有证据前，照片只能用于设计启发，不能改变 Browser MVP 的技术路线。
