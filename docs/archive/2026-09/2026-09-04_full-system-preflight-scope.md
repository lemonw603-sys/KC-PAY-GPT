# 全系统体检范围与执行纪律｜2026-09-04

## 目的

在下一笔 Browser 真实订单前，一次性核对客户充值页、运营管理后台（含 Browser）、后端共享核心、卡台/库存/自动补给、生产部署与运行状态，避免只查单一模块。

## 固定检查面

1. 客户充值页：字段、确认、建单、路线冻结、状态/时间线/邮箱展示、失败与未知状态。
2. 运营后台总览：默认路线、开始营业、接单/派发、就绪检查、告警与跳转。
3. 订单/资金后台：订单详情、attempt、资金栅栏、失败透传、对账、交易、余额、Bark、取消/复核。
4. 库存与卡台：实时卡资格、运营覆盖、消费次数、同步、卡段、卡台余额、自动补余额、自动开卡。
5. Browser：dispatch、Profile、Worker、Session、Checkout、付款前门禁、失败收敛和清理。
6. 后端共享核心：状态机、路线冻结、队列租约、幂等、并发、重启恢复和权限边界。
7. 生产/部署：本地 HEAD、候选与当前 release、systemd、timer、migration、数据库开关、日志和健康端点。

## 证据纪律

- 每项标记为：生产已验证 / 代码已验证生产未验证 / 历史快照 / 未验证。
- 实时运行、数据库、日志和当前 release 优先于历史文档和对话记忆。
- 发现冲突先停在冲突点，不用局部字段补全业务结论。
- 体检期间不创建订单、不调用 Provider 写接口、不付款；只有体检通过后才进入路线切换和真实订单阶段。
- 真实订单前的路线切换属于生产写操作，需在体检报告中说明影响、回滚和当次确认点。

## 当前不得假定

- Browser 按钮可用；
- 自动补余额或自动开卡能在生产成功执行；
- 当前可分配卡数量；
- 当前数据库默认路线；
- “卡台允许开卡”与“自动补卡未就绪”矛盾的根因。

## 维护要求

体检完成后，同一轮更新 `PROJECT_MAP.md`、`CURRENT_STATE.md`、`DECISIONS.md` 和 `HANDOFF_LOG.md`；未完成项和证据路径不得只留在聊天上下文。

## 进展汇报要求

统筹窗口按“阶段/板块”汇报进展，而不是逐个命令或微步骤打断：每完成一个检查板块，说明当前已完成板块、正在处理板块、下一板块及阻塞/未验证项。只有遇到生产写入、真实付款或必须由用户决定的分叉时才暂停请求确认。
