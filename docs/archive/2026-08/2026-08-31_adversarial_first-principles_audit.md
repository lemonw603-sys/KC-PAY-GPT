# 方案对抗式审查与第一性原理复核｜2026-08-31

## 审查方法

本次不依赖历史对话作为证据，直接检查当前 `main` 源码、生产 release、systemd 配置、生产数据库只读结果和测试。

核心问题拆成四个最小事实：

1. 订单是否只会绑定一张正确的卡；
2. 付款前看到的余额/交易证据是否仍然新鲜；
3. 资金栅栏是否先于唯一外部写入建立；
4. 开关显示为可执行时，实际执行器和 Provider 是否真的可用。

## 直接证据

- 生产当前 release：`/opt/pojia/releases/20260830-card-sync-wording-d230273`；Web/Worker active。
- 生产 readiness：`ok=true`，迁移 041，活动任务/资金风险/UNKNOWN/对账案件均为 0。
- 生产 Provider/API/卡台写入均关闭；Browser Worker disabled；卡资金补给 timer disabled。
- 生产卡 `1839/1013` 资料同步后，交易同步过期时被判为 `BLOCKED`；手动完整交易同步后才恢复 `READY`。
- 当前 `recharge-attempt-repository.js` 和 `browser-execution-repository.js` 的付款前新鲜度查询只读取 `c.last_synced_at AS card_last_synced_at`，没有读取或校验 `last_transaction_synced_at`。
- 当前 `submitRecharge()` 在付款前调用 Provider `card()` 详情接口，但不调用 Provider 交易接口；因此已分配卡在等待期间交易证据过期时，付款前仍可能只看到“资料新鲜”。
- `card:stock` 状态和分配 SQL 会检查 `last_transaction_synced_at`，但这是“分配时”门槛，不是“付款提交时”门槛。
- 相关测试覆盖了资料同步过期，但没有覆盖“分配后等待超过 15 分钟、交易证据过期、提交前必须重新同步/阻断”的场景。

## 对抗式结论

此前“同步问题已解决、可直接进入真实 API 订单”的表述不完整：同步入口文案已修复，`1013` 也曾恢复 READY，但付款前的权威检查仍未把交易证据新鲜度纳入同一门槛。这是一个真实的前后端/状态机未对齐问题，优先级 P0。

## 最小修复方案

不重做库存系统，只做三件事：

1. 将 `last_transaction_synced_at` 纳入 API 和 Browser 付款前权威 snapshot，超过 15 分钟直接阻断并排队该卡完整只读同步；
2. 同步完成后让原订单以短间隔重试，避免人工刷新；
3. 增加一个集成测试：卡分配成功后人为推进时间超过 15 分钟，提交前必须被阻断；同步完成后才能继续。

同时修正总览可执行性：接单/派发开启不等于 Provider 可写，必须明确显示“当前只能接单，不能完成 API 充值”。

## 不应做的修复

- 不降低 15 分钟门槛；
- 不把旧交易时间当成新证据；
- 不仅修改前端文案而不改付款前权威检查；
- 不为绕过测试而直接把 `1013` 标为可分配；
- 不启用 Provider 写权限或真实付款作为排查手段。

## 当前决定

在上述 P0 修复和回归测试完成前，不开始下一笔真实 API 充值。本报告是审查结论，不代表已经完成修复或部署。
