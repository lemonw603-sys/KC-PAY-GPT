# 控制面最小改造方案对抗式复查｜2026-08-31

## 结论
总体方向成立，但第一版必须进一步收窄为“控制面收敛 + 就绪结果展示”，暂不同时改自动补卡、补余额、Browser 付款或同步调度。这样才能在半天内可验证、可回滚，并避免把运营体验改造与资金行为改造混在一起。

## 发现的风险与修正
1. **隐藏开关不等于删除开关**：后台可以移到高级区，但后端独立门禁必须保留；开始营业不得隐式打开 Provider/卡台/Browser 写权限。
2. **检查结果不能只返回一条错误文本**：必须返回稳定的 `checkId`、状态（READY/AUTO_HEAL/ACTION_REQUIRED/BLOCKED）和可选 `actionId`，前端按 ID 跳转，不能按中文文案匹配。
3. **自动动作必须幂等**：交易同步、补给排队只能插入一个活动任务；重复点击开始营业不能重复调用 Provider。
4. **开始营业的库存门禁暂不放宽**：当前自动开卡/补余额尚未完成生产写入验收，因此第一版不改变 `available < 1` 的安全门禁，只把原因解释清楚。
5. **API 次数结论需实测**：界面收敛本身不增加调用；要证明减少调用，必须另行比较卡库存定时器和订单驱动同步的实际 Provider 请求计数，本版不宣称已经减少。
6. **Browser 不能被误显示为可用**：Browser Worker/心跳/付款写权限未满足时，入口显示未就绪，不允许切换或自动放行。
7. **半天交付的边界**：首个 release 仅涉及后台展示、就绪聚合和跳转，不改 Provider 写路径、资金账本、订单状态机和任务调度；若健康检查失败，直接回滚 release。

## 第一性原理
系统目标是“客户提交后尽快完成充值，同时不重复扣款、不制造未知资金风险”。因此：
- 自动化只处理可逆且幂等的只读/排队动作；
- 资金副作用仍由既有硬门禁控制；
- 运营界面显示决策结果，不暴露实现细节；
- 无法安全判断的状态必须停住并进入核对。

## 修订后的实施顺序
1. 后端增加统一就绪检查结果（只读、稳定 ID、动作分类）；
2. 前端首页收敛为默认充值方式、开始营业/暂停接单、就绪摘要；
3. 高级区承载原有内部开关；
4. 加入跳转映射和幂等/回滚测试；
5. 本地全量与生产候选只读演练；
6. 部署后观察，不改变自动补给和 Browser 生产状态。

本报告不改变资金安全规则，也不授权真实 Provider 写入。
