## 一、项目是什么

项目是一个 **ChatGPT Plus 自动充值与运营管理系统**，目标规模为每天 200–300 单。

当前确定的三端架构：

1. **可替换卡台层**：当前主要是 HNSKJ，负责卡片目录、开卡、卡片状态、余额和交易读取；未来允许人工切换备用卡台；旧订单保留原卡台路线。
2. **运营后台**：订单、CDK、卡片库存、Provider 调用、交易、对账、告警和操作审计；内部问题在这里处理，客户问题和系统内部问题分层展示。
3. **执行/充值台**：当前保留 API 直充兼容路线；未来主路线是 Browser Worker，使用 HNSKJ 虚拟卡在 ChatGPT 官方页面购买 Plus，并确认取消自动续费；Browser 不建立第二套订单或资金账。

## 二、已经确认的业务规则

- V1 只做 Plus；Pro 5X、Pro 20X 只预留。
- 客户在系统外通过支付宝/微信付款；生成并交付 CDK 代表客户已经付款。
- CDK 绑定产品、不绑定价格；格式为 `PJ-ABCDE-FGHIJ-KLMNO-PQRST`。
- 默认一单一卡；已消费或已绑定卡不得自动跨订单复用；特殊复用只能人工、二次核验、完整审计。
- Session 可在原订单更换，最多 3 次；窗口初始为 72 小时，不是 CDK 过期时间。
- 客户只看到自己的问题，例如 Session 无效、目标账号已经是 Plus；库存、卡余额和 Provider 故障只在后台和运营告警中展示。
- 正常已付款订单目标是自动履约，不要求逐单人工确认。
- 任何外部付款结果未知时必须冻结，禁止换卡、换路线或重付。
- 最终成功必须同时满足支付/开通成功和自动续费取消确认。
- 退款只保留原始交易、人工案件和追溯点，不做自动退款识别、提醒或自动提取。
- 自动补卡当前规则：每次 1 张、每张 `$16`、默认每日最多 5 张；每日上限可调，人工开卡不计入自动额度。
- API 路径不增加独立账号套餐预检；充值 API 的明确拒绝（例如 40030）作为权威结果。Browser 的同 Context 只读账号判断另行通过非付款 PoC 验证。

## 三、项目演进和当前完成状态

### 1. Legacy 到 v1

根目录保留原 KC-PAY-GPT 的浏览器、Stripe、代理、hCaptcha 和卡池能力，作为历史基线或隔离参考，不是 v1 生产架构。

v1 已建立 Express Web、MySQL 状态机、持久化 Worker、CDK 兑换、Session 加密、HNSKJ/ZZSHU 适配器、Provider 审计、任务租约、客户页面、运营后台和 Bark 告警。

### 2. 真实 Provider 证据

2026-08-18 独立 Provider PoC 验证了新卡开通、卡片就绪、ZZSHU 直充成功、实际扣款和取消续费确认；它没有进入正式订单库，不能当作正式 CDK→订单→Worker 成功验收。

2026-08-21 正式真实订单验证了：客户提交、CDK 兑换、Session 入库、库存卡分配、卡片只读核验、Permit、ZZSHU `create_direct`、40030 明确拒绝、本地 `RECHARGE_FAILED` 和客户 `FAILED` 状态。没有 Provider 外部订单号，也没有确认扣款。

### 3. 阶段一：追溯中心

已完成代码、测试和生产安全部署：CDK/邮箱/订单/卡片/Provider 订单/交易/成本/人工记录关联、CDK 反查、邮箱与时间查询、卡片绑定历史、付款记录、备注标签、PAN HMAC 精确查询、CDK 交付/补发/作废审计和订单档案。

特殊跨订单复用入口尚未完成。

### 4. 阶段二：Session 和正确终态

已完成代码、隔离 MySQL 验证和生产安全部署：`WAITING_FOR_SESSION`、原订单更换 Session、最多 3 次、72 小时窗口、客户原因映射、`CANCELLATION_PENDING`、`CANCELLATION_REVIEW_REQUIRED`、40030 可恢复状态和取消续费硬终态。

符合规则账号的生产成功验收尚未完成。

### 5. 阶段三：自动履约底座

已完成并安全部署：正常订单自动履约、逐单 Permit 降级为灰度/紧急工具、唯一 `recharge_attempt`、唯一 `create_direct` intent、Provider 调用和资金栅栏、UNKNOWN 锁定、配置型阻塞恢复、提交前卡片只读刷新和 readiness 一致性检查。

生产写开关仍全部关闭。

### 6. 阶段四：库存、补卡、卡余额

已完成代码和隔离测试，尚未生产部署：`WAITING_FOR_CARD`、统一库存资格 SQL、库存不足等待/告警、自动补卡规划器、每日上限后台配置、HNSKJ `rechargeCard()` 适配器、`card_funding_attempts` 账本、Provider 关联、PENDING/FAILED/UNKNOWN/MANUAL_REVIEW 状态、只读余额/交易对账 Runner、Prepared 唯一资金栅栏、后台总览和只读详细队列。

未完成：生产注册 Runner、真实卡余额写入、UNKNOWN 人工恢复动作、特殊卡复用、卡台切换和自动开卡真实付费验证。

### 7. Browser 阶段

## 六、本次通读发现的问题

### P0

1. **阶段四代码和生产状态不能混写。** 代码和隔离测试已经存在，但生产仍是阶段三 release；阶段四没有生产部署，也没有真实卡余额写验证。
2. **Browser 工作树尚未形成可重建提交。** 当前工作树有约 75 个修改/未跟踪项目，Browser 迁移、Worker、后台和测试大量未进入当前 Git 提交。部署从精确提交构建时不会包含这些文件。
3. **正式生产成功链路仍未闭环。** 尚未用免费目标账号验证正式 CDK→订单→Worker→Provider 成功→卡交易→取消续费→本地成功→资金账一致性。

### P1

4. **卡余额充值没有生产执行闭环。** 代码已有执行器、PENDING 对账和后台只读队列，但 Runner 未生产注册，真实 Provider 写入未发生。
5. **UNKNOWN 人工恢复没有后台动作。** 后台可以查看 UNKNOWN/MANUAL_REVIEW，但还不能完成有审计的人工恢复或对账结论。
6. **卡台替换与备用卡台仍未实现。** 自动补卡调度器当前使用固定 HNSKJ 账户 ID；人工切换需要 Provider account/route 配置、健康、余额、卡段、写权限和切换审计。
7. **特殊卡复用仍未实现。** 当前只有禁止自动复用和历史基础，缺少人工核验、二次确认、原/新订单关联和交易快照操作入口。
8. **历史文档有过时状态。** 已发现并修正了 API 独立预检、每日补卡后台入口、卡余额执行器、Session/40030/自动履约状态和测试数量等过时描述；仍应继续把历史审查文档标记为历史快照。
9. **HNSKJ API Key 运行证据需要重新核对。** 历史合同曾记录后台显示 Key 有效但 `/account/profile` 返回 401；后续生产记录又写卡片只读同步正常。应以当前生产运行时重新核对，不能仅凭旧文档判断。

### P2

- 连续 24 小时 soak、并发竞争和真实队列积压；
- Browser champion/fallback 冻结和人工同 Context 接管；
- 200–300 单/日容量；
- 备份恢复密钥异地托管；
- Provider account/履约路线人工切换；
- Pro 产品扩展。

## 七、当前最准确结论

项目已经是一个具有客户页面、运营后台、订单/CDK、MySQL 状态机、任务租约、资金栅栏、追溯、告警、自动履约底座和 Browser 离线控制面的候选系统。

它目前仍不是：

- 已完成真实自动充值的生产系统；
- 已完成自动补卡生产闭环的系统；
- 已完成 Browser 真实充值的系统；
- 已达到 200–300 单/日的系统。

准确表述是：

> **代码和隔离验证较完整，生产写入关闭，正式成功订单未验收，阶段四未部署，Browser 未接生产。**
