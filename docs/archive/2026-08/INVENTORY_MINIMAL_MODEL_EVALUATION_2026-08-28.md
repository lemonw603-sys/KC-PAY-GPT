# 库存最小模型评估（2026-08-28）

## 已确认的现状

当前接管代码把卡片是否可进入 `AVAILABLE` 同时绑定到：Provider 状态、卡类型、开卡金额、当前余额、完整卡资料、最近同步和历史交易等条件。余额不足或资料缺失时，统一落到 `PROVISIONING`/审查路径。

## 对现状的纠偏

### 余额不足不等于卡不可用

余额不足通常表示“尚未准备好”，可以通过卡余额充值脚本补足，再重新读取余额。它不应被解释为卡片损坏或永久不可分配。只有充值失败、Provider 明确拒绝或余额长期无法确认，才升级为失败/人工处理。

### 资料缺失不等于卡不稳定

资料没有抓取到可能只是读取失败、字段漂移、超时或同步过期。系统应先标记“待刷新/待补齐”，保留原始 Provider 记录，不把卡判定为坏卡。只有 Provider 明确返回无效/关闭，或多次读取确认资料不存在，才判定为不可用。

## 建议的最小运行模型（提案）

将一个笼统的库存状态拆成三个独立事实，最终再计算是否可分配：

1. **卡片健康**：`PROVIDER_ACTIVE` / `PROVIDER_TERMINAL` / `UNKNOWN`。
2. **资金准备**：`FUNDED` / `NEEDS_FUNDING` / `FUNDING_IN_PROGRESS` / `FUNDING_FAILED`。
3. **资料状态**：`READY` / `NEEDS_REFRESH` / `MISSING` / `READ_FAILED`。

`ALLOCATABLE` 只在健康为 active、资金为 funded、资料为 ready、未被绑定且未超过消费次数上限时成立。`NEEDS_FUNDING` 和 `NEEDS_REFRESH` 都是可恢复状态，不是永久淘汰。

## 运行与 API 成本原则

- 余额不足：进入补资金任务，不重复开卡。
- 资料缺失/读取失败：按退避重试和人工刷新，不高频轮询。
- Provider 明确终态：停止重试并保留证据。
- 每次状态变化只生成一次审计事件，避免重复告警。

## 本次结论

库存外围状态确实偏复杂；应保留“能否安全分配”的核心判断，但把“暂时没钱”“暂时没抓到资料”和“卡本身失效”区分开。上述是评估提案，尚未修改生产逻辑，需确认后再实现。
