# BRFE 执行者自检与后续工作规则（2026-08-23）

## 一、我在前几轮存在的问题

1. **把重要结论分散在聊天里**：虽然多次口头确认，但没有及时同步到主规划、决策和接班入口，导致“赛马”等结论看起来像丢失。
2. **阶段口径不同步**：新规划已经把本地 mock 子闸门与控制面长 soak 并行处理，但旧 handoff/roadmap 仍写旧停止点，容易让下一模型误判当前阶段。
3. **实现清单不等于业务闭环清单**：曾经更关注 MySQL、lease、Worker 和 soak，表达不足的是订单/CDK/卡片/attempt/Plus 激活/取消/审计的完整接口链。
4. **证据类别混用风险**：容易把代码完成说成链路完成，把本地测试说成真实页面通过，把网络限制下的页面 403 解释成账号或风控事实。
5. **把大阶段拆得过细并反复请求确认**：增加用户负担，也掩盖了阶段级闸门和真正需要确认的不可逆节点。
6. **对赛马、账号安全和流程闭环的关系表达不稳定**：赛马应是内部实验机制；流程真实闭环是首要交付，账号安全是并列放行闸门，不能互相替代。
7. **对外部项目/指南的使用边界不够清晰**：公开代码、X 帖子、卡网商品只能作为研究输入，不能当作本项目运行事实、风控规则或成功率证据。
8. **没有在每次重要落盘后立即做完整性复核**：造成旧文件、当前代码和新要求之间的冲突累积到后面才发现。

## 二、以后每一轮的固定工作方式

### 1. 开始前恢复事实

先读 `CLAUDE.md`、角色阅读指南、Browser 接班入口、BRFE 主规划、完整性审查、当前状态、总需求、实施计划和 `DECISIONS.md`。先输出当前阶段、已完成、未完成、阻塞和证据类别，不从聊天记忆猜停止点。

### 2. 先做冲突清单

发现旧文档、当前代码和用户新要求不一致时，先写“冲突—影响—备选—建议—是否需确认”，不得静默选一个版本。统一后再更新主规划、决策、合同/报告和接班入口。

### 3. 所有结论强制标注证据

每条状态使用以下标签之一：生产证据、数据库/网络证据、代码证据、测试证据、历史聊天证据、未核验。任何标签都不能被改写成更强的结论；尤其不能把 mock、隔离 MySQL 或 US cohort 外推为 PH/生产事实。

### 4. 按大阶段推进

阶段内部连续完成，不逐小步骤索要确认。当前 BRFE 阶段为 A 控制面稳定性、B 本地 Browser、C 非 PH 只读、D PH 生产相似输入、E 受控真实履约。只有生产写入、真实卡、真实付款、不可逆删除或资金状态改变才停下来确认。

### 5. 每个重大节点必须同步五处

至少更新：

- `docs/archive/2026-08/2026-08-23_browser-master-plan.md`
- `docs/archive/2026-08/BROWSER_CURRENT_STATUS_2026-08-22.md`
- `docs/DECISIONS.md`
- 对应 `docs/contracts/` 或阶段报告
- `docs/archive/2026-08/BRFE_HANDOFF_2026-08-22.md`

同时运行 `git diff --check`，并记录实际测试命令、结果、环境和未验证项。

### 6. 赛马固定规则

赛马只比较 lane/cohort 的 runtime、Session policy、网络、页面适配和恢复指标；共享订单、资金、审计和对账底座。Checkout 创建前可预路由，创建后 route 冻结；未知结果、挑战或漂移不切 lane、不换卡、不重付。最终最多一个 champion 和一个预验证 fallback。

### 7. 不可逾越的业务边界

Browser 不创建第二订单，不创建第二资金 attempt，不伪造 Provider call；付款未知只能 reconcile-only；最终成功必须包含 Plus 激活和取消续费；Session、卡片和 Checkout authority 不进入普通任务、日志或证据。

## 三、下一阶段执行纪律

当前先核验 detached 24 小时 soak 的独立日志/残留/资源结果，并继续无付款的 C 阶段前置。菲律宾出口、真实 Session、真实 Checkout 或任何付款动作都必须建立新 manifest/cohort、形成证据报告，并在不可逆动作前取得当次确认。

## 四、当前自检结论

本次审查已把前述遗漏和冲突写入主规划、决策、状态和接班入口；没有新增生产、PH、真实 Session 或真实付款证据。后续模型应以本文件和上述五处事实源为准，不依赖本窗口历史聊天。
