# 运营后台控制面盘点｜2026-08-31

## 目的
从“每天上百单”的运营视角，区分必须由人工操作的开关、应由系统自动维护的内部状态，以及只应放在高级/紧急区域的资金闸门。该审查只盘点，不改变生产行为。

## 当前日常界面实际暴露的控制项
| 当前项目 | 当前作用 | 是否应成为日常操作 |
|---|---|---|
| 默认充值方式（API/Browser） | 决定新订单路线；订单创建后冻结 | 是，但通常只在切换线路时操作 |
| 接收新订单 | 控制客户能否提交新订单 | 是；应并入“开始营业/暂停接单” |
| 自动充值/派发 | 控制新订单是否进入充值资金路径 | 不应单独操作；应由营业状态联动 |
| 自动充值模式（自动/灰度许可） | 决定是自动授权还是逐单许可 | 不应放在日常首页；属于高级配置 |
| 追踪已有订单 | 是否继续轮询已有订单 | 不应日常关闭；应默认保持开启 |
| 同步卡片交易（只读） | 是否运行交易只读同步 | 不应日常关闭；是资金证据基础 |
| 开始营业 | 先做就绪检查，再同时打开接单和派发 | 应成为主要入口，但当前会因库存不足拒绝开启 |
| 卡段刷新/默认卡段 | 读取 Provider 卡段并选择长期默认 | 低频配置，不应每单操作 |
| 卡片库存刷新 | 读取本地库存 | 低频手动刷新，不能代替同步 |
| 只读同步全部 | 排队卡片资料/交易只读同步 | 按需使用，不是每单必点 |
| 同意并接管新卡 | 将 Provider 新发现卡纳入本地运营 | 低频人工接管，不是每单操作 |
| 开卡/卡余额充值 | 产生卡台资金写入 | 高级资金操作；当前不应成为日常首页按钮 |

## 当前未在日常首页完整展示、但实际影响充值的条件
- Provider 账户 `read_enabled` / `write_enabled`；
- 进程级 `PROVIDER_WRITES_ENABLED`、`PROVIDER_CARD_WRITES_ENABLED`、`PROVIDER_RECHARGE_WRITES_ENABLED`；
- 卡台资金写入开关；
- Browser Worker 心跳、Browser dispatch 和 Browser payment writes；
- 默认路线健康、卡台规则同步新鲜度、可分配卡数量；
- 付款前卡资料和交易证据 15 分钟新鲜度；
- 活动资金风险、未知 Provider 调用、开放对账案件。

这些不应让运营人员逐单寻找；应由“系统就绪状态”统一计算并显示原因。

## 关键发现
1. 当前系统把“业务控制”（接单、路线）与“安全/基础设施状态”（Provider 写权限、Worker 心跳、交易证据）混在同一后台语境中，造成操作成本高和理解困难。
2. `开始营业` 已存在，但目前是严格就绪门禁：没有可分配卡会拒绝开启。这是安全正确的，但用户体验上应明确显示“卡不足，系统自动补给中”，而不是让用户寻找更多开关。
3. `自动充值` 与 `接收新订单` 已能分开控制；保留底层独立性有价值，但不应要求日常人员同时点击。
4. `追踪已有订单` 与“同步卡片交易”属于持续后台能力，关闭它们会损害已接订单和资金证据，不应作为正常运营动作。
5. Provider/卡台写权限不是“每单开关”。它们应保持默认关闭或按已批准的生产配置运行；真实资金操作仍需单独授权和审计。
6. Browser 目前仍未完成真实付款生产验收，因此不能把 Browser 显示为可用路线；只能在 Worker/心跳/配置满足时允许切换。

## 最小收敛方案（不删除底层安全）
### 日常首页只保留
1. **默认充值方式**：API / Browser。
2. **营业状态**：开始营业 / 暂停接单。
3. **一行就绪摘要**：可接单、可派发、库存、卡台只读状态、当前阻断原因。

### 系统自动联动
- 开始营业成功后联动打开接单和自动派发；
- 暂停接单只关闭新订单，不停止已有订单轮询；
- 卡不足时订单驱动补卡/补余额，用户无需寻找额外开关；
- 交易同步、订单轮询、Worker 心跳持续运行；
- 付款前证据过期自动只读刷新并重试。

### 高级/紧急区域
- Provider 写权限与卡资金写权限；
- Browser 付款写权限；
- 全局急停；
- 单订单 Permit/未知资金处理；
- 卡台路线人工切换。

## 不建议现在做的事
- 不删除底层 `dispatch_new_recharges`、`poll_existing_orders` 或 `sync_card_transactions` 数据字段；
- 不取消付款未知锁定、资金账本、交易证据门槛；
- 不把“开始营业”改成无条件打开；
- 不把 Provider 写权限隐藏到无法追溯的位置；应放在高级区并显示当前真实状态；
- 不在本轮顺手重做库存模型或 Browser 付款线。

## 结论
当前问题主要是**控制面暴露过多和层级不合理**，不是底层状态机必须删掉。系统应从“多个开关让人手动协调”收敛为“一个营业入口 + 一个默认路线 + 系统自动协调 + 高级紧急闸门”。本报告完成盘点，尚未修改生产代码或生产开关。
