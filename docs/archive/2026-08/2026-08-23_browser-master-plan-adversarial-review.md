# BRFE 主规划对抗式审查（2026-08-23）

## 审查问题

检查当前方案是否出现目标偏移、阶段顺序错误、赛马遗漏、证据越级、生产/资金边界模糊，及是否存在更简单且更可验证的替代方案。

## 发现

### 通过项

- BRFE 仍是 Browser 执行器，不是第二套订单、CDK、卡池、Provider 或资金系统。
- 赛马已被定义为 cohort 隔离的内部实验；Checkout 创建后不切 lane，未知结果不换路、不换卡、不重付。
- A/B/C/D/E 顺序覆盖控制面、本地页面、非 PH 观察、PH 生产相似输入和受控真实履约；真实付款明确放在最后。
- 证据类型、资源租约、Session/authority 脱敏、最终成功和资金未知边界均已写入主规划。
- US VPN 被限制为 `NON_PH_US` 观察 cohort，没有被提升为 PH 或默认生产依赖。

### 需要修正的边界

1. **A 阶段退出条件不应把不可用的高可用拓扑变成假通过或无限阻塞。** 当前只有单 MySQL 容器，因此把 A 拆成“控制面稳定性子闸门”和“高可用拓扑证据闸门”：前者可依据隔离 soak/故障注入关闭；后者标记 `NOT_AVAILABLE_IN_TEST_TOPOLOGY`，在真实生产接入前必须补双节点/代理证据。
2. **D 阶段的“支付可用性观察”容易被误读成付款许可。** 改成：D 默认不创建 Checkout、不写支付；如需观察 Checkout，必须使用独立 `CHECKOUT_MUTATING` 隔离 cohort、单独 manifest、一次 checkout grant 和当次操作确认；仍禁止填写真实卡和点击付款。
3. **C 阶段必须有输入前置条件。** 没有仓库外 `0600` Session 材料时只做 manifest、Worker 和脱敏观察器测试，不宣称真实账号观察失败或成功。
4. **“A/B 并行”只适用于无付款工作。** 所有外部页面、真实 Session、PH 网络和 Checkout 观察仍受相应 cohort/manifest 和确认边界约束，不能因 B 已通过而绕过 A 的未验证项。

## 替代方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 当前 A-E 大阶段，A/B 无付款部分并行 | 保留证据闸门，又不让本地工程等待长 soak；与已有代码和合同一致 | 文档需明确子闸门 | **推荐** |
| 严格串行，A 完成后才开始 B/C | 阶段口径简单 | 让本地无付款证据无谓等待；延迟发现页面/Worker问题 | 不推荐 |
| 直接跳到 PH/真实 Checkout | 反馈快 | 把 Session、网络、页面、资金和账号风险混在一起，难以归因；不可逆 | 禁止 |
| 只选一个赛道，不做 cohort 比较 | 实现简单 | 无法验证上号器、同 Context、hosted 等方向的差异 | 不推荐 |

## 结论

当前方案方向正确，没有发现需要更换总体架构的更好方案。采用当前 A-E 主规划，但补上 A 子闸门、D 的 Checkout 边界和 C 的 Session 输入前置。补丁完成后继续执行；不需要用户为文档级调整重复确认。真实 Session、PH 网络、Checkout 或付款仍按既定规则在不可逆节点停下确认。

## 证据状态

本审查是规划/合同审查（历史聊天证据 + 代码/测试状态汇总），没有新增生产证据、菲律宾网络证据或真实付款证据。
