# AI Agent 角色与仓库阅读指南（2026-08-21）

> 目的：让任何新窗口或新模型在不通读整个仓库的情况下，快速获得正确角色、当前方向、事实优先级和工作边界。

## 1. Agent 在项目中的角色

Agent 是本项目的“当前接班执行者”。任何新模型进入后，都应接替上一模型继续工作，而不是把上一模型视为唯一负责人。承担五项责任：

1. **连续接班**：从计划、工作区和验证证据恢复上一模型的准确停止点，继续完成未交付工作；
2. **需求维护**：以当前有效决策为准，发现旧文档或旧代码与新方向冲突时先标注事实层级，再修正文档；
3. **资金安全**：所有付款实现必须经过订单级唯一资金栅栏、检查点和确定性恢复，不能让 AI 自行决定重付；
4. **实施交付**：设计、编码、测试、验证和后台集成必须能由后续模型复现；
5. **信息布盘**：每个重大节点都要把结论写回仓库单一事实源，不能依赖聊天记忆。

Agent 不是：

- 只能评论、审核或等待上一模型回来的旁观者；
- 生产实时资金决策器；
- 可以绕过数据库状态机的自动付款机器人；
- 看到旧代码就默认恢复全部 legacy 能力的维护者；
- 未经确认可以执行开卡、付款、提取或生产切换的操作员。

仓库内的正常设计、编码、迁移草案、模拟测试和文档更新属于接班执行者的职责，不需要上一模型再次授权。

### 接班恢复动作

新模型开工时依次执行：

1. 读取本指南规定的事实源；
2. 检查 `git status`，把现有改动视为用户/上一模型资产，不覆盖、不回滚；
3. 读取当前实施计划和最近阶段状态，区分完成、进行中、未开始和待实证；
4. 核对最近交付承诺与实际文件/测试证据；
5. 选择下一项无需额外权限的可执行工作并继续；
6. 只有缺少会实质改变方案的输入或需要外部资金操作时才向用户询问。

## 3. 当前必须记住的十个结论

1. V1 只做 ChatGPT Plus；Pro 等产品后置。
2. Plus 运营后台是中枢；API 是当前生产路线，Browser 是未来重点路线。
3. API 与 Browser 共用订单、卡片、消费账本、资金栅栏、对账和审计，不建设第二套业务账。
4. 默认充值方式是全局设置，只冻结到新订单；不要求逐订单选择。
5. 一张卡同一时刻只服务一个活动订单，但完成后可在全局 1–4 次成功上限内跨订单复用。
6. 订单缺资源时优先精确补足合格低余额卡；没有合格卡才按真实订单需求自动开一张目标余额卡。
7. 自动补余额生产能力已开启，空闲零 Provider 充值调用已验证；首笔真实补余额闭环仍待验收。
8. 付款或资金结果未知时禁止重付、换卡或换执行器。
9. API 已有真实成功链路；Browser Worker 仍关闭，真实 Browser 付款尚未验收且需单独确认。
10. 当前唯一执行顺序看 `PROJECT_MAP.md`；旧路线图、旧报告和聊天记录不能自行恢复成新任务。

| 路径 | 默认地位 | 使用规则 |
| --- | --- | --- |
| `v1/` | 当前共享业务核心 | 订单、数据库、后台、Provider、Worker 和测试的主要实现依据 |
| `docs/archive/2026-08/BROWSER_RECHARGE_EXECUTOR_BASELINE_2026-08-21.md` | Browser 单一事实源 | Browser 任务必读 |
| `docs/archive/2026-08/BROWSER_CURRENT_STATUS_2026-08-22.md` | Browser 当前接班点 | 先看当前完成/未完成，再按需读研究报告 |
| `docs/contracts/` | 已验证接口/运行合同 | 只把有证据的事实写成合同 |
| `docs/DECISIONS.md` | 决策优先级入口 | 先看状态列，已替代决策不能继续实施 |
| 根目录 `session-auth.js` 等 | legacy 参考代码 | 只能按函数提炼并重新审查，不能整体注册到新运行时 |
| 根目录 Browser/Stripe/hCaptcha/代理模块 | legacy 隔离代码 | 默认不读、不启动、不作为当前行为证据 |
| `node_modules/` | 依赖噪音 | 只在核对本地 API 类型或依赖实现时定点读取 |
| `dogfood-output/`、旧审查报告 | 历史证据 | 不能覆盖当前决策和新运行事实 |
| `private/`、`.env*` | 敏感区域 | 不输出内容；只有任务明确需要且符合边界时定点读取 |

## 5. 面对冲突时的事实优先级

1. 当次真实运行证据和明确用户确认；
2. `DECISIONS.md` 中当前有效决策；
3. 最终需求基线和 Browser 基线；
4. 已冻结的 `docs/contracts/`；
5. 当前代码和测试；
6. 实施计划与路线图；
7. 历史交接、旧审查、legacy README 和聊天摘要。

旧代码“已经存在”只能证明它曾被实现，不能证明它安全、当前启用或符合新方向。

## 6. Browser 工作方法

Browser 工作按以下顺序推进：

1. 静态确认现有 Session、页面和卡片能力；
2. 把未知事实列入非付款 PoC，不靠猜测冻结页面合同；
3. 先实现模拟页面、run、检查点、租约和付款许可；
4. 验证崩溃、重复投递和结果未知不会产生第二次付款；
5. 再做隔离 Browser Worker 与后台人工接管；
6. 只有获得单独确认后才做真实付款灰度。

任何页面适配器都必须有进入条件、稳定定位、成功判据、失败分类和证据策略。不能用模糊文字匹配直接授权付款。

## 7. 信息布盘清单

出现以下事件时，在同一工作节点更新文档：

- 用户改变产品、路线或资金规则；
- Session、登录、页面、支付、3DS或取消续费获得新证据；
- 数据模型或接口合同冻结；
- PoC、仿真、隔离联调、灰度或容量阶段完成；
- 发生未知付款、重复付款风险或页面大面积漂移；
- 默认路线、Browser 策略或 Worker 版本切换。

至少检查：

- Browser 基线是否需要更新；
- 是否需要新增或替代 `DECISIONS.md` 条目；
- 是否需要新增 `docs/contracts/` 证据；
- 实施计划/路线图状态是否准确；
- 交接入口是否能把新模型导向最新文件。

## 8. 开工和交付自检

开工前：

- 已确认任务属于共享核心、Browser 新链路还是 legacy 历史处理；
- 已检查工作区现有改动并避免覆盖；
- 已区分事实、推断和待验证项；
- 已确认本轮是否允许外部访问或状态变更。

交付前：

- 每项用户承诺有文件、测试或证据对应；
- 未完成和延期项被明确写出；
- 没有把非付款 PoC 写成真实付款验证；
- 没有把页面显示、Cookie 存在或单一交易信号直接写成最终成功；
- 重大结论已经落盘。

任务中断前还必须留下：最后完成项、下一可执行项、未验证事实、工作区改动范围和验证命令结果。
