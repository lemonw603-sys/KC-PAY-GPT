# 充值前完整链路：对抗式审查结论

日期：2026-08-19

## 结论

本文记录了 2026-08-19 付款前验收开始时的缺口。三个必补项现均已完成：正式订单停在 `PREPARE_RECHARGE submitted=false`，开卡缺失 ID 恢复/卡片就绪轮询已进入正式执行器，MySQL 租约与恢复语义已在生产机隔离库验证。

该订单的真实直充仍未执行，这是用户确认的零新增费用边界，不是技术缺口。

## 已观察到的证据

- `v1/src/workers/worker-runtime.js` 会根据运行时开关决定是否派发充值任务；这是 Worker 层的门禁。
- `v1/src/workers/workflow-handlers.js` 在提交直充前检查 `rechargeWritesEnabled`，但通过后会直接调用 `createDirectOrder`。
- `v1/scripts/provider-poc.js` 已提供付款前硬停模式；只有显式接受直充费用时才会调用 `zzshu.createDirectOrder()`。
- 本地自动化测试当前通过，但其中的 Provider 是假实现，不能证明真实 API 的请求没有发送。

## 必须补充或修正的项目

### P0：建立真实的付款前硬停止

不能调用 ZZSHU 的直充创建接口来“试试看余额不足”。必须把“构造请求”和“发送请求”拆开，验证到以下证据后主动停止：

1. 已拿到并核验 HNSKJ 卡片字段；
2. 已核验 ChatGPT Session、计划类型、地区、币种和金额参数；
3. 已生成将要发送的请求摘要；
4. 运行日志中确认未出现 `POST /third-party/orders/direct`。

### P0：验证 HNSKJ 开卡响应不确定时的处理

必须验证真实开卡响应是否包含稳定卡片 ID、状态、余额和卡片凭据。若超时、502/503 或响应缺少卡片 ID，系统必须保持人工核对状态，并使用原幂等键查询/恢复，不能自动重开。

### P1：验证真实 MySQL 和 Worker 恢复语义

本地测试不能替代线上 MySQL 验证。至少要验证：同一 CDK 并发只有一个订单、同一任务不会被两个 Worker 同时处理、Worker 在卡台超时或进程重启后能恢复租约且不会重复开卡。

## 已在原清单中、无需新增范围的项目

- Session 格式和有效期；
- CDK 一次兑换、订单事务和并发；
- 卡片到账等待、状态/余额/凭据核验；
- 菲区 Plus 金额、币种和请求参数的文档/真实响应证据；
- 单订单失败隔离；
- Provider 调用日志脱敏；
- 真实直充只对后台逐单签发的短时一次性 Permit 开放。

## 暂不纳入本轮

退款识别、退款提醒和退款关联订单全部延后，不影响本轮充值前链路验收。

## 验收门槛

只有在三个新增项目均有真实证据，并且未产生任何 Plus 扣款时，才把本轮标记为“充值前完整链路验证完成”。
