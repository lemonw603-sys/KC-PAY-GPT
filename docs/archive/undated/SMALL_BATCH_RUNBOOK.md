# 3–5 单灰度运行检查表

本检查表用于未来有真实订单后的逐单运营，不代表当前自动执行资金操作。没有待处理订单时只运行只读体检。

## 当前无订单阶段

1. 执行最新数据库迁移。
2. 运行 `npm run preflight:readiness`，保存 JSON 报告。
3. 确认三个 Provider 写开关均为 `false`。
4. 配置并验证 Bark；测试只使用人工创建的普通内部告警，不创建开卡或充值任务。
5. 确认最新加密备份可校验，恢复密钥已分离保存。
6. 若 Bark 有 `DEAD` 记录，先人工恢复或确认后再进入灰度；不得静默忽略。

## 每单执行前

- [ ] 客户订单真实存在，查询码和套餐已人工核对。
- [ ] `expired_task_leases=0`。
- [ ] `uncertain_provider_calls=0`。
- [ ] `active_or_unknown_funds_risk=0`。
- [ ] 没有未解释的余额差异或开放的高风险对账案例。
- [ ] Worker 心跳不超过 120 秒。
- [ ] 仅为该订单签发短时、一次性充值授权。
- [ ] 记录执行前卡台余额、可用卡状态和供应商余额快照。

## 执行期间

- [ ] 并发保持 1。
- [ ] 不重复点击、不更换幂等键、不对 `SUBMIT_UNKNOWN` 自动重试。
- [ ] 只观察一个订单从授权、提交到最终状态的完整链路。
- [ ] Bark 异常到达时先停止新提交，再核对权威状态。

## 每单执行后

- [ ] 核对 Provider 最终订单状态。
- [ ] 核对卡台扣款、卡余额、交易记录和本地资金尝试。
- [ ] 确认充值授权已消费或撤销，没有遗留活动授权。
- [ ] 确认 Provider 创建调用最多一次。
- [ ] 记录总耗时、调用次数、资金变化和异常原因。
- [ ] 再次运行只读体检并保存报告。

## Bark 运维恢复

- [ ] `SENDING` 超过 5 分钟的记录可被下一轮自动重新领取。
- [ ] `DEAD` 记录先核对 Bark Server/Device Key 和告警内容，再由运维执行 `BARK_RETRY_CONFIRM=RETRY-DEAD-BARK npm run notifications:bark:retry-dead -- <notification-id>`。恢复动作必须留存操作记录；`--all` 只允许在确认所有死信原因相同后使用。

## 立即停止条件

- 重复充值或重复开卡。
- `SUBMIT_UNKNOWN` 或无法确认的外部订单。
- 无法解释的余额差异。
- Worker 租约异常、Provider 连续 5xx/429、Bark 通知进入 `DEAD`。
- 任何本地状态与供应商权威状态冲突。
