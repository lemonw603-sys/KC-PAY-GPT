# 外部审查协议（Codex 审查员 / 分板块核查）

目的：由不参与实施的模型，对执行者（当前为 Claude）的规划、策略、实施、生产、代码、部署做中立核查。审查员发现偏差，执行者处置，用户裁决。三方各守边界。

## 1. 角色边界

- 审查员只读：不改代码、不改文档、不部署、不碰生产写操作、不创建任务；不替执行者做决定，不提出「应该改成我的方案」，只指出「哪里与事实源或硬约束不一致、证据是什么」。
- 审查员不与执行者直接对话。报告落盘后由用户转交执行者，执行者的处置也落盘，避免相互引导。
- 记录分离：审查记录只由审查员写，处置记录只由执行者写，互不编辑对方文件，靠发现编号交叉引用。审查意见是可质疑、可拒绝、有版本边界的信息，不是整改清单；只有用户明确确认且仍有效的业务要求才构成约束。
- 审查员不靠措辞、选择性证据或强制待办推动执行者接受某个方案；结论错了追加更正条目，不删不改历史条目。
- 审查员进入仓库先读 `AGENTS.md`，但按本协议的角色工作，不接手执行。

## 2. 输入与禁区

- 事实源只认：`CLAUDE.md`、`docs/HANDOFF_NOW.md`（当前状态与已验证/未验证边界）、`docs/PROJECT_MAP.md`、`docs/CURRENT_STATE.md`（唯一生产事实表）、`docs/CORE_SPEC_2026-09-07.md`、`docs/PRODUCT_SIMPLIFICATION_DISCUSSION.md` 末尾基线、当前代码、只读生产证据（release 目录、systemd、只读 SQL、访问日志）。
- `docs/archive/` 与聊天摘要不是事实；引用必须注明「历史」。
- 每条发现必须附可复现证据：文件路径与行号、执行过的只读命令与输出、或生产只读查询结果。没有证据的写进「疑问」而不是「发现」。
- 不为了找问题而找问题：与硬约束、基线、事实源无冲突且无用户影响的风格差异不列为发现。
- 每批每板块最多 10 条发现，按严重度排序；超出的留到下一批。执行者只逐条复核 P0/P1 的证据，P2/P3 按证据直接判定，不重新推导。

## 3. 输出格式

审查记录：`docs/reviews/REVIEW_RECORD.md`，审查员维护，只追加。按批次写，批次头注明「截至 <UTC 时间>｜commit <hash>｜release <名>｜板块 <A–F>」；一板块一个对话框，仍可以写进同一记录。每条发现：

```
### F-<序号> <一句话>
- 板块 / 严重度：P0 资金或客户影响｜P1 功能错误｜P2 与事实源/基线偏差｜P3 建议
- 观察（原始字段，不含结论）：
- 结论（依据哪条规则或基线）：
- 证据（路径:行 / 命令 / 输出）：
- 影响条件（什么情况下才成立）：
- 反证或不确定性：
- 参考验证办法（不是任务）：
- 建议（可选，一句话）：
- 置信度：高 / 中 / 低
```

报告末尾固定三节：「未能核实的事项」「与事实源冲突但无法判断谁对」「本次未覆盖范围」。

## 4. 处置流程

1. 处置记录：`docs/reviews/DISPOSITIONS.md`，执行者维护。执行者独立决定是否验证、如何解决；但 P0/P1 必须在下一节交接日志之前逐条写下 `接受｜拒绝｜待验证` + 理由 + 关联提交，沉默不算处置。P2/P3 可批量处置。
2. 接受的 P0/P1 立即进入当前工作；P2/P3 进入 `docs/PROJECT_MAP.md` §5 或穿插小修清单。
3. 执行者拒绝 P0（资金或客户影响）时，由用户裁决，结果写入 `docs/DECISIONS.md`；其余分歧记录在处置文件即可。
4. 批次触发：每次 release 或执行顺序完成一步后，执行者在 `docs/HANDOFF_LOG.md` 标「可审版本 <commit>」；审查按该版本做，不实时追踪在途改动。
5. 两份记录都不删除、不改写历史条目；更正以追加方式进行。

## 5. 板块划分与核查问题

一板块一个对话框，一份报告。板块按链路划分，不按页面划分。

| 板块 | 范围 | 核查问题 |
|---|---|---|
| A 客户下单链 | 充值后台（客户页）、CDK、订单建单、Session 校验、等待承诺 | CDK 只在交付时消耗、未付款失败自动退回是否成立；Session 密文交付后是否清理；客户页承诺与真实队列/开关是否一致；客户侧是否暴露退款/内部字段 |
| B 供给链 | 卡台 Provider、开卡幂等、补余额、备用卡快照导入、消费账本、卡资格 | 一卡同时最多一个活动订单；成功次数上限以账本为权威；失败/未知不释放卡；X-Idempotency-Key 稳定；导入原子性与 RETIRED/PRODUCT_ONLY 覆盖项 |
| C API 路线（历史兼容） | ZZSHU 适配器、API Worker、旧任务 | 是否仍能被自动触发；停用状态与事实源一致；是否与 Browser 路线共享订单/卡/账本而无双写 |
| D Browser 路线 | 身份池、会话注入/替换/清理、结账创建、填表、付款许可、UNKNOWN 锁定、凭证刷新、取消续费 | 付款前所有写开关默认关闭；单次点击唯一 PAYMENT_SUBMIT；崩溃先对账不重点；换账号清登录态留设备；结账由页面点击触发；日志无令牌/卡号 |
| E 运营后台 | 五个决定、三件日常、告警、开关、密码与确认词 | 开关语义与 app_settings 一致；停单与追踪独立；无零使用入口；密码/手打确认词剩余清单；后台资产不含密文字段 |
| F 生产与部署 | release 构建/校验/切换、systemd、备份、日志、密钥、迁移 | `/opt/pojia/current` 与文档一致；release 从单一提交构建且 manifest 全量校验；备份可验证；日志脱敏；worker 写权限 drop-in 与事实表一致；迁移可审计 |

## 6. 对话框开场（可直接粘贴给审查员）

```
你是本仓库的外部审查员，不是执行者。先读 AGENTS.md 了解仓库，然后严格按 docs/REVIEW_PROTOCOL.md 工作：只读，不改任何文件，不部署，不与执行者对话。
本次板块：<A–F 之一>。范围与核查问题见协议 §5。
只以协议 §2 列出的事实源和当前代码/只读生产证据为依据；docs/archive 与任何聊天摘要不是事实。
每条发现必须有可复现证据；没有证据的放进「疑问」。不为了找问题而找问题。
把本批次追加到 docs/reviews/REVIEW_RECORD.md（只追加，不改历史），批次头写清截至时间、commit、release、板块；格式按协议 §3；最后列出未能核实、事实源冲突、未覆盖范围三节。不要写 docs/reviews/DISPOSITIONS.md，那是执行者的。
```

## 7. 由谁做、开几个对话框

- 审查用 Codex，处置与实施用 Claude：审查员必须不带执行者的假设。Codex 额度不足时，用一个不带历史上下文的 Claude 新对话框按同一协议审查，作为次选。
- 一板块一个对话框：报告独立、上下文不淹没、可并行、可重跑。总对话框只做一件事：汇总六份报告的处置状态，不做审查本身。
