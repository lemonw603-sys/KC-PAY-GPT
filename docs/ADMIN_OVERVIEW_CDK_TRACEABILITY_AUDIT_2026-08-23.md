# 运营后台总览、UI 与 CDK 追溯审计（2026-08-23）

## 证据范围

- 本次检查范围：`v1/public/admin/index.html`、`v1/public/admin/assets/admin.js`、`v1/src/services/admin-read-service.js`、`v1/src/services/cdk-service.js`、`v1/src/services/operations-csv-export-service.js`、后台路由注册与现有测试。
- 本次为代码/API/数据模型审计；未声称逐页浏览器视觉验收，也未执行生产写入。

## 已确认事实

### 总览指标

- 总览当前渲染 18 个指标，混合了订单状态、资金风险、卡库存、同步积压、Worker 健康和成功率。
- `成功订单` 的定义是 Plus 开通成功且取消续费确认完成；定义与 V1 业务规则一致。
- `自动处理中`、`待执行充值`、`需要关注`、`三方对账异常`存在业务交叉，运营人员需要点击后再看订单列表才能区分具体原因。
- `待验证新卡`、`本地可分配卡`、`卡片同步积压`属于库存运营指标，不属于“今日运行情况”。
- `卡余额充值待处理`、`资金结果未决`属于资金风险/对账指标，不属于普通运行量。
- `成功率`只按已完成订单计算，未完成订单不计入；样本不足时显示 `—`。

### 已确认的后台 UI/数据不一致

- 总览供应商卡片前端固定显示“ HNSKJ 卡台”，后端 `providerHealth.provider` 也固定返回 `hnskj`；这与已实现的“当前卡台路线可切换”架构不一致。切换后会出现“实际当前路线”和总览名称不一致的风险。
- 总览供应商卡片只显示同步时间和是否允许开卡，卡台账户余额没有在总览显示，页面显示“详见卡片库存页”和破折号；实际余额只在库存页 Provider 摘要中显示。
- “内部提醒”卡片只在存在开放告警时显示；其文案是面向内部的“需要核对”，不是客户错误提示，功能上是告警容器，但名称和严重程度/行动入口仍不够明确。
- 系统开关区展示 `accept_new_orders`、`dispatch_new_recharges` 等运行状态，但 Provider 写入开关、卡余额写入开关属于进程/账户/环境层门禁，不在总览中完整呈现；仅凭总览不能判断资金写入是否真的可执行。

### CDK 导出能力

- 已有单批次导出：CDK 管理页可下载原始 TXT，也可下载逐码状态 CSV。
- 批次状态 CSV 包含 CDK 明文、状态、关联订单查询码、兑换时间、作废时间和作废原因；该接口受敏感操作二次确认保护。
- 批次列表当前只读取最近 50 个批次，没有批次分页、日期筛选或一次导出多个历史批次的功能。
- 已有运营 CSV 导出接口，但 `cdk_batches` 数据集只导出批次聚合字段，不导出明文 CDK；订单数据集也不是完整订单追溯报表。

### CDK 反查订单与追溯

- 已兑换 CDK 可以通过订单查询接口反查关联订单；订单详情可继续看到邮箱、产品、订单金额字段、卡片关联、卡片后四位、卡台卡 ID、Provider 调用、卡片交易、状态事件和时间。
- 未兑换或已作废 CDK 没有订单关联，这是业务上正确的结果。
- 订单列表支持 CDK 精确查询，并支持邮箱、ChatGPT 账号 ID、卡号 HMAC、卡台 ID、三方外部订单号等查询条件。
- 订单详情保留订单创建/更新时间/完成时间、Provider 调用时间、卡片交易时间和状态事件时间。
- 客户付款记录允许金额为空；CDK 生成时会建立 `PAID` 付款追踪记录，但默认没有实际付款金额和实际付款时间。因此“所有订单都能通过 CDK 查到准确支付金额”目前不成立。
- 订单产品字段为 `plan_type`，当前 V1 只生成 Plus；模型已为后续 Pro 5X/20X 保留产品字段。
- 充值金额、客户付款金额、卡台开卡金额、卡余额充值金额是不同概念，当前后台详情有分开字段，但导出报表尚未提供统一的跨表追溯视图。

## 不应直接下结论的事项

- 未做浏览器逐页点击，不能把所有视觉问题定性为已发现或已修复。
- 未执行生产资金写入，不能证明卡台余额充值真实扣款、异步结果或退款路径。
- 未查询完整生产历史批次，不能给出“所有历史批次是否都有可恢复明文”的统计结论。

## 建议的整改顺序

1. **P0：修正总览语义**——将订单处理、库存、资金风险、系统健康拆成四组；每个指标提供明确口径和行动入口。
2. **P0：修正动态卡台显示**——总览和库存页都显示当前有效路线名称、账户标识、只读同步时间、账户余额和卡片可分配数，并区分“卡台账户余额”和“卡片余额”。
3. **P1：补充 CDK 历史批次管理**——批次分页、日期/产品/状态筛选、多批次状态汇总导出；原始明文导出继续保持敏感确认，不默认批量导出明文。
4. **P1：建立统一追溯导出**——以 CDK/订单为主键，关联邮箱、产品、订单时间、客户付款记录、卡台卡 ID/后四位、Provider 订单号、卡片交易、失败/退款案件；金额缺失必须显示“未记录”，禁止推算。
5. **P1：补齐付款记录规则**——后台生成 CDK 时是否录入客户实际付款金额和时间，需要单独确定；在未录入前，报表明确标记为外部付款、金额未记录。

## 本轮实施结果（2026-08-23）

- 已完成总览指标分组、卡台账户余额/可分配卡展示、动态当前路线名称展示。
- 已完成 CDK 批次日期/产品/状态筛选、游标加载更多，以及订单追溯 CSV 入口。
- 已增加 `order_trace` 安全导出数据集，包含 CDK、订单、邮箱、产品、订单时间、客户付款记录、卡片、Provider 结果、失败原因和自动续费状态；敏感凭据与 CDK 明文不进入该报表。
- 客户付款规则已明确：CDK 生成只确认外部付款状态，实际金额/时间未补录时显示“未记录”，不推算。
- 本地回归测试：408 tests，374 passed，0 failed，34 skipped；跳过项为未配置 `TEST_DATABASE_URL` 的隔离 MySQL 集成测试。
- 未部署生产，未执行生产写入；当前生产接单、派发和资金写入门禁保持关闭。

## 实施后对抗式复核（2026-08-23）

### 已验证

- 总览指标切分边界已复核：订单处理、资金风险、库存运营、系统健康不再把卡片同步积压误归入资金组。
- `order_trace` 导出 SQL 只选择白名单字段；未选择 Session、完整卡号、CVV、密钥或 CDK 明文。
- CDK 批次游标使用创建时间与批次号双字段，避免同一时间批次分页重复或遗漏。
- CDK 日期、产品和状态筛选均在服务端执行；状态筛选使用批次成员存在性，不会破坏批次总数统计。
- 追溯导出金额为空时保持为空，不进行价格或汇率推算。

### 仍需生产验证

- 生产后台视觉布局和不同屏幕尺寸下的显示效果；本地代码审查不能替代逐页浏览器验收。
- 真实历史批次数量超过一页时的连续加载和汇总导出结果。
- 卡台实际切换后，总览路线名称、账户余额和快照提供方是否同时变化；当前卡台升级期间未执行切换。
