**阶段 2 大摸排具体查什么（面间连贯）：**
- **数据流首尾接得上**：一个 CDK 从兑换到交付，端到端走一遍六个面，数据不断链。
- **状态在面间传递不丢**：执行面的结果，展示面/通知面/看板读得到、读得对。
- **无重复、无冲突、无缝隙**：没有两个面抢做同一件事；没有面间规则打架（如销卡时机 vs 一卡多单）；没有"谁都以为对方做了"的缝。
- **红线闭环**：资金安全、销卡、零税、订阅成功不再动，在拼起来的全链路上仍然成立。

**贯穿原则一：需求灵活变通。** 需求不是一次冻死（销卡就是深入才长出来的）。发现前期没考虑到的、或面间打架的，**大脑主动停下跟 Lemon 核对，不自己拍板改需求**。

**贯穿原则二：一贯对着真实核实。** 每个面的设计/落实/验收都对真实代码和生产核实（CLAUDE.md 三道闸门当动作做），不回文档拍脑门。验收由测试（真实响应）+ 脚本 + 生产只读复验证明，不由自述。

**贯穿原则三：每轮必须有给 Lemon 看的文字输出。** 只调工具不写字，Lemon 那边看到的是空白（2026-09-15 实际发生过：连续几轮无可见输出）。任何窗口每轮至少写一句"在做什么 / 发现了什么"。**超长会话是诱因**——所以 V2.0 落实阶段用专门的新窗口，靠本账本恢复状态，不靠对话历史。

## 3. 六个面的确认方案（阶段 1 产出，待填，按 A/B/C 组）

### A 组方案（执行面 + 资源面）· 2026-09-15 出稿，**待 Lemon 审**

> 全部基于 §2 测绘的真实现状；每项标"牵动哪些面"（D-227 要求）。

#### A1 · verify 接线：付款不明先核实，不锁死（D-227）

- **怎么改**：把已有的 `confirmPlus()` 接到 `SUBMIT_UNKNOWN` 的消解上——① 核实到账号已是 Plus → 直接转 `RECHARGE_SUCCESS` → 走取消续费；② 未开通**且无扣款证据** → 允许安全重试（走原有资金栅栏）；③ 核实不了 → 才进"需要我处理"。
- **不新建**：状态机已允许 `SUBMIT_UNKNOWN → RECHARGE_SUCCESS`，verifier 已存在 → 这是**接线/调线**。
- **牵动**：通知面（少推人工）· 展示面（"核实中"态）· 看板（失败构成能分清抓取问题 vs 真拒付）· 资金安全（**不违反"订阅成功绝不再动"**）。
- **DoD**：三分支单测（已开通 / 未开通无扣款 / 核实不了）；生产只读复验一单 `SUBMIT_UNKNOWN` 实际走向；`state-check` 一致。
- **边界**：绝不因"核实不了"就自动重付；重试只允许在"未开通且无扣款证据"。

#### A2 · 按产品化：每卡单数 + 开卡金额 + 后台端点（D-221，其实是 09-07 基线欠账）

- **怎么改**：`card_max_successful_payments`、`default_open_card_amount` 从全局改为**按产品**（Plus **3~4 单可配**／$50——$50 是**为 3 单设计的升级防线**，将来做 4 单要调高；5X·20X **一卡一充**），并按基线"**按 CDK 所带产品在建单时决定，不读全局设置**"；补上开卡金额的**后台写端点**（现在一个都没有）。
- **牵动**：执行面（分卡读按产品值）· 资源面（开卡金额）· 控制面（设置页）· 看板（用卡数/花费）。
- **DoD**：三产品上限与金额单测；端点带审计；建单时读 CDK 产品值而非全局（生产只读复验一单）。

#### A3 · 自动开卡：资金循环模型（Lemon 2026-09-15 确认新设计）

- **怎么改**：**新建 worker 侧 highvcc 开卡路径**（现状零调用）；触发＝订单需求驱动 + 维持 **1~2 张小缓冲**；**不补余额**；每日上限可配；**钱包最低水位**覆盖资金回笼延迟（D-228 补充二）。
- **不做**：库存阈值囤卡（卡活着就有被客户点升级扣钱的风险，囤卡＝扩大暴露面）。
- **牵动**：执行面（没卡时的等待预期）· 通知面（**钱包余额 / 缺卡必推**）· 看板（开卡数/花费/回收额）· 控制面（缓冲池、日上限、水位设置）· 资金安全（卡少活短）。
- **DoD**：离线单测（缓冲逻辑/日上限/水位）；**真开卡是花钱动作 → 先 dry-run，再由 Lemon 确认一次真开**；生产只读复验。
- **优先级**：hnskj 侧卡台本身不稳，排后。
- **前置缺口（D-230，方案原先漏了）**：**highvcc 钱包余额从未入库**（`provider_balance_snapshots` 里 backup-a 一条都没有，只有后台手动点查）→ "钱包最低水位"判断**没有数据源**。A3 必须先补**钱包余额定时同步**，否则水位逻辑是空中楼阁。

#### A4 · 销卡：半自动 + 可销时间（D-228 及其两条补充）

- **怎么改**：交付且用满 N 单的卡 → 进**待销清单**；清单带**可销时间**（开卡时间 + 最短存活期，可配"当天/次日/几点"）；**到点才提醒**；**highvcc 无 API → 提醒 Lemon 手动删**，**hnskj 有 `withdraw` → 自动**；销不掉退回清单稍后再试，并**记录每次真正销成功的时间点**，攒卡台真实规则。
- **牵动**：资源面（卡生命周期终结）· 通知面（到点提醒）· 控制面（待销清单进工作台）· 看板（销卡回收额）· 资金安全（压缩"客户点升级扣我们钱"的窗口）。
- **DoD**：单测（可销时间判断 / 容错重试 / 两卡台分支）；hnskj 自动销走 API 需 Lemon 确认一次；生产只读复验。
- **硬约束**：风险窗口压不到 5~6 小时以下，设计消不掉。
- **D-229 修正**：真实风险是**持续的小额拒付费**（Browser $0.1 / API $0.4 每次），不是"余额被扣走"（$50 面额已挡住 $128.75 的升级）。→ **定期批量销即可，不需要"抢着销"**；但**销卡必须做**（不销就一直漏）。

#### A5 · 发布账本推算口径（PLAN 里原称 A3）· **优先级提高（D-229）：一卡 3~4 单靠它计数，而账本计数已证明不可靠**

- **怎么改**：发布工作区 `card-inventory-eligibility.js`（生产 `7efec865` → 工作区 `525b7e1b`）。配套已齐（补余额开关已关成 `false`）。

#### A6 · 卡可用性只读查询（新增，D-229：客户页前置验证的 A 组部分）

- **为什么在 A 组**：客户页要在输入 CDK 时就提示"缺卡/门槛不够"，用的是 A 组的卡资格能力。不在 A 组定，C 组做客户页时要回头改 A 组接口＝返工。
- **怎么改**：把 `eligibleInventoryCardSql` 暴露成**只读、不锁卡、按产品门槛**的可用性查询（区别于分卡时带 `FOR UPDATE` 的事务路径），供①客户页 CDK 验证前置提示 ②后台工作台显示卡况。
- **牵动**：展示面（客户页提示文案——C 组细化）· 控制面（工作台卡况）· 资源面（同一份资格口径，**不得抄第二份规则**）。
- **DoD**：只读查询与分卡口径**同源**的单测（防两套规则漂移）；客户页调用不产生锁；生产只读复验（当前应返回"Plus 有 1 张可用"）。
- **边界**：只读不锁、不预占卡；**前置提示只是提示**，真正的分卡仍在下单事务里做。

### B 组方案（通知面 + 对账看板）· 2026-09-15 出稿，**待 Lemon 审**

#### B1 · 通知面重分类：把"默认全推"倒成"按类别推"（D-219/D-227/D-228）

- **怎么改**：现状是"默认全推 Bark + 两个静音"。倒过来——**四类，推不推由类别定不由数量**：
  - **需要你**（进"需要我处理"队列）：`HUMAN_REQUIRED` / `HUMAN_VERIFICATION` / `ORDER_STALLED` / 同一 CDK 连败 N 次 → **推**
  - **供给**：`CARD_STOCK_EMPTY` / `WAITING_FOR_CARD` / 开卡失败 / 余额低于阈值 → **推**（单独通道）
  - **资金异常**：重复扣款 / 账本与卡台对不上（来自 B4 对账）→ **推**（最高优先级）
  - **信息**：`ORDER_SUBMITTED` / `ORDER_COMPLETED` / `PAYMENT_CONFIRMED` / `PAYMENT_UNKNOWN` → **只进后台/看板，不推**
  - **例外**：`PROVIDER_BALANCE_CHANGED` 虽是 info，**要推**（Lemon 业务判断，D-228——余额是我们的钱，时刻要知道）
- **不新建告警类型**：余额变化告警已存在（§2.4），只改分类与推送开关。
- **牵动**：执行面/资源面（谁触发哪类）· 看板（信息类落看板）· 资金安全（资金异常最高优先级）。
- **DoD**：分类函数单测（每类推/不推正确，含余额变化推、SUBMITTED 不推）；生产灰度对一批真实告警核对分类。

#### B2 · highvcc 交易同步（B 组前置，D-230）

- **怎么改**：新建 highvcc 交易同步——`allTransactions`（账户级流水）→ 按 `provider_card_id` 归属到卡 → 写 `card_transactions`（现同步器只按 hnskj 的"按卡查"语义，highvcc 套不进）。
- **牵动**：看板（花多少钱/拒付/回收的**唯一数据源**）· 对账（B4 要读）。
- **DoD**：同步后 backup-a 在 `card_transactions` 有记录；抽一张 highvcc 卡的流水与卡台后台核对一致（外部字段先验真响应）。
- **优先级**：**B 组第一步**，不补它看板算不准。

#### B3 · 运营看板（D-227）

- **怎么改**：一页看板——今日单数/成功率 · 花了多少钱（含开卡费，依赖 B2）· 用了多少卡 · 两路线各自耗时 · 异常支出（拒付哪张卡）· 当天突发。只读聚合，不建新事实表。
- **牵动**：读执行面（订单结局）· 资源面（卡/花费/余额/回收）· 通知面（当天突发＝当天告警）。
- **DoD**：每个数字都能点到明细（拒付→哪张卡→哪个订单）；生产只读复验各数字与底表一致。
- **注意**：开卡费 $0.5 现在没进 `card_transactions.fee`（§2.3），花费统计要单独把开卡费算进来。

#### B4 · 自动对账接进流程（D-219 发现 7）
