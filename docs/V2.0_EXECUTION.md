## 0. 工作流程（Lemon 2026-09-15 确认，四阶段 + 两条贯穿原则）

**四个阶段，前一个不过不进下一个：**

| 阶段 | 做什么 | 谁做 | Lemon 花时间吗 |
|---|---|---|---|
| **0 真实测绘** | 摸六个面的真实代码/生产，对照文档，过时/做错/没落地的全现形 → 真实地图（§2） | 大脑窗口 | 不用 |
| **1 逐面方案 + 分组审** | 每个面：真实现状 + 怎么改 + 影响哪些面 + DoD；按耦合分三组给 Lemon 审、拍板（§3） | 大脑出，Lemon 审 | 审方案，不重提需求 |
| **2 整体大摸排** | 六个面方案拼起来，验全局连贯（下方清单）→ 没缝才算方案定稿（§4） | 大脑出，Lemon 一起过 | 一起过一次 |
| **3 落实** | 开专门执行窗口，强耦合先串行、弱耦合再并行；每面做完给真证据（§5） | 执行窗口 | 只看验收证据 |

**阶段 2 大摸排具体查什么（面间连贯）：**
- **数据流首尾接得上**：一个 CDK 从兑换到交付，端到端走一遍六个面，数据不断链。
- **状态在面间传递不丢**：执行面的结果，展示面/通知面/看板读得到、读得对。
- **无重复、无冲突、无缝隙**：没有两个面抢做同一件事；没有面间规则打架（如销卡时机 vs 一卡多单）；没有"谁都以为对方做了"的缝。
- **红线闭环**：资金安全、销卡、零税、订阅成功不再动，在拼起来的全链路上仍然成立。

**贯穿原则一：需求灵活变通。** 需求不是一次冻死（销卡就是深入才长出来的）。发现前期没考虑到的、或面间打架的，**大脑主动停下跟 Lemon 核对，不自己拍板改需求**。

**贯穿原则三：每轮必须有给 Lemon 看的文字输出。** 只调工具不写字，Lemon 那边看到的是空白（2026-09-15 实际发生过：连续几轮无可见输出）。任何窗口每轮至少写一句"在做什么 / 发现了什么"。**超长会话是诱因**——所以 V2.0 落实阶段用专门的新窗口，靠本账本恢复状态，不靠对话历史。

**贯穿原则二：一贯对着真实核实。** 每个面的设计/落实/验收都对真实代码和生产核实（CLAUDE.md 三道闸门当动作做），不回文档拍脑门。验收由测试（真实响应）+ 脚本 + 生产只读复验证明，不由自述。

### 2.1 资源面 · 卡台能力（销卡相关，2026-09-15 测绘）

**两个卡台的真实 API（`v1/src/providers/*.js`，我们已接的）：**
- **highvcc**（backup-a，base `www.highvcc.com`＝舜捷跨境）：8 端点——`openCardCost` `newCard`(开卡) `detail` `autoCard` `rangeList` `page`(列表) `wallet` `authTrans`(交易)。**无删卡、无提余额端点。** `newCard` 返回 `cardId`（能定位卡）。
- **hnskj**（legacy-primary）：有 `withdraw`（`POST /cards/{id}/withdraw`，提走卡余额），已接但没接成自动流程。

**销卡机制对比：**
- highvcc = 删卡（删了余额自动回钱包），Lemon 手动能做；**highvcc 卡台没有删卡 API（Lemon 2026-09-15 确认，目前都是他手动删）** → **highvcc 侧自动销卡不可行**。务实方案：系统判断"该销哪些卡（已交付+不再服务新单+到销卡时机）"→ 列待销清单 → 提醒 Lemon 手动删（**半自动**，符合"系统解决不了才叫人"）。这是 A 组销卡方案的硬约束。
- hnskj = withdraw（提余额），API 已接。

**文档 vs 真实**：无既有文档描述销卡能力，本次测绘首次落实；D-228 记的需求现状＝highvcc 侧能力未知、hnskj 侧有 withdraw 未自动化。

### 2.2 执行面 · 骨架与 verify 现状（2026-09-15 测绘）

- **路线分叉点**：`workflow-handlers.js:228` 读 `recharge_executor_kind`（API/BROWSER）→ 235 分 BROWSER、255 分 API，分叉后两条独立。V2 执行面接口要统一，就动这里。
- **交付四步**：落在 `browser_operations.operation_type`（`PAYMENT_SUBMIT` / `PAYMENT_CONFIRMED` / …），Browser 侧。API 侧四步落哪＝待查。
- **verify 能力已存在且完整（关键，利好 D-227 + V2.1）**：`chatgpt-post-payment-verifier.js`（深读 2026-09-15）——
  - `confirmPlus()`：轮询 `/backend-api/accounts/check` 核实账号 `hasActive && plan 含 plus` → **正是 D-227"付款不明先 verify"，已存在**。
  - `confirmCancellation()`：读订阅 → 调 `/backend-api/subscriptions/cancel` 取消续费 → 确认 `willRenew=false`。交付第四步，已存在（apple/google 来源不支持退，会标 `unsupportedOrigin`）。
  - `openUpgradeDialog()`：**5X/20X 升级雏形已存在**——账号已 Plus 后开升级对话框、选 tier、停在"Confirm plan changes"**不按 Pay now**。→ **D-224"5X/20X 无真实样本"要更新：代码骨架有了。**
  - 读订阅真实字段：`hasActive` / `subscription_plan` / `will_renew` / `purchase_origin_platform`。
- **SUBMIT_UNKNOWN 不是死锁**：状态机允许 `SUBMIT_UNKNOWN → RECHARGE_SUCCESS / CANCELLATION_PENDING`（`order-status.js:59`），worker 有 `POLL_RECHARGE` / `RECHECK_CANCELLATION` 轮询已有订单（`worker-runtime.js:20`）；`confirmPlus` 在 Browser 付款流程里被调（`payment-executor.js:265`、`shared-live-composition.js`）。→ **D-227"付款不明先 verify"零件齐全，是接线/调线级别，不是重建**。最后一厘米（POLL_RECHARGE 对 Browser 的 SUBMIT_UNKNOWN 具体怎么核实）留方案时钉。

### 2.3 资源面 · 卡供给现状（2026-09-15 当场重查）

- **卡资格 SQL**（`card-inventory-eligibility.js`）：A3 账本推算口径**仍未发布**（生产 `7efec865` ≠ 工作区 `525b7e1b`）；配套已齐（补余额开关已关成 `false`），**可以发了**。三处读 `card_max_successful_payments`。
- **每卡单数 = 全局 `card_max_successful_payments=3`**（后台能设 1-4），**非按产品**。5X/20X 启用要按产品——V2.0 建。
- **开卡金额 = 全局 `default_open_card_amount=16`**，**无后台写端点**（`create-app` 无）。Plus 3 单需 $50 → V2.0 加按产品端点。
- **自动开卡**：hnskj 走 worker 的 `PURCHASE_CARD` 任务（`card_auto_replenishment_enabled=false` 关着，且生产从没成功过）；**highvcc 根本没有自动开卡路径**——`openCard` 只注册给后台手动端点（`server.js:229` → `create-app.js:417`），**worker 侧零调用**，`supports_auto_open=0`。→ **主力卡台的自动开卡要新建 worker 路径，不是打开一个 flag。**
  - 更正（2026-09-15，Lemon 质疑后复核）：此前写"flag 关、有人工确认词"**两处都不准**。服务端 `openCard` 的 `confirmation` 是机器校验字段（须等于 `开卡 {vid} {amount}`），按 09-06 基线**由页面填充、运营不手打**；后台卡片页有完整开卡表单（卡段/金额/报价/开卡按钮/钱包）。我此前引用的 `--confirm` 证据来自本机 CLI，**不是业务路径**。
- **余额同步**：`pojia-highvcc-snapshot-sync.timer` + `pojia-card-read-sync.timer` 在跑；订单触发 `order-demand-sync`。
- **销卡**（见 §2.1）：highvcc 无 API（半自动），hnskj 有 `withdraw`。
- **SUBMIT_UNKNOWN（真实锁定机制）**：付款不明 → `status=SUBMIT_UNKNOWN, funds_risk_state=UNKNOWN`（`recharge-attempt-repository.js:476`、`browser-execution-repository.js:1000`）。
- **待深挖**：post-payment-verifier 细节、API 侧四步、`SUBMIT_UNKNOWN` 后有没有自动 verify 消解（这正是 D-227 要接的点）。
