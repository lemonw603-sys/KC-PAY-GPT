**阶段 2 大摸排具体查什么（面间连贯）：**
- **数据流首尾接得上**：一个 CDK 从兑换到交付，端到端走一遍六个面，数据不断链。
- **状态在面间传递不丢**：执行面的结果，展示面/通知面/看板读得到、读得对。
- **无重复、无冲突、无缝隙**：没有两个面抢做同一件事；没有面间规则打架（如销卡时机 vs 一卡多单）；没有"谁都以为对方做了"的缝。
- **红线闭环**：资金安全、销卡、零税、订阅成功不再动，在拼起来的全链路上仍然成立。
- **主动发现 > 对照清单（Lemon 2026-09-15 强调）**：巡检清单（`UX_PUNCHLIST` 23 条 + `SYSTEM_REMEDIATION` 19 条）只是**已发现问题的一部分**，大摸排拿它当**对照子集**确保不漏，但**绝不以它为边界**——重点是系统走查一个 CDK 的完整旅程，**主动找清单外、还没人列过的新缝**。做着做着退化成"逐条核对清单"＝失败。

**贯穿原则一：需求灵活变通。** 需求不是一次冻死（销卡就是深入才长出来的）。发现前期没考虑到的、或面间打架的，**大脑主动停下跟 Lemon 核对，不自己拍板改需求**。

**贯穿原则二：一贯对着真实核实。** 每个面的设计/落实/验收都对真实代码和生产核实（CLAUDE.md 三道闸门当动作做），不回文档拍脑门。验收由测试（真实响应）+ 脚本 + 生产只读复验证明，不由自述。

**贯穿原则三：每轮必须有给 Lemon 看的文字输出。** 只调工具不写字，Lemon 那边看到的是空白（2026-09-15 实际发生过：连续几轮无可见输出）。任何窗口每轮至少写一句"在做什么 / 发现了什么"。**超长会话是诱因**——所以 V2.0 落实阶段用专门的新窗口，靠本账本恢复状态，不靠对话历史。

### 2.1 资源面 · 卡台能力（销卡相关，2026-09-15 测绘）

**两个卡台的真实 API（`v1/src/providers/*.js`，我们已接的）：**
- **highvcc**（backup-a）：**不是卡台 API,是"网页 token 扒取"同步工具**(2026-09-15 读代码+Lemon 确认钉死)。真相:provider 用**你在后台手动贴的网页登录 token**(`app_settings.highvcc_access_token_ciphertext`,`/highvcc/token` 端点 setToken),带 `Bearer {token}` 打 `www.highvcc.com` **内部地址**读数据;token 会**登录态过期**(401 报"登录/过期",过期需 Lemon 重贴)。→ **highvcc 无官方 API**:开卡/删卡你都在网站手动做。**但「读卡」是自动的**——`pojia-highvcc-snapshot-sync.timer` 每小时用这 token 拉全量卡、刷 `cards.current_balance`(§2.3 生产核实:enabled、次次 SUCCESS),唯一单点是 token 过期时同步失败、需重贴,**不是"随时不可用"**。账本任何"highvcc newCard API/自动开卡"表述都是错的,已删。**三件事务必分清:①开/删卡=手动 ②读卡余额=timer 自动 ③钱包账户余额+交易流水=至今未入库(§2.4/D-230)**;按**无官方 API 卡台**对待(开删手动、读卡自动)。
- **hnskj**（legacy-primary）：有 `withdraw`（`POST /cards/{id}/withdraw`，提走卡余额），已接但没接成自动流程。

**销卡机制对比：**
- highvcc = 删卡（删了余额自动回钱包），Lemon 手动能做；**highvcc 卡台没有删卡 API（Lemon 2026-09-15 确认，目前都是他手动删）** → **highvcc 侧自动销卡不可行**。务实方案：系统判断"该销哪些卡（已交付+不再服务新单+到销卡时机）"→ 列待销清单 → 提醒 Lemon 手动删（**半自动**，符合"系统解决不了才叫人"）。这是 A 组销卡方案的硬约束。
- hnskj = withdraw（提余额），API 已接。

**文档 vs 真实**：无既有文档描述销卡能力，本次测绘首次落实；D-228 记的需求现状＝highvcc 侧能力未知、hnskj 侧有 withdraw 未自动化。

### 4.1 走查发现（逐段填,缝记这里）

**第一段「你生成 CDK → 客户输入」(2026-09-15 走查)**
- ✅ 产品身份流通：CDK 生成绑 `cdks.plan_type` → 验证返回 planType → 建单读 plan_type，三处同源。

**第二段「兑换下单 → 分卡 / 缺卡开卡」(2026-09-15 走查)**
- ✅ 分卡并发保护有：`workflow-repository` 用 `FOR UPDATE SKIP LOCKED`,同时来单不抢同一张卡。

**第三段「付款 → 核实交付 → 客户看四态」(2026-09-15 走查)**
- ✅ 状态映射完整：`order-status-service` 内部态→客户 10 视图态齐全(SUBMIT_UNKNOWN→VERIFYING、WAITING_FOR_SESSION→ACTION_REQUIRED)。
