# CDK 系统对抗式审查报告

审查日期：2026-08-19。本文保留尚未解决的扩量风险，不把它们误写为当日 MVP 启动阻断。

审查对象：v1 CDK 生成、兑换、订单创建、管理员会话与线上部署边界。

证据等级：代码审查；本地自动化测试 146 pass、11 skipped；生产机隔离临时 MySQL 完整测试 157/157 通过；线上已确认 Web/Worker/MySQL/备份健康。

## 结论

当前版本适合小规模、人工保管明文 CDK 的内部试运行；不适合直接做几十到几百单/天的批量生产。必须先补“生成请求幂等与批次恢复”以及“失败订单的 CDK 处置策略”。否则最容易出现已经生成并写库、但明文丢失，或订单失败后客户资产永久卡死。

## Findings

### F-01（高）：生成成功但响应丢失时，CDK 无法恢复

证据：`createAdminCdkService` 先在事务中提交 `cdks`，再由 HTTP 返回明文；代码库只有 `POST /api/v1/admin/cdks/generate`，没有按批次查询、加密导出或一次性重新取回接口。数据库只保存 `code_hash`。

影响：网络断开、浏览器刷新、代理超时或用户误关闭页面时，CDK 已消耗库存但明文永久不可得；重试会生成另一批，造成数量对不上。

复现思路：让数据库提交成功后人为断开响应，随后查询会发现批次存在，但后台没有任何合法恢复路径。

建议：生成接口增加管理员提供的 `Idempotency-Key`，同一 key 重放返回同一批次结果；批次表保存生成元数据和加密明文文件引用，提供管理员鉴权的一次性下载/重新导出；严禁通过列表接口直接返回全部明文。

### F-02（高）：订单失败后 CDK 永久为 REDEEMED，没有补偿状态

证据：订单创建事务把 CDK 改为 `REDEEMED`；工作流后续即使开卡失败、超时或进入人工复核，也没有 CDK `REISSUABLE/VOID/REFUNDED` 状态或管理员处置接口。

影响：系统故障会把客户已支付的兑换资产锁死，客服只能手工改库，容易重复发码或账务不一致。

建议：先定义业务规则：系统责任失败允许一次补发/换码，客户原因失败不自动退回。将处置写成受审计的状态迁移，不允许直接 SQL 改状态。

### F-03（已处理第一阶段）：CDK 没有套餐/面额字段，订单层硬编码 Plus

证据：`cdks` 表无 `plan_type`；`createOrderFromCdk` 的 INSERT 固定写入 `'plus'`。

影响：一旦加入 Pro、地区差异或不同售价，后台批次标签无法证明兑换权益，错误配置会把不同产品当成 Plus 处理。

处理：已加入 `plan_type` 迁移、生成时写入和订单兑换时快照；当前仍明确拒绝非 `plus`，未来扩展时再增加受支持套餐。

### F-04（中高）：没有生成审计身份和独立批次记录

证据：`cdks` 只有 `batch_no/created_at`，生成接口没有管理员 ID、原因、请求 ID；管理员会话也不携带身份。

影响：无法回答“谁在何时生成了多少张、是否重复点击、哪批泄漏/作废”，也无法可靠对账。

建议：增加 `cdk_batches` 或统一审计事件，至少记录 `batch_no、created_by、request_id、count、plan_type、created_at、status`；管理员会话绑定 operator 标识。

### F-05（已处理第一阶段）：服务端上限 10,000 与页面上限 1,000 不一致

证据：服务端 `MAX_BATCH_SIZE=10_000`，页面 input 为 `max=1000`。

影响：直接调用 API 可一次生成 10,000 张并把全部明文放入响应，造成误操作、浏览器内存/剪贴板泄漏和库存冲击。

处理：服务端上限已统一为 1,000；更大批量仍应改为分批任务和加密文件下载，不在 JSON 中返回全部明文。

### F-10（已处理第一阶段）：没有按批次作废能力

处理：已加入 `POST /api/v1/admin/cdks/:batchNo/revoke`，只会把该批次仍为 `AVAILABLE` 的 CDK 标记为 `REVOKED`，不会触碰已兑换订单。完整操作审计和批次恢复仍在 F-01/F-04 范围内。

### F-06（中）：生成接口没有独立写操作限流或二次确认

证据：只有登录限流；`POST /api/v1/admin/cdks/generate` 没有按管理员/会话的次数和数量限制。

影响：会话被盗或页面被重复提交时，可快速生成大量可兑换资产。

建议：加会话级限流、单日配额和显式批量确认；所有拒绝也写审计事件。

### F-07（中）：管理员写接口依赖 SameSite，缺少显式 CSRF 防护

证据：Cookie 设置 `HttpOnly; SameSite=Strict`，但生成和同步接口没有 CSRF token，也没有 Origin/Referer 校验。

影响：浏览器策略、代理或未来新增跨站场景变化后，资产写操作保护不足。

建议：在所有管理员 POST/DELETE 写接口统一校验 Origin，或加入 CSRF token；不要把 SameSite 当作唯一防线。

### F-08（中）：管理员会话不能单独撤销

证据：签名 Cookie 是无状态令牌，12 小时内仅凭签名有效；退出只清理当前浏览器 Cookie，服务端没有会话吊销表或会话版本。

影响：Cookie 泄漏后无法立即让已发出的其他会话失效；重置密码也不会自动失效旧会话。

建议：增加会话版本/撤销时间（至少密码轮换时全量失效），并把 operator ID 写入令牌或服务端会话。

### F-09（中）：导入 CDK 允许低熵自定义码，数据库泄漏时可离线猜测

证据：导入格式只要求 8–128 个字母、数字、下划线或短横线；哈希为无盐 SHA-256。

影响：用户自定义的短码可能被字典枚举，进而被兑换或查询订单。

建议：生成码保持当前高熵；导入码至少要求更长且禁止常见模式，或使用带服务器密钥的 HMAC 哈希。不要为已有高熵生成码改成低熵兼容。

## 已确认的正面控制

- 生成码使用 `crypto.randomInt`，生成批次内部去重。
- 数据库不保存 CDK 明文，只保存哈希，并有唯一约束。
- 兑换使用 `SELECT ... FOR UPDATE` + 事务，设计上可避免同一 CDK 双花。
- Session 在入库前加密；客户接口不返回内部订单、卡片或 Session 字段。
- 卡台开卡权限与订单 Worker 隔离；直充任务没有指定订单的短时一次性 Permit 时不可领取。
- `npm audit --omit=dev` 当前无已知生产依赖漏洞。

## 验证边界

生产机隔离 MySQL 已验证并发兑换、事务回滚、批次完整插入、任务租约和完整假 Provider 链路。这些证据不替代小批量真实客户订单放量。

## 修复顺序

1. F-01：幂等键 + 批次恢复/加密导出。
2. F-02：失败订单 CDK 补偿/作废状态机。
3. F-03：明确 Plus-only 或加入套餐快照。
4. F-04、F-05、F-06：审计、统一上限、生成限流。
5. F-07、F-08、F-09：管理员防护和导入策略。
