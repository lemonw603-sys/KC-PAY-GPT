# Plus 运营后台全量审计（第一轮事实盘点）

日期：2026-08-22
状态：审计进行中；本文件只记录已从当前源码核对出的事实，不把未实测项目写成结论。

## 1. 当前后台页面入口

当前 `v1/public/admin/index.html` 声明 9 个导航入口：

- 总览 `overview`
- 订单 `orders`
- 异常队列 `exceptions`（复用订单视图的 REVIEW_REQUIRED 过滤）
- 资金证据核对 `reconciliation`
- 卡余额充值 `card-funding`
- 卡台路线 `provider-routes`
- Browser 执行 `browser`
- 卡片库存 `stock`
- CDK 管理 `cdks`

当前页面中有 8 个实际 `<section>` 视图；`exceptions` 没有独立 section，而是由 `switchView()` 映射到订单视图。这是代码事实，不代表一定是错误。

## 2. 总览 API 与前端实际使用情况

后端 `getOverview()` 返回：

- `metrics`：总订单、今日订单、成功订单、处理中、待执行充值、需关注、三方对账异常、成功率；
- `orderStatuses`；
- `cdkStatuses`；
- `refundStatuses`；
- `openAlertCount`；
- `runtimeHealth`；
- `operationalBacklog`：待验证新卡、资金风险、卡余额充值风险、人工复核、对账案例、卡片同步积压；
- `cardStock`：可用、开卡中、已分配、耗尽、隔离、低库存线和低库存布尔值；
- `settings`。

前端 `loadOverview()` 当前实际渲染 11 张指标卡：

1. 今日订单
2. 自动处理中
3. 待执行充值
4. 需要关注
5. 三方对账异常
6. 资金结果未决
7. 卡余额充值待处理
8. 待验证新卡
9. 本地可分配卡
10. 订单 Worker
11. 已完成订单成功率

## 4. 当前不能仅凭源码确定的项目

以下必须通过实际服务或生产页面核对，不能猜测：

- 用户看到的“卡片消失”是源码设计问题、生产 release 版本不一致、静态资源缓存，还是 API 返回异常；
- 生产总览 API 当前实际返回的字段和值；
- 当前生产页面实际渲染了几张卡；
- 其他视图是否存在“接口返回但页面遗漏”或“页面控件请求失败”；
- 数据库中的统计值是否与卡片定义一致。

## 6. 公网只读核对结果（2026-08-22）

对 `https://ops.vibebridge.top/admin` 和其公开静态资源进行只读请求得到：

- 后台 HTML HTTP 200，响应体 1,661 bytes；引用的是 `admin.css?v=8`；
- 公网 `admin.js?v=17` HTTP 200，响应体 92,636 bytes；响应时间为 `Fri, 21 Aug 2026 23:57:26 GMT`；
- 公网脚本包含“资金结果未决”和“已完成订单成功率”，但不包含当前本地源码新增的“卡台路线”和“卡余额充值待处理”；
- 当前本地 `v1/public/admin/index.html` 引用 `admin.css?v=17`、`admin.js?v=17`，本地 `admin.js` 文件大小为 116,078 bytes；
- 公网 HTML 与当前本地 HTML 的静态资源版本不一致，说明公网后台不是当前工作树这版静态资源。仅凭此事实不能判断具体部署原因，但可以确认公网未提供当前本地最新后台界面。

这直接解释了用户看到的部分后台内容缺失：至少存在“本地实现与公网实际资源不一致”。仍需在生产服务器上核对 release、部署清单和静态文件哈希，才能确定应发布哪个已验收版本。

## 7. 与现行后台合同/阶段计划的对照结果

与当前本地总览前端逐项对照，已确认未作为独立总览指标或区域展示的项目：

- 卡台账户余额；
- Provider 健康状态（当前只有订单 Worker 健康，不等于 Provider 健康）；
- 等待 Session 数量；
- 等待补卡数量；
- 取消续费待确认数量；
- 自动补卡今日用量/剩余量；

- CDK 状态分布；
- 退款观察分布；
- 对账案件开放数量；
- 卡片同步积压数量。

这些是“当前合同/计划要求”与“当前总览展示”之间的事实差异。是否全部恢复为总览卡片，仍需按运营优先级决定；但它们不能继续被描述为已经在总览完整体现。

## 8. 卡台路线后台的已确认缺口

当前 `provider-route-admin-service.js` 的切换门槛只核对：

- `read_enabled`；
- `circuit_state = CLOSED`；
- `retry_after_until` 未生效。

当前列表/切换 SQL 没有核对：

- 卡台账户实时余额；
- 可用卡段或剩余卡数量；
- 卡台目录快照是否新鲜；
- Provider 写权限是否满足当前开卡/充值业务。

因此，当前只能把它描述为“基础健康门槛人工切换”，不能描述为“完整卡台健康检查后切换”。生产尚未部署该路线切换功能。

## 11. 继续核对发现的页面/API缺口

### 卡片接管

后端存在以下受保护接口：

- `POST /api/v1/admin/card-intake/:batchId/validate`
- `POST /api/v1/admin/card-intake/:batchId/accept`

当前后台 JavaScript 没有调用这两个接口；“待验证新卡”页面只有“同步并接管新卡”入口。因此后端已有的分步验证/接管能力没有对应的独立人工操作入口。这是已确认的页面/API覆盖缺口。

### 设置

后台合同/阶段计划把最低余额、库存阈值、自动补卡参数、卡段、Provider 门禁和并发列为设置管理范围。当前导航没有独立“设置”页面；目前只在总览显示部分开关、在库存页显示库存阈值和自动补卡日上限。其余设置没有统一后台入口。这是已确认的界面组织缺口，具体哪些设置允许后台修改仍需遵守现有安全门禁，不能直接开放全部配置。

### 第一轮页面覆盖修复

已补上卡片接管页面对后端接口的调用入口：

- 最近批次可发起重新验证；
- 已验证批次可进入人工接管；
- 接管仍经过后台敏感操作保护；
- 不改变卡台 API 或生产数据。

本地脚本语法和后台静态资源测试通过。尚未部署公网。
