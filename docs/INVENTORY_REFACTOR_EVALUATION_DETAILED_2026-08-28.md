# 库存模块重构评估（详细版，2026-08-28）

## 结论先行

当前库存实现不是“完全错误”，但把接管、同步、资金准备、分配资格和历史追溯混在多个字段/模块中，明显超出一单 Plus 充值所需的最小模型。建议**先不删表、不改生产状态**，按“运行判断收敛、历史证据保留”的方式渐进重构。

## 代码事实盘点

当前运行资格实际由多处共同决定：

- `cards.inventory_status`：`AVAILABLE/ASSIGNED/PROVISIONING/DEPLETED/HELD_FOR_REVIEW` 等；
- `cards.intake_status`：`ACCEPTED/LEGACY_ACCEPTED` 等；
- Provider 状态（active 等）；
- 卡资料密文是否存在；
- 最近交易同步时间是否在 15 分钟内；
- 当前余额是否达到最低值；
- `card_assignment_history` 是否存在任何历史记录；
- `card_transactions` 是否存在任意 `PURCHASE`；
- `refund_cases` 是否存在未撤销案件。

这些条件全部同时满足才进入可分配 SQL。该逻辑能防止误用消费卡，但也会把“暂时没钱/暂时没抓到资料/永久失效”混在同一条资格链上。

## 应保留（真正解决问题）

1. 一张卡是否已绑定订单（防并发重复分配）。
2. 卡资料是否完整且可读取（付款必需）。
3. 余额是否达标，以及补余额任务状态（资金安全）。
4. Provider 交易唯一 ID 去重（避免重复计数和重复退款识别）。
5. 已消费次数/上限（为未来一卡多充服务）。
6. 订单、卡片、Provider 交易的追溯关系（异常处理必需）。
7. Provider 明确终态和退款案件记录（不可丢失的历史证据）。

## 应合并（减少运行复杂度）

### A. 把 `inventory_status` 与临时准备状态分开

建议运行层只保留：`READY`、`IN_USE`、`BLOCKED`；余额和资料问题用独立原因字段表达，例如 `funding_state`、`credentials_state`。这样“卡没钱”不会被误读为“卡坏了”。

### B. 把 intake/review 作为接管审计，不直接承担全部库存语义

`card_discoveries`/批次记录继续保留用于审计；最终是否可分配只读取一份规范化的卡片资格视图，避免后台同时展示多套互相矛盾的数字。

### C. 同步 tier 与显示状态分离

`sync_tier` 只决定下一次读取时间，不应直接代表卡是否可用；同步过期应显示“待刷新”，而不是直接显示“坏卡”。

## 应删除或降级为后台详情（不是立刻物理删除）

- 将 `providerActiveCount/providerOnlyActiveCount/unresolvedActive` 等 Provider 对账指标从日常库存主卡片移到“同步详情”；
- 将 discovery 批次的 discovered/review/failed 计数从运营首页移到审计页；
- 将多种同步 tier、历史批次状态从日常“可分配库存”口径中移除；
- 不再为每个临时读取失败创建高频告警，只保留状态变化或连续失败告警。

## 一卡多充的最小数据基础

Provider 交易是重要证据，但不能作为唯一计数来源：本次已完成的真实订单 `PJV1-FqFnMiSKBtLGN14GyP7W` 已确认 `RECHARGE_SUCCESS` 且绑定卡 `1477`，但本地 `card_transactions` 当前尚未有该卡交易行，说明交易同步可能晚于订单完成。若只数 Provider `PURCHASE/SUCCESS`，会漏计并导致超额复用风险。

因此最小可靠计数应同时记录两类事实并去重：

1. 本地订单履约成功 + 卡绑定（订单成功即占用一次额度）；
2. Provider `PURCHASE/SUCCESS` 唯一交易（用于确认、补账和发现本地遗漏）。

订单关联不是展示上的前置条件，但在“限制每卡最多 3 次”这一资金安全规则上必须有一个可追溯的占用事实；否则无法在 Provider 交易尚未同步时阻止第四次使用。

## 不能直接做的事情

- 不能因为余额不足就把卡标成永久不可用；
- 不能因为资料一次读取为空就判定卡坏；
- 不能把 Provider `active` 直接当作可分配；
- 不能删除历史 discovery/交易记录来“清理臃肿”；
- 不能在没有回填和回滚方案时直接改现有状态枚举。

## 推荐实施顺序

1. 先增加只读“资格原因”投影，不改分配逻辑；
2. 用真实数据验证余额不足、资料读取失败、消费卡三类是否能正确区分；
3. 增加消费计数和唯一约束；
4. 后台主视图只展示 `READY/IN_USE/BLOCKED` 和原因，详细审计另页展示；
5. 通过隔离 MySQL 和单笔回归后，再考虑简化旧字段/视图。

## 库存数据清理计划

清理不能直接批量删除。建议分四步：

1. **只读盘点**：按卡片、Provider 状态、余额、绑定、消费交易、退款案件和最近同步时间生成分类清单，先确认哪些是重复记录、历史记录、临时状态和真正可分配卡。
2. **停用展示**：把低价值的 Provider 对账数字、批次统计、同步 tier 从运营首页移到详情/审计页；不删除底层证据。
3. **软停用运行状态**：对不再参与分配的旧卡或旧状态使用 `ARCHIVED/RETIRED` 类标记（具体字段待设计），保留卡、订单、交易和 discovery 关联。
4. **极少量物理清理**：仅考虑无订单、无交易、无审计引用且确认是重复/临时数据的记录；先备份、设置保留期、提供回滚，禁止删除真实消费卡和历史交易。

时间顺序：先完成消费计数基础，再做只读盘点；盘点结果经确认后做展示收敛和软停用，最后才评估物理清理。生产暂停期间只做盘点和代码准备，不直接删除生产数据。
