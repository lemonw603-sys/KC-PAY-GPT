# 多卡源/卡台切换策略（Browser 优先）

> 状态：讨论稿（用户尚未最终确认，代码尚未实现/部署）。更新时间：2026-09-05
>
> 目的：在不复制订单、资金账本、卡片和审计系统的前提下，支持原 HNSKJ 与多个备用卡台高频切换；备用卡台可以只提供银行卡/账单资料并仅用于 Browser。

## 1. 不变的业务边界

- 订单、`recharge_attempts`、卡片消费账本、资金栅栏、租约和审计只有一套。
- 充值路线在建单时冻结；卡源在成功分配时冻结。之后切换策略不影响已分配订单。
- 资金状态为 `SUBMIT_UNKNOWN`/付款结果未知时，禁止换卡、换卡台、换执行器或重付。
- API 只能选择声明 `API_RECHARGE` 能力且健康的卡源；无 API 的手工导入源永远不会进入 API 分配。
- Browser 可以选择声明 `BROWSER_RECHARGE` 能力的 HNSKJ 或备用卡源。
- 卡源选择失败只能进入有界重试/人工复核，不静默跨源重付。

## 2. 卡源目录（Card Source Registry）

每个卡源是一条可注册记录，而不是写死的“主卡台/备用卡台”：

- `source_id`：稳定内部标识；不使用供应商名称作为业务主键。
- `provider_code` / `account_code`：外部适配器和账户引用。
- `capabilities`：`API_RECHARGE`、`BROWSER_RECHARGE`、`CARD_CREATE`、`CARD_FUND`、`MANUAL_IMPORT`。
- `priority`：同一路线内的整数优先级，数值越小越优先。
- `enabled`：运营是否允许新订单选择。
- `health_state`：`HEALTHY`、`DEGRADED`、`UNAVAILABLE`、`UNKNOWN`；由最近探针/任务结果更新。
- `sync_tier`：例如 `HNSKJ`、`MANUAL_IMPORT`，决定是否参与上游同步/补给。
- `config_version`：策略变更的单调版本号，用于订单冻结和审计。

卡源的能力必须由适配器合同和运行证据支持；仅有数据库字段不能证明能力可用。

## 3. Browser 选择策略（最小三种模式）

控制面只保留三个模式，避免把每个底层开关暴露给日常运营：

### AUTO（默认）

按以下顺序选取：

1. 路线能力匹配（Browser）；
2. `enabled=true`；
3. `health_state=HEALTHY`，`DEGRADED` 只在明确兜底规则允许时使用；
4. 有资格、未被活动订单/未知资金状态占用的卡；
5. 运营者指定的来源选择；
6. 卡余额、剩余成功次数和地址占用等既有资格规则。

### PREFER_SOURCE（指定来源）

运营者明确选择一个来源后，新订单只使用该来源。该来源没有合格卡、健康状态不允许或能力不可用时，订单停留在可见的等待/人工处理状态，**不得自动回退到其他卡台**。

### DISABLE_SOURCE（暂停来源）

将指定来源排除新订单选择；不影响该来源已分配订单、历史账本和对账。恢复只改变后续新订单。

API 控制面复用同一目录，但自动过滤无 `API_RECHARGE` 的来源；不提供 Browser 专属手工卡台给 API。

## 4. 订单冻结与事务边界

1. 建单事务写入 `route_code` 和 `route_policy_version`。
2. 分配事务锁定候选卡行与卡源映射，原子写入 `card_id`、`card_source_id`、`source_policy_version` 和 assignment。
3. 创建充值 attempt 后，卡源不得被策略切换覆盖。
4. 付款提交前可以处理“尚未分配且未进入资金未知”的运营例外；必须生成新的审计事件并保留原失败原因。
5. 付款提交后，无论成功、失败还是未知，均沿用冻结来源完成对账；未知状态只能人工处置。

## 5. 后台控制面

集中在一个“卡源策略”区，不把入口分散到卡片库存、卡台路线和 Browser 页面：

- 当前路线策略：AUTO / 指定来源优先；
- 每个来源：启用/暂停、优先级、能力标签、健康状态、可分配数量；
- 最近一次变更：操作者、时间、旧/新版本、原因；
- 订单影响提示：只影响新订单；进行中的订单保持原来源。

页面只允许改策略字段，不允许直接改卡片状态、余额、资金 attempt 或付款许可。底层高级权限继续单独保护。

## 6. 故障与恢复

- 健康探针失败只标记来源为 `DEGRADED/UNAVAILABLE`，不会删除卡、释放活动 assignment 或重建订单。
- AUTO 也只在当前策略允许的来源集合内选择；发生来源故障时不跨到运营者未选择的来源。
- 指定来源不可用时进入可见的 `WAITING_FOR_CARD`/`REVIEW_REQUIRED`，由运营者处理是否切换；系统不自动回退。
- 来源恢复后只恢复其新订单资格，不回溯改写历史订单。
- 卡源操作必须幂等；重复点击不能产生重复策略版本或重复审计。
- 运营者切换来源是明确的全局操作，新的来源选择只影响尚未冻结的新订单。

## 7. 最小实现批次

1. 新增卡源策略表/版本与审计事件（复用已有 `provider_accounts` 和 `fulfillment_route_card_sources`，不复制卡表）。
2. 将 Browser 分配查询改为按策略版本读取来源，并返回冻结来源字段。
3. 增加单事务的 AUTO/PREFER/DISABLE 选择器和 API 能力过滤。
4. 后台新增集中策略入口及来源分组统计；保留现有“卡台路线”用于路线/Provider 映射，不混淆为同一动作。
5. 增加并发切换、订单冻结、未知付款锁定、重复操作、无 API 源排除和来源故障隔离测试。
6. 先本地/隔离库回归，再生产只读部署核对，最后才在用户当次确认下做真实资金动作。

## 8. 预审查清单（待用户讨论确认）

- **复杂度风险**：不新增第二套订单或账本；目录、策略和版本是已有来源映射的薄层，复杂度可控。
- **误切换风险**：订单冻结和 attempt/UNKNOWN 闸门阻止付款中换源。
- **能力漂移风险**：能力标签不是自证，必须由适配器合同、健康探针和生产证据共同确认。
- **卡池混淆风险**：来源 ID、独立统计和 UI 分组同时保留；自动分配不把不同来源合并成一个运营池。
- **高频操作风险**：策略变更幂等、版本化，操作只影响新订单；不会要求逐单人工确认。
- **过度设计风险**：首版只实现三种模式、有限状态和一处控制面；不引入无限规则、复杂评分或跨订单动态改路。

## 9. 验收标准

- HNSKJ 可同时声明 API/Browser；手工备用源只能声明 Browser/Manual Import。
- 切换来源后，新订单使用新策略，旧订单仍使用冻结来源。
- API 永远不会分配无 API 源；Browser 可按优先级使用多个源。
- 并发切换与分配不会双分配同一卡或产生重复 attempt。
- 付款结果未知时，任何入口都不能换源或重付。
- 生产部署前后均能从代码、数据库、服务和审计记录复现上述事实。
