# 全局对抗式与系统联动审查报告

**目标：** `https://ops.vibebridge.top/admin`、`https://plus.vibebridge.top/` 及 AI充值业务 v1 生产底座
**日期：** 2026-08-20  
**范围：** 客户提交 → CDK 核销 → 订单/任务 → 卡池/开卡 → 单订单充值放行 → 直充提交/回查 → 卡片交易/退款观察 → 后台告警/备份恢复

## 结论

订单与资金主链路已达到小批量人工盯盘的技术基线。本次找到并修复 2 个可能造成订单卡死或错误判定的关键中断窗口，补上已分配卡自动交易回查、Worker 心跳、超时外部调用可见性、正确的 Docker 启动依赖和有界内存限流。

生产仍有两项非代码风险：数据库备份与密钥同机；关键异常还没有外部通知通道。前者按已确认的放量标准仍是 3–5 单前的必须项，后者可在首批人工盯盘下延后、但必须在 10–20 单前完成。

## 发现与处理

| # | 严重度 | 发现 | 结果 |
|---:|---|---|---|
| 1 | Critical | Permit 消费后、外部调用意图落库前崩溃，订单可停在无法恢复的中间态 | 已修复：Permit、订单 `SUBMITTING` 和 `provider_calls STARTED` 同一 MySQL 事务提交 |
| 2 | Critical | 外部直充已成功、但本地提交失败时，原逻辑可误判为明确充值失败 | 已修复：转入 `SUBMIT_UNKNOWN`，禁止自动二次提交 |
| 3 | High | 已分配卡没有周期性交易回查，退款可能只有手工点同步后才能发现 | 已修复：每小时自动为到期的已分配卡排队，充值成功后立即补一次回查 |
| 4 | High | 加密备份和恢复密钥同机 | 未完成；需指定异地保存位置和独立密钥托管 |
| 5 | Medium | 后台无法直接判断 Worker 是否失联 | 已修复：15 秒心跳，后台显示“订单 Worker 正常/需检查” |
| 6 | Medium | `STARTED` 的直充调用可无限期显示“提交中” | 已修复：超过 2 分钟自动进入三方对账异常 |

| 8 | Medium | 内存限流表不清理，攻击者持续换 IP 可长期增长进程内存 | 已修复：客户状态有界且优先清理过期记录 |
| 9 | Medium | 关键异常只在后台展示，无 Telegram/其他外部通知 | 未完成；首批人工盯盘可接受，10–20 单前必须补齐 |

## 联动矩阵

| 链路 | 失败关闭/幂等 | 可见性 | 验证 |
|---|---|---|---|
| CDK → 订单 | HMAC 查找、唯一订单约束、事务核销 | 批次及审计事件 | 真实 MySQL 并发测试 |
| 订单 → 卡池 | 原子占用，无卡时不自动付费开卡 | 库存状态与卡号明细 | 并发抢卡测试 |
| 开卡任务 → 卡台 | 人工确认、实时规则/余额/额度复核、逐卡幂等 | 任务进度与失败隔离 | 假供应商 + 真实只读合同 |
| 订单 → 直充 | 一次性 Permit、进程开关、调用意图原子落库 | 超时调用进对账异常 | 故障注入 + MySQL 事务测试 |
| 直充 → 订单结果 | 未知结果不自动重提，明确失败二次确认 | 订单时间线、Provider 审计 | 假供应商全链路 |
| 卡片交易 → 退款 | 只读、显式 refund 类型才候选 | 内部提醒；不自动提取 | 分页/字段漂移/误判测试 |
| 数据库 → 恢复 | 加密、哈希校验、14 天保留 | 定时器和运维命令 | 无网络临时 MySQL 恢复 19 张表 |
